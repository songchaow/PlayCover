## PlayCover MCP 架构与设计

### 一、最终架构结论

当前 PlayCover MCP 不是单一入口，而是**两套入口、三种 transport**：

| 模式 | 入口 | transport | 当前定位 |
|---|---|---|---|
| GUI 模式 | `PlayCover/Services/MCPManager.swift` | `StreamableHTTPTransport` | **默认 / 官方方案** |
| GUI 模式 | `PlayCover/Services/MCPManager.swift` | `TCPTransport` | 兼容 / 回退 |
| CLI 模式 | `PlayCoverMCP/main.swift` | `StdioTransport` | 保留 |

### 二、GUI 与 CLI 的职责分工

#### 1. CLI

CLI 入口仍然存在，主要用于：

- 保持 stdio MCP 兼容性
- 提供不依赖 GUI 的本地工具入口
- 保持单元测试与最小闭环验证能力

CLI 入口文件：`PlayCoverMCP/main.swift`

#### 2. GUI

GUI 入口是当前产品侧主方案，主要用于：

- 用户启动 `PlayCover.app` 即自动获得 MCP 服务
- 通过 HTTP 端点对外暴露能力
- 复用 GUI 内已有的设置、状态页、应用生命周期
- 在真实运行中连接 Host、Runtime、PlayTools、Session Bridge

GUI 入口文件：`PlayCover/Services/MCPManager.swift`

### 三、GUI 默认为什么是 HTTP

当前 `MCPManager.TransportType` 只定义两种 GUI transport：

- `http`
- `tcp`

其运行时策略为：

1. **优先 HTTP**
2. **若系统不支持 HTTP transport 依赖（macOS 14 以下）则自动回退 TCP**
3. **TCP 仍可由配置显式选择，但不是主文档推荐路径**

这意味着：

- **GUI 当前对外默认是 `http://127.0.0.1:<port>/mcp`**
- 旧 TCP 文档不能再代表当前推荐接入方式

### 四、整体结构图

```text
CLI Client ── stdio ──▶ PlayCoverMCP/main.swift ──▶ MCPServer

GUI Client ── HTTP POST/GET/DELETE ──▶ StreamableHTTPTransport ──▶ MCPServer
                                                │
                                                ├── MCPSessionManager
                                                ├── SSEEncoder / SSEStreamManager
                                                └── notificationSink

MCPServer
  ├── ToolRegistry
  ├── ResourceRegistry
  ├── MCPLogger
  ├── TaskManager
  └── Host / Session Services

Session Bridge
  ├── RegistrationListener (host 侧注册监听)
  ├── SessionRegistry
  ├── SessionHealthMonitor
  ├── BridgeClient
  └── PlayTools runtime bridge
```

### 五、bootstrap 顺序

#### 1. CLI bootstrap

`PlayCoverMCP/main.swift` 的实际流程是：

1. 创建 `Implementation`
2. 创建 `MCPLogger`
3. 创建 `TaskManager`
4. 创建 `MCPServer`
5. 注册 app / settings / resources / tasks / installer / launch / cleanup / signing / injection / keymap
6. 创建 `SessionRegistry`
7. 启动 `RegistrationListener`
8. 启动 `SessionHealthMonitor`
9. 注册 session / touch / input / capture
10. 创建 `StdioTransport`
11. `transport.run()`

#### 2. GUI bootstrap

`MCPManager.start()` 的流程与 CLI 基本镜像：

1. 归一化 transport 类型
2. 创建 `MCPLogger`
3. 创建 `TaskManager`
4. 创建 `MCPServer`
5. 调用 `registerServices(on:taskManager:)`
6. 启动 HTTP 或 TCP transport
7. 更新 GUI 状态与连接数

这里最重要的设计点是：

- **GUI 与 CLI 的服务注册逻辑必须保持镜像**
- 凡是 tools / resources / session infrastructure 改动，都要检查两条入口是否一致

### 六、MCPServer 的角色

`MCPServer` 是核心分发器，负责：

- 注册内置 method：`initialize`、`ping`、`tools/list`、`resources/list`、`tools/call`、`resources/read`
- 注册 logging method：`logging/setLevel`
- 注册 task method：`tasks/create`、`tasks/get`、`tasks/list`、`tasks/cancel`
- 分发 tool handler
- 分发 resource handler
- 通过 `notificationSink` 向 transport 侧输出服务端主动通知

### 七、Server capabilities

当前 server capabilities 为：

- `tools`
- `resources`
- `logging`
- `tasks`
- **不包含 `prompts`**

也就是说，当前最终 MCP 文档应围绕上面四类能力组织，而不是继续沿用旧阶段的任务卡结构。

### 八、Session Bridge 设计

#### 1. Session 不是 HTTP session 本身

这里有两层 session：

- **HTTP MCP session**：由 `MCPSessionManager` 管理，用于 HTTP 协议握手和 SSE 推送
- **Runtime session**：由 `SessionRegistry` / `RegistrationListener` / `BridgeClient` 管理，用于 Host 与目标 app runtime 的桥接

#### 2. Runtime bridge 主链路

1. Host 侧启动 `RegistrationListener`
2. runtime 在目标 app 中向 host 注册 `sessionId / bundleId / pid / port`
3. Host 将其写入 `SessionRegistry`
4. `SessionTools` 使用 `SessionService` 暴露会话能力
5. `TouchService` / `InputService` / `CaptureService` 通过 `BridgeClient` 与 runtime 通信

#### 3. 固定注册端口

`RegistrationListener.defaultPort` 当前为：

- **`52741`**

这也是 live 联调时必须关注的关键端口。

### 九、Render Capture 在最终架构中的位置

Metal 截帧不是独立产品线，而是当前 MCP 最终形态中的一个 session capability。

它的链路是：

1. Host 设置中开启 `metalCaptureEnabled`
2. 重新安装 app 让 `MetalCaptureEnabled` 生效
3. runtime 侧通过 PlayTools 的 capture service 执行截帧
4. MCP 侧通过 `capture_metal_frame` / `get_capture_status` 暴露能力

因此，相关文档应被收敛到**最终能力文档**里，而不是继续挂在独立阶段目录下。

### 十、关键代码锚点

| 文件 | 作用 |
|---|---|
| `PlayCoverMCP/main.swift` | CLI 入口与 stdio bootstrap |
| `PlayCover/Services/MCPManager.swift` | GUI 入口、transport 选择、服务注册 |
| `PlayCoverMCP/Server/MCPServer.swift` | method / tool / resource 分发核心 |
| `PlayCoverMCP/Transport/StreamableHTTPTransport.swift` | HTTP `/mcp` 端点与 SSE 实现 |
| `PlayCoverMCP/Transport/MCPSessionManager.swift` | HTTP 会话管理 |
| `PlayCoverMCP/Session/RegistrationListener.swift` | runtime 注册监听 |
| `PlayCoverMCP/Session/SessionRegistry.swift` | runtime session 注册表 |
| `PlayCover/Views/Settings/MCPStatusView.swift` | GUI 设置页中的 MCP 入口展示 |

### 十一、当前文档组织原则

最终文档不再回答“当年是怎么一步步做出来的”，而是回答：

- 现在推荐用什么
- 现在代码如何工作
- 现在有哪些能力
- 现在已知有什么问题

因此本目录以**最终状态**组织，而不是以 **Hxx / Gxx / Rxx / RTxx** 任务卡组织。
