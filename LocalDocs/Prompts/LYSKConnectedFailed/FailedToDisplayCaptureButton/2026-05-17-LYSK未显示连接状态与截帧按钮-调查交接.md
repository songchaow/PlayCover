### 四、当前最关键的运行时现象

#### 4.1 PlayCover 的 MCP 服务与注册监听端口都已启动

当前 `PlayCover` 进程监听：

- `19820`：MCP Server 端口
- `52741`：runtime registration listener 端口

同时 `CodeBuddy` 进程已与 `19820` 建立连接，说明：

> **PlayCover GUI 侧的 MCP 服务本身是活的。**

#### 4.2 当前没有任何 runtime app 连到 `52741`

检查端口连接时发现：

- `52741` 只有 `PlayCover` 自己在 `LISTEN`
- 没有任何目标 app 连接到这个注册端口

而 GUI 中 session 状态与截帧按钮的显示前提恰好是：

- `runtimeSessions[bundleId]` 里要有 session
- `CaptureButton` 需要 `sessionIndicatorStatus == "ready"`
- `MCPManager.canCapture(bundleId:)` 也要求至少存在一个 `ready` session

因此当前现象的更精确解释是：

> **不是按钮代码没了，而是当前这次运行没有把 runtime session 注册回 GUI，所以 UI 按规则不显示状态，也不显示截帧按钮。**

#### 4.3 当前实际运行的是 `LYSK`，且它确实加载了 `PlayTools.framework`

当前加载 `PlayTools.framework` 的目标 app 进程为：

- PID：`86979`
- 可执行文件：
  - `/Users/songdogwang/Library/Containers/io.playcover.PlayCover/Applications/com.papegames.lysk.app/Unity-iPhone`

而且它的确映射了：

- `/Users/songdogwang/Library/Frameworks/PlayTools.framework/Versions/A/PlayTools`

这说明：

> **`LYSK` 并不是完全没注入 PlayTools；它确实把 PlayTools 加载进进程了。**

但当前该进程**没有**任何到 `52741` 的连接，所以问题进一步收紧为：

> **PlayTools 已经被加载，但 runtime → GUI 的 session 注册没有成功完成。**

### 五、诊断日志的对照结论

#### 5.1 历史上别的 app / 旧轮次可以成功注册

对 `com.tencent.tmgp.speedmobile` 的历史 `RuntimeLaunchDiagnostics` 日志中，明确存在：

- `playcover_bridge_listener_start_requested`
- `bridge_listener_command_listener_ready`
- `bridge_registration_attempt_started`
- `bridge_registration_established`
- `playcover_bridge_listener_start_succeeded`

因此可以确认：

> **这套 session 注册链路在这个 PlayCover 构建里不是“完全坏掉”的。**

#### 5.2 当前没有找到 `com.papegames.lysk` 的 runtime diagnostics 目录

本轮检查时，没有发现：

- `~/Library/Containers/io.playcover.PlayCover/RuntimeLaunchDiagnostics/com.papegames.lysk/launch-events.jsonl`

这一点很关键，因为 `BridgeListener.swift` / `RuntimeLaunchDiagnostics` 设计上会在启动和注册过程中持续写入事件。

这说明当前更可能是以下几种情况之一：

1. `LYSK` 虽然加载了 `PlayTools.framework`，但没有真正执行到 `PlayCover.launch()`
2. `PlayCover.launch()` 进入了，但 `RuntimeLaunchDiagnostics` 没成功写盘
3. `BridgeListener.start()` 没触发，或很早就异常返回
4. 注册 listener 使用了不同 bundleId / 不同诊断路径，导致当前查找路径偏了

当前还**不能**只凭“没日志目录”就断言是哪一种，但可以明确说：

> **当前缺失的不只是 GUI 状态，而是连用于解释状态的 `LYSK` runtime diagnostics 证据也没看到。**

### 六、当前最高置信判断

2. 当前安装包中确实包含 session status / capture button / RenderCapture 相关 GUI 代码与资源

所以当前最准确的问题定义不是：

> **PlayCover GUI 代码丢了，或者截帧按钮功能不在这个分支。**

而是：

> **在当前 `pre-hokcrash` 现场里，`LYSK` 这次运行虽然加载了 `PlayTools`，但没有成功完成 runtime → GUI 的 session 注册，因此 GUI 无法显示连接状态，也无法显示依赖 `ready session` 的截帧按钮。**

### 七、后续调查最值得优先做的方向

#### 方向 A：直接钉 `LYSK` 是否执行到了 `PlayCover.launch()`

优先级最高。

因为当前最大的断点是：

- `PlayTools.framework` 已加载
- 但没有 `LYSK` 对应的 runtime diagnostics 目录
- 也没有注册到 `52741`

所以最值得先确认的是：

> **`LYSK` 当前这次到底有没有执行到 `PlayCover.launch()`。**

可以围绕以下线索继续看：

- `PlayTools` 注入入口是否真的被调用
- `PlayCover.launch()` 是否被调用
- `BridgeListener.shared.start(bundleId:)` 是否被执行
- `RuntimeLaunchDiagnostics.record(...)` 是否能正常写盘

#### 方向 B：确认 `LYSK` 对应的 bundleId / diagnostics 路径是否与预期一致

虽然当前运行进程路径显示 app 是：

- `com.papegames.lysk.app/Unity-iPhone`

但仍建议继续确认：

- 运行时 `Bundle.main.bundleIdentifier` 是否真的是 `com.papegames.lysk`
- 是否存在 bundleId 为空、fallback 到 `playtools.runtime.<pid>` 的情况
- 诊断目录是否可能写到了意料之外的 bundle 目录下

#### 方向 C：如果能复现一次 fresh launch，优先抓新的 runtime diagnostics 与端口行为

建议新的 agent 在下一轮调查时，尽量围绕“fresh launch + 立刻采集”组织证据：

- 先确认 `PlayCover` GUI 与 `LYSK` 旧进程都彻底退出
- 重新从 GUI 启动 `LYSK`
- 立即检查：
  - `52741` 是否出现来自 `LYSK` 的连接
  - `RuntimeLaunchDiagnostics` 是否新建 `com.papegames.lysk` 目录
  - 是否出现 `bridge_registration_attempt_started`
  - 是否出现 `bridge_registration_established`

如果 fresh launch 后这些仍缺失，就可以把问题进一步收敛到：

- `LYSK` 的 PlayTools 入口未执行
- 或 `LYSK` 特定运行路径绕过了 `PlayCover.launch()` / `BridgeListener.start()`
