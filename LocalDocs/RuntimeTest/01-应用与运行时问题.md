# 应用与运行时问题

## RT01：`preview_entitlements` 对两款 app 都失败

### 现象

对以下两个 bundle 调用 `preview_entitlements` 都失败：

- `com.tencent.tmgp.speedmobile`
- `com.miHoYo.Yuanshen`

### 影响

- 无法通过 MCP 读取 app 当前 entitlement 摘要
- 无法验证后续签名、PlayTools 注入、系统框架开关等操作前后的 entitlement 变化

### 预期

工具应返回结构化的 entitlement 概览（sandbox、network、camera、microphone 等能力摘要）。

### 实际

工具直接失败，错误表现为 **entitlements 格式不正确 / 无法解析**。

### 初步判断

可能有两类问题：

1. app 内确实没有可解析的 entitlements
2. 解析逻辑对当前 entitlements 文件格式兼容性不足

### 建议排查

1. 先对比 `validate_app_signing` 的原始检查逻辑与 `preview_entitlements` 的输入来源是否一致
2. 核对读取到的 entitlements 原始数据格式
3. 明确“无 entitlements”和“entitlements 格式错误”两种情形的报错边界

### 2026-03-30 live 回归补充

- 在真实 `原神`（`com.miHoYo.Yuanshen`）上重新调用后，`preview_entitlements` 仍直接失败
- 实际错误：`Failed to dump entitlements: 未能读取数据，因为它的格式不正确。`
- 2026-03-30 晚间 fresh live 复测再次得到同样结果，说明 RT01 在 live 环境下**仍未关闭**，而且当前仍不是“空结果/无 entitlements”的稳定语义

### 2026-03-30 最终结论

> **已定位并修复。**

- 根因是 entitlements dump 链路直接把 `codesign` 的混合输出送入 plist 解析，真实 app 上会因为前缀噪声导致“格式不正确”
- 修复 `MCPShell.dumpEntitlements(...)` 的 stdout/stderr 捕获与嵌入 plist 提取后，真实 `原神` 上已成功返回结构化摘要
- 最新 live 结果：`preview_entitlements` 返回 `Entitlements preview for 原神 (com.miHoYo.Yuanshen): 18 key(s).`
- 因此 RT01 已关闭

## RT02：`validate_app_signing` 显示已签名，但 `entitlementsPresent=false`

### 现象

`QQ飞车` 与 `原神` 在 `validate_app_signing` 上都表现为：

- `signed = true`
- `entitlementsPresent = false`

### 影响

- `validate_app_signing` 的诊断结果与使用者直觉不一致
- 会让人难以判断：到底是 app 本身真的没有 entitlements，还是检测逻辑漏判
- 与 RT01 结合后，会进一步放大 entitlement 诊断链路的不确定性

### 预期

如果 app 已签名且 entitlement 存在，应能稳定识别为 `entitlementsPresent=true`；
如果确实不存在，也应与 `preview_entitlements` 的行为保持一致、可解释。

### 实际

两款 app 都显示已签名，但 entitlement 不存在；与此同时 `preview_entitlements` 又不是“空结果”，而是直接失败。

### 初步判断

- 可能是 `validate_app_signing` 的 entitlement 检测标准过窄
- 也可能是当前 app 签名确实不带 entitlements，而 `preview_entitlements` 没有优雅处理“缺失”场景

### 建议排查

1. 明确 `signed`、`Info.plist in signature`、`entitlementsPresent` 三者的判定来源
2. 为“无 entitlements”返回稳定、可读的状态，而不是让上层只能推测
3. 与 RT01 联动修复，保证两个工具的输出语义一致

## RT03：`create_session` 在两款 app 上都超时，且 `timeout` 参数疑似未生效

> **2026-03-30 最新结论：已定位并修复。**
>
> - `timeout` 参数问题来自 `SessionTools.swift` 只按 `Double` 读取，整型输入会回退到默认 `10.0`
> - 真实 app 一直不注册的根因不是 host listener，而是 **live 使用的 `PlayTools.framework` 仍是旧预编译产物**
> - 进一步定位发现：`PlayTools.xcodeproj` 之前没有把 `BridgeListener.swift` / `MetalCaptureService.swift` 纳入 `PlayTools` target；与此同时，GUI 构建只会复制 `Carthage/Build/PlayTools.xcframework/ios-arm64/PlayTools.framework`
> - 修复 `timeout` 解析、补齐 `PlayTools.xcodeproj` target membership、重建替换 `Carthage/Build` 预编译 framework 并重装 GUI 后，原神 live 已验证：`list_sessions` 返回 ready session，`create_session` 成功返回 `runtimePort=60054`，进程侧可见 `127.0.0.1:* -> 127.0.0.1:52741` 的注册连接

### 现象

已成功 `launch_app` 后，对以下两个 bundle 调用 `create_session` 都超时：

- `com.tencent.tmgp.speedmobile`
- `com.miHoYo.Yuanshen`

测试时显式传入过 `timeout: 20`，但错误信息仍体现为 **10 秒超时**。

### 影响

- runtime session 无法建立
- 后续 `tap`、`long_press`、`swipe`、`drag`、`press_key`、`type_text`、`toggle_debug_overlay` 等“人工/手动”能力无法继续实测
- 当前 GUI 自动化的关键价值链路被整体阻断

### 预期

1. 已启动 app 且满足前置条件时，可在设定超时时间内成功拿到 session
2. 如果失败，错误信息应准确反映实际使用的 timeout 参数

### 实际

1. 两款 app 都未等到 runtime 注册
2. 传入的 `timeout=20` 疑似未被使用
3. 错误文案看起来仍是写死的 `10s`

### 初步判断

更像是 **全局 runtime 注册链路问题**，而不是某个 app 特例。

### 建议排查

1. 检查 `create_session` 是否真的读取并传递了调用方的 timeout 参数
2. 检查 runtime 注册事件是否根本没到达 host
3. 检查 PlayTools 注入状态、session registry、app 启动时机之间是否存在竞态
4. 让错误文案输出“实际生效的 timeout 值”而不是固定文案

## RT04：`delete_keymap` 返回成功后，`list_keymaps` 立即回读仍能看到旧项

### 现象

对 `QQ飞车` 进行如下操作：

1. 创建临时 keymap
2. 重命名临时 keymap
3. `delete_keymap` 删除该 keymap
4. 立即再次 `list_keymaps`

结果：`delete_keymap` 返回成功，但 `list_keymaps` 里仍能看到刚删除的 keymap。

### 影响

- keymap 管理结果不具备立即一致性
- 上层 GUI / 自动化调用方难以判断删除是否真正成功
- 容易引发重复删除、误判失败、或 UI 列表残留

### 预期

删除成功后，立即回读 `list_keymaps` 应不再返回该项。

### 实际

接口返回“成功”，但结果列表短时间内仍残留旧项。

### 补充观察

后续直接查看 keymap 目录时，临时文件已不存在，因此更像是：

- 内存缓存未刷新
- 列表来源与文件系统状态不同步
- 或通知 / 刷新链路有延迟

### 建议排查

1. `delete_keymap` 成功后是否同步清理内存缓存
2. `list_keymaps` 读取的是缓存还是磁盘
3. `mcpKeymapsChanged` 通知是否触发、是否有消费方刷新列表
4. 是否需要在删除完成后主动刷新一次 keymap 索引

### 2026-03-30 live 回归补充

在真实 `原神` 上也复现到了同类一致性问题：

1. `create_keymap(rt08-temp-2)` 成功
2. `rename_keymap(rt08-temp-2 -> rt08-renamed-2)` 返回成功
3. **首次** `list_keymaps` 仍返回旧名 `rt08-temp-2`
4. 但此时 `get_keymap(rt08-temp-2)` 已报 `Keymap not found`，`get_keymap(rt08-renamed-2)` 可成功读取，说明真实存储状态已经切到新名
5. 再次 `list_keymaps` 后，列表才恢复为 `rt08-renamed-2`
6. 随后 `delete_keymap(rt08-renamed-2)` 返回成功，但**首次** `list_keymaps` 仍能看到已删项；再次回读后列表才恢复正确，且 `get_keymap(rt08-renamed-2)` 已报 not found

这说明 RT04 在 live 环境中**仍未完全修复**；问题不只是删除链路，rename 后的首次列表回读也存在同类滞后。

### 2026-03-30 最终结论

> **已定位并修复。**

- `KeymapService.listKeymaps(...)` 已补上 config 与磁盘文件的 reconciliation，keymap plist / config 写入也改成原子写入
- `rename_keymap` / `delete_keymap` / `reset_keymap` 后会补发 `.mcpKeymapsChanged`，GUI `KeymapViewVM` 也已监听并刷新缓存
- 在重装最新 GUI 后，对真实 `原神` 完整执行：
  1. `create_keymap(rt-live-20260330-2242)`
  2. `rename_keymap(... -> rt-live-20260330-2242-renamed)`
  3. 首次 `list_keymaps` 直接返回新名
  4. `get_keymap(旧名)` 直接 `Keymap not found`，`get_keymap(新名)` 成功
  5. `delete_keymap(rt-live-20260330-2242-renamed)` 后，首次 `list_keymaps` 已不再返回该项
  6. `get_keymap(已删名)` 直接 `Keymap not found`
- 因此 RT04 已关闭
