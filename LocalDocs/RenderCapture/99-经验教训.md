## 三、PlayTools 修改

### 3.1 PlaySettings.swift 直接纳入 git 管理

- `Carthage/Checkouts/PlayTools/` 整体被 `.gitignore` 忽略，但 `PlaySettings.swift` 通过 `!` 例外规则纳入了 git 版本控制
- `.gitignore` 中使用逐级"打洞"方式实现精确例外：
  ```
  /Carthage/*
  !/Carthage/Checkouts/
  /Carthage/Checkouts/*
  !/Carthage/Checkouts/PlayTools/
  ...
  !/Carthage/Checkouts/PlayTools/PlayTools/PlaySettings.swift
  ```
- **前提**：构建时始终使用 `FASTLANE=1` 跳过 Carthage Bootstrap，这样不会重新 checkout 覆盖本地修改
- 如果未来有人误执行了不带 `FASTLANE=1` 的构建导致文件被 checkout 覆盖，git 会检测到 modified，用 `git checkout -- Carthage/Checkouts/PlayTools/PlayTools/PlaySettings.swift` 即可恢复

### 3.2 旧 Patch 机制（已废弃）

- 之前尝试过 `Patches/playtools-*.patch` + `apply_playtools_patches.sh` 的方案
- **废弃原因**：
  - `FASTLANE=1` 跳过 Carthage Bootstrap 时，patch apply 脚本也一起被跳过，形同虚设
  - 不加 `FASTLANE=1` 时，Carthage Bootstrap 虽然会触发 patch apply，但 SwiftLint 缺失导致 PlayTools framework 构建失败
  - 直接纳入 git 管理更简单、可靠
- Patch 文件和 apply 脚本已从仓库删除，build phase 中的 patch 调用也已移除

### 3.3 修改 PlayTools 的工作流程（更新后）

1. 确认 `Carthage/Checkouts/PlayTools/` 目录存在
2. 直接编辑文件（如 `PlaySettings.swift`）
3. 如果修改的文件已在 git 追踪中 → 直接 `git add` + `git commit`
4. 如果修改了新文件 → 在 `.gitignore` 中添加对应的 `!` 例外规则（参照 `PlaySettings.swift` 的逐级打洞模式），然后 `git add` + `git commit`
5. **注意**：Host 端和 PlayTools 端的 `AppSettingsData` 需保持同步

## 四、构建环境

### 4.1 PlayCover GUI scheme 的完整构建命令

```bash
xcodebuild -project PlayCover.xcodeproj -scheme PlayCover -configuration Release build \
  CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES \
  FASTLANE=1
```

| 参数 | 作用 |
|------|------|
| `CODE_SIGN_IDENTITY="-"` | ad-hoc 签名 |
| `CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES` | 跳过严格签名检查 |
| `FASTLANE=1` | 跳过 Carthage Bootstrap 和 SwiftLint build phase |

### 4.2 FASTLANE=1 跳过 Carthage Bootstrap 和 SwiftLint

- PlayCover.xcodeproj 中有两个 build phase 脚本被 `if [[ -z "$FASTLANE" ]]` 包裹：**Carthage Bootstrap** 和 **SwiftLint**
- 设置 `FASTLANE=1` 环境变量可以同时跳过这两个步骤
- 跳过 Carthage Bootstrap 后，构建会使用 `Carthage/Checkouts/` 中已有的源码，不会重新 checkout 覆盖修改
- `PlaySettings.swift` 等有自定义修改的文件已直接纳入 git 管理（见 3.1），`FASTLANE=1` 保证它们不被覆盖
- **注意**：跳过 Carthage Bootstrap 的前提是 `Carthage/Checkouts/` 目录已存在且内容完整。首次 clone 仓库后需先运行一次 `carthage checkout`
- 此技巧来自 `LocalDocs/MCPWithGUITask/99-经验教训.md` G02 条目

### 4.3 Codesign sparkle 脚本的 "Sign to Run Locally" 坑

- 使用 `CODE_SIGN_IDENTITY="-"` 进行 ad-hoc 签名时，Xcode 会将 `EXPANDED_CODE_SIGN_IDENTITY_NAME` 设置为 `"Sign to Run Locally"`（而非 `"-"` 或空字符串）
- Codesign sparkle build phase 脚本中的 fallback 逻辑需要将 `"Sign to Run Locally"` 也作为 ad-hoc 的判定条件，否则 `codesign --sign "Sign to Run Locally"` 会因找不到 identity 而失败
- 已修复：在判断条件中增加了 `|| [ "$IDENTITY" = "Sign to Run Locally" ]`

## 五、Bridge 通信

### 5.1 新增命令不需要修改 BridgeMessageType

- Bridge 协议使用通用的 `command` / `commandResponse` 消息类型，命令类型靠 `CommandPayload.command` 字符串区分
- 新增命令（如 `capture_frame`）只需在 `BridgeListener.handleCommand()` 的 switch 中加 case，不需要修改 `BridgeMessageType` 枚举
- 在 `BridgeProtocol.swift` 中通过 `BridgeCommandName` 枚举统一管理命令字符串常量，确保 Host 和 Runtime 两侧使用同一值

### 5.2 BridgeListener.swift 需要纳入 git 管理

- `BridgeListener.swift` 位于 `Carthage/Checkouts/PlayTools/PlayTools/Controls/Backend/Bridge/` 下
- 需要在 `.gitignore` 中逐级打洞，从 `Controls/` → `Backend/` → `Bridge/` → `BridgeListener.swift`
- 目录级别的 `!` 例外规则必须逐级添加，不能跳级（如 `!.../Controls/Backend/Bridge/BridgeListener.swift` 不生效，除非 `Controls/`、`Backend/`、`Bridge/` 每一级都先被排除再被例外）

### 5.3 截帧命令的线程模型

- `capture_frame` 命令同步调用 `MetalCaptureService.shared.captureFrame()`
- `MetalCaptureService` 内部使用 `DispatchQueue.main.asyncAfter` 延迟 0.1 秒后自动停止截帧
- BridgeListener 不需要做额外的异步等待或线程切换——command 返回 "Capture started" 即可，实际截帧在后台完成

1. 从 `LocalDocs/MCP/08-经验教训与常见陷阱.md` 继承的关键原则：
