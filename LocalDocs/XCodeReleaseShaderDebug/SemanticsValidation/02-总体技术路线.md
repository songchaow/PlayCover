## 总体技术路线

## 目标

在不打乱当前 offline-first 工作流的前提下，为“语义验证”新增一条分层、渐进、可止损的测试体系。

核心思想：

- **不追求一步到位**
- **先建立离线证据，再逐步增加行为与真实场景证据**
- **最终做到哪一层，由当时的人力余量决定**

## 四层模型

### L1：IR Round-trip 结构验证

目标：建立最小闭环：

```text
IR -> MSL -> AIR -> IR
```

回答的问题：

- 当前链路能不能把 `module.ll` round-trip 回 `regenerated.ll`
- 哪些样本在 round-trip 的编译阶段就失败
- 哪些样本可以继续进入结构比较

这是本专项最优先、最基础的一层。

### L2：Canonical Compare + 风险分级

目标：不再只看文本 diff，而是比较：

- entry 函数集合
- shader 类型
- 参数/返回类型摘要
- 地址空间
- builtin / resource 使用
- CFG 粗结构
- instruction family 统计
- 关键 attribute / fast-math 语义点

输出不应只是“same/diff”，而应分级：

- **L0**：几乎一致 / 低风险
- **L1**：存在非关键差异 / 可接受
- **L2**：存在需要进一步复核或升级验证的差异
- **L3**：关键语义面明显不一致

### L3：最小行为测试

目标：在少量高价值样本上建立“固定输入 → 固定输出”的自动验证。

推进顺序：

1. **compute-first**：最容易自动化
2. **必要时补离屏 render**：覆盖 vertex/fragment 的关键路径

这一层的意义是：

- 把“结构相近”推进到“行为更可信”
- 对历史高风险 lowering 模式形成回归样本

### L4：真实场景验证

目标：在真实 shader / 真实 capture / 真实 app 上做最终后置验证。

这一层默认只在下面任一情况启用：

- L1/L2/L3 已基本收敛，需要真实确认
- 某类问题只有 `.gputrace` / live 渲染结构才能暴露
- 新修复影响 runtime/library replacement 主链路

默认使用自动化脚本 / MCP；若必须人工介入，需先取得用户确认。

### 阶段 P2：把结构比较从“文本 diff”升级为“风险分级”

交付目标：

- 新增 IR canonical summary
- 对 round-trip 结果做风险分类
- 在 `test-data/` 形成首批基线
- 挑少量 `ShaderCorpus` 样本试跑

当前状态：

- `SV-002`：**已完成**
- `SV-003`：**TODO（当前主线）**

这意味着当前阶段的 active work 已经不是“继续发明 compare 指标”，而是把现有能力收口成更稳定的默认工作流：

- 把 `--preset test-data-representatives` 继续维护成**跨机器硬默认 gate**；fresh workspace 只要能跑通这条链，就说明当前离线控制面仍可由 agent 自主完成
- 把 `--preset daily-default` 理解为**脚本层的一键日常入口**，但在控制面上仍只应把它视为“本机已有样本时的增强入口”；`--preset local-corpus-representatives` 则保持为更窄的本地观察入口。三者都不应把缺样本时的 fresh capture / 用户协助写回默认流程；对应 `gate profile` 需要区分 `minimumExpectedJobCount`（硬下界）与 `expectedJobCount`（完整代表集）
- 用 `gate-summary.json` / `--gate-profile` / `--enforce-gate` 稳定表达“已知 debt vs 新增回归”的边界
- 用 `preset-manifest.json`、`--baseline-report`、`--save-baseline` 把代表集、baseline 与报告落点一起固化成可维护契约；固定输出目录在重复执行时也应继续通过 manifest 稳定暴露当前 active baseline 摘要，而不只是在本次显式保存时体现；当前 manifest 还应直接写出 preset 期望代表集与 discovered jobs 的 `expected / matched / missing / unexpected` 摘要，便于区分“本机缺样本”与“代表集边界真的变化”；runner 内部的内建代表样本与 known-debt 元数据也应保持单一来源，让 `preset` / `gate profile` / manifest 期望边界从同一份定义推导
- 用纯逻辑单测持续保护这份契约，至少覆盖 `build_compare_result`、`build_preset_manifest`、`sample_identity`、known-debt improvement、job-count 上下界，以及代表集定义到 `preset / gate / manifest` 的同步关系，避免代表集 / gate profile 语义在后续维护中静默漂移
- 明确 `test-data-batch` 只承担参考批量基线角色，默认不附带日常 gate profile，不应把它误当成每次都要执行的阻断入口
- 继续让 L2 报告真正变成后续 `SV-006 / SV-004` 的分流器
- 当前 `test-data-representatives` 的最新收敛结果是：`8/8` 样本都能完成 round-trip，`test_struct_array_field` 已从 compile failure 收敛为已知 blocked debt；对应 gate 合同也应同步从 allowed failure 切换为 allowed blocked sample，使 `--enforce-gate` 继续稳定返回 `WARN`

对应：`SV-002`、`SV-003`

## 预算与止损策略

### 人力余量较低时

优先做到：

- **L1 完整落地**
- **L2 第一版 summary compare**
- **`SV-003` 的 `test-data-representatives` 硬默认 gate 固化**

此时已经能显著提高“语义风险可见度”，也是当前最现实、最高性价比的停点。额外约束是：默认 gate 必须仍可由 agent 自主完成，不能把用户配合、fresh capture 或权限交互带回主路径。

### 人力余量中等时

继续做到：

- 代表性 `ShaderCorpus` 作为**已有本地条件下的增强证据**接入
- 建立明确的升级/止损规则（`SV-006`）
- 从稳定代表集里挑少量样本建立最小 compute 行为测试

这是推荐的“中期完整度”目标。

### 人力余量充足时

再补：

- 更丰富的行为样本
- 离屏 render 行为测试
- 真实场景自动化验证
- 必要时更深一层的 canonical compare / AST compare / ISA 验证

## 与现有工作流的关系

现有主回路仍然是“真实样本采集 → 导出 corpus → 离线 replay / compile / diff → 少量 live 复测”。

本专项新增的是一条**更早暴露语义风险的离线验证支路**：`module.ll → round-trip → canonical compare → risk grading → （必要时）behavior test → （必要时）real-scene validation`。

它不是替代现有 E-005/E-006，而是在更低成本、更自动化的阶段提前暴露风险。

补充约束：

- 若前置任务仍在处理更靠前的运行时 blocker，这里应优先提供更强的离线证据，而不是过早把默认流程切到 live
- `SV-003` 默认只复用本地已有 `test-data/` 与 `ShaderCorpus`；若缺样本，不应自动升级为需要用户介入的 fresh capture 流程

## 当前推荐的默认 gate

### 必须优先满足

当改动涉及离线语义验证脚本、preset / gate profile / report contract 或 `IRToMSLConverter` 时，默认优先满足：

- `Scripts/test_ir_canonical_compare.py`、`Scripts/test_ir_semantics_roundtrip_runner.py` 保持通过
- `SV-001` 的 round-trip 能稳定跑 `--preset test-data-representatives --allow-failures --enforce-gate`
- `SV-002` 能对代表 preset 生成结构化 compare 报告
- 代表 preset 能继续产出 `gate-summary.json`，并在 `--enforce-gate` 下仅对新增回归执行阻断
- `daily-default` / `local-corpus-representatives` 需要把 job count 的**硬下界**与**完整代表集**分开表达：缺少部分本地 `ShaderCorpus` 样本时记为 `WARN`，不得直接误判为回归
- 固定输出目录下的代表 preset 会继续产出 `preset-manifest.json`；若目录里已有 `baseline.json`，可自动复用它做 replay baseline diff；manifest 还应显式标出 preset 期望代表集与本次 discovered jobs 的命中 / 缺失 / 意外新增情况
- `test-data-batch` 仍只作为参考批量入口：默认不附带 gate profile，也不应承担日常阻断职责
- 若改动触及 `IRToMSLConverter`，应补一次 `FORCE_PLAYTOOLS_REBUILD=1 ./BuildScripts/sync_playtools_xcframework.sh`

推荐默认顺序：

1. **跨机器硬默认**：先保持 `Scripts/test_ir_canonical_compare.py`、`Scripts/test_ir_semantics_roundtrip_runner.py` 通过，再执行 `python3 Scripts/ir_semantics_roundtrip_runner.py --preset test-data-representatives --allow-failures --enforce-gate`
2. **本机已有 `ShaderCorpus` 样本时的一键增强入口**：`python3 Scripts/ir_semantics_roundtrip_runner.py --preset daily-default --allow-failures --enforce-gate`
3. **参考批量入口**：`python3 Scripts/ir_semantics_roundtrip_runner.py --preset test-data-batch --allow-failures`

固定输出目录优先使用：

- `build/semantics-validation/roundtrip/test-data-representatives/`
- `build/semantics-validation/roundtrip/test-data-batch/`
- `build/semantics-validation/roundtrip/local-corpus-representatives/`
- `build/semantics-validation/roundtrip/daily-default/`

### 可以作为第二阶段 gate

- `python3 Scripts/ir_semantics_roundtrip_runner.py --preset local-corpus-representatives --allow-failures`
- 最小 compute 行为测试通过
- 必要时使用 `./BuildScripts/build_and_install.sh` 进行运行时链路验证；默认保持脚本自带的 `user` 安装模式，不主动切到可能触发 `sudo` 的 `auto/system`

### 不应作为默认日常 gate

- 需要用户反复介入的 live 流程
- 高成本 GUI 操作
- 手动打开 Xcode 的视觉确认
- 工作区外分析
- 因缺少现成样本就要求用户协助准备环境


### 报告建议

默认仍以结构化 JSON 报告为主；具体字段详见 `03-L1-IR-RoundTrip.md`、`04-L2-CanonicalCompareAndRiskGrading.md`、`05-L3-最小行为测试.md` 与 `06-L4-真实场景验证.md`。

当前控制面只要求按层稳定产出：

- L1/L2：`replay-summary.json`、`compile-summary.json`、`roundtrip-summary.json`、`compare-summary.json`、`risk-report.json`、`gate-summary.json`、`preset-manifest.json`
- L3：`behavior-summary.json`
- L4：`live-summary.json`、`gputrace-summary.json`、`render-diff-summary.json`、`diagnostics-summary.json`

### 样本建议

- `test-data/`：最小模式覆盖，也是跨机器硬默认入口的主要来源
- `ShaderCorpus/`：真实样本代表集，但只作为本机已有条件下的增强证据
- 本目录后续若需新增专门样本选择策略，可另开子文档维护
- 首轮基线与历史细节下沉到 `07-首轮基线与历史进展归档.md`（历史参考，**不必须读取**）

## 当前结论

当前最优技术路线不是直接冲向 L4，而是：

1. **先把 L1/L2 的既有能力收口成稳定日常 gate（`SV-003`）**
2. **把升级/止损规则写清楚（`SV-006`）**
3. **再按预算决定是否推进 L3/L4**

这条路线最符合当前仓库的工具现状，也最能保证 agent 自主推进时对用户依赖最低。
