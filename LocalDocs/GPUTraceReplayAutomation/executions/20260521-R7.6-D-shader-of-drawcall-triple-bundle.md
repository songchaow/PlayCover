## 3. 设计决策

### 3.1 `with_uniforms` 隐含 `with_bindings`

`uniforms[]` 的每个元素需要知道 `(rps_key, bind_slot, buffer_key, offset)`。前两个来自 frame-list 的 `draw_to_rps_map`，后两个来自 R7.6-A 的 `bindings.<stage>.buffers[i].{resource_id, offset}`。绕过 bindings 拿不到 buffer_key/offset，所以 `with_uniforms=True` 自动开启 `with_bindings`。

### 3.2 单次 `frame-list` 调用承载两份数据

R7.6-C 旧实现已在 `shader_of_drawcall()` 内部跑 `frame_list(with_draws=True, with_timing=False)`，但 `with_bindings` 默认为 True 而 R7.6-C 调用方没显式传——这意味着 wrapper 已经付了 binding 捕获的钱却扔掉了输出。R7.6-D 不增加新的子进程调用，而是把现有 `frame_list` 调用的 `bindings` 字段从 `command_buffers[].encoders[].draws[]` 树里读出来，在已有的 rps_label 寻路循环里同时回收 — O(1) 增量代价。

调用方不开 `with_bindings` 时仍按 R7.6-C 老路径走（默认 `frame_list(with_bindings=False)`），输出体积保持 ~105KB。

### 3.3 内部 helper `_dump_uniforms_for_resolved()`：避免重复跑 frame-list

公共 API `dump_uniforms()` 在 `target_kind="draw"` 模式下会自己跑一次 `frame-list --with-bindings` 解析 `(rps_key, buffer_key, offset)`。但在 `shader_of_drawcall` 上下文里，调用方刚跑过一次 frame-list，所有解析信息都在手；如果对每个 buffer slot 都调 `dump_uniforms(target_kind="draw")`，会重复跑 N 次 frame-list（N=fragment buffer 数量，LYSK draw 0 = 4，每次 1.7s × 4 ≈ 6.8s 浪费）。

新增 `_dump_uniforms_for_resolved()` helper 直接构造 bridge args（target=rps_key, --buffer-key, --offset 都已知），跳过 wrapper 层 frame-list 调用。LYSK draw 0 fragment 4 个 slot 实测耗时从理论 ~6.8s → 实际 ~1.7s（一次 frame-list + 4 次 ~50ms 的 bridge dump-uniforms），与 R7.6-D 设计承诺的"零额外开销"一致。

### 3.4 Per-slot 软错误隔离

某些 buffer slot 可能解码失败：bridge `dump-uniforms` 返回 exit 11 + `error="reflection_not_captured"` / `binding_not_a_buffer` / `offset_out_of_range` 等结构化错误。`_run()` 已有 exit 11/12 graceful 路径（保留 stdout JSON），所以这些软错误自然落到 `DumpUniformsResult.error` 字段，不阻塞链路。
- 顶层 `result.error` 仍然只反映 `shader-of-rps` 半边的错误（`rps_not_found` / `descriptor_not_captured` 等），与 R7.6-C 行为一致。
- `uniforms_summary.slot_failed` 让消费方一眼看到 per-slot 健康度。
- 极少见的 bridge 硬故障（exit 4–10）通过 try/except `BridgeError` 捕获，落一个伪 `DumpUniformsResult` 标 `error="bridge_error_exit_N"`。

### 3.5 `bindings` 字段在 CLI payload 中的形态

`FrameDrawBindings` dataclass 通过手写 `_bg()` 转成 dict（保留 `inline_bytes_size` 仅在 inline 形态出现，其余字段过滤 `None`），与 frame-list 子命令的 JSON 输出形态一致。这让消费方对 `shader-of-drawcall --with-bindings` 的输出可以与同一 trace 的 `frame-list` 输出做字面比较。T7s-2 测试断言 `fragment.buffers` 数量与 `frame-list` 同 draw 一致。

## 5. 不变量与已知局限

### 5.1 不变量（R7.6-D 维持）

- 默认（无 flag）调用产物与 R7.6-C 完全相同（T7s-1）。
- `--with-bindings` 不改变 `shader_of_rps` 嵌入字段（同一 RPS 的 metallib/AIR/cacheKey 字节级一致；T7q-3 chain 兼容性测试覆盖）。
- 各 stage 独立：`--stage vertex` 取 `bindings.vertex.buffers`；`--stage fragment` 取 `bindings.fragment.buffers`。
- compute-only trace 上 OOR 行为不变（exit 12 + `draw_index_out_of_range`）。

### 5.2 已知局限

- inline-bytes 形态的 buffer slot（`setVertexBytes:length:atIndex:`）没有 `resource_id`；当前 R7.6-D 仍调 `dump-uniforms`（`buffer_key=None` 时不传 `--buffer-key`），bridge 仅返回 layout，`decoded` 缺失（`error` 字段会有结构化标记如 `binding_not_a_buffer`）。LYSK 实测 inline_count=0，未触发；改进留给后续 chunk（如果实际需要）。
- `uniforms[]` 不包含 sampler / texture 的反射；仅 buffer 类绑定走解码。这与 `dump-uniforms` 子命令的设计边界一致。
- `--output-dir` 同时被 `shader-of-rps` 与 `dump-uniforms` 共用；同一 draw 的多个 slot 解码不会互相覆盖文件（bridge 内部用 rps_key+slot 命名），但跨多次调用如复用同一目录需注意。
- 性能：LYSK draw 0 三件套 ≈ 1.9s（一次 frame-list ~1.6s + 一次 shader-of-rps ~0.2s + 4 次 dump-uniforms ~50ms 各）。对单次调试不敏感；批量循环仍建议用 `frame-list` 一次性 + per-draw `dump-uniforms` 直调（playbook 决策表已注明）。
