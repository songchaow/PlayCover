## QQ飞车：RC-001-B live 样本（2026-03-31）

### 一、测试对象

- **app**：`QQ飞车`
- **bundleId**：`com.tencent.tmgp.speedmobile`
- **设置前提**：`metalCaptureEnabled=true`

### 二、样本 A：重建 PlayCover GUI 但未重建 PlayTools 预构建产物

执行结果：

- `launch_app`：成功
- `create_session`：`ready`
- `get_capture_status`：仍只返回 4 个旧字段
- `capture_metal_frame`：失败，错误为 `GPU trace document not supported`
- 目标输出路径下未生成 `.gputrace`

关键信息：

- `QQ飞车` 二进制实际加载的是：
  - `~/Library/Frameworks/PlayTools.framework/PlayTools`
- 当时 app 内 `AKInterface.bundle` 的哈希与 GUI 内置版本不一致
- `check_playtools_installed == true`，但这只能说明“有注入”，不能说明“注入的是最新 runtime”

### 三、关键发现

这轮 live 复测证明：

> **`Carthage/Checkouts/PlayTools` 中的源码改动，并不会自动进入 GUI 打包产物；`PlayCover.app` 实际拷贝的是 `Carthage/Build/PlayTools.xcframework/ios-arm64/PlayTools.framework` 这个预构建 framework。**

因此，之前看到的“源码已有新诊断字段，但真实 app 还是旧 4 字段返回”，并不是逻辑矛盾，而是**构建产物陈旧**。

### 四、阻塞点修复

本轮已完成：

1. 修复 `Carthage/Checkouts/PlayTools/PlayTools/MetalCaptureService.swift` 中会阻塞源码重建的字符串转义错误
2. 从源码重建 `PlayTools.framework`
3. 用新构建产物回写 `Carthage/Build/PlayTools.xcframework/ios-arm64/PlayTools.framework`
4. 重装 `PlayCover.app`
5. 重新为 `QQ飞车` 执行 remove/inject PlayTools，使 app 内 `AKInterface.bundle` 与 GUI 内置版本一致

### 五、样本 B：真正切到新 PlayTools runtime 后

执行结果：

- `launch_app`：成功
- `create_session`：`ready`
- 第一次 `get_capture_status`：**超时**（`Bridge operation timed out: Receive timed out`）
- 之后 `list_sessions` 显示该 session 进入：`disconnected`
- 最新 crash 报告：`speedmobile-2026-03-31-114113.ips`

补充说明：

- 在一次误操作中，曾复用旧进程导致 session 未重新注册；在手动 kill 旧 PID 并真正 fresh launch 后，新 runtime 能正常注册为 `ready`
- 因此，当前新的主问题不再是“旧产物没生效”，而是：
  - **新 runtime 在真实 app 上执行 `get_capture_status` 时会超时，并最终导致 session 断开 / app 崩溃**

### 六、当前结论

`RC-001-B` 已完成，得到两条高价值结论：

1. **旧 4 字段 live 样本来自陈旧的 `PlayTools.xcframework` 预构建产物，而不是最新源码逻辑**
2. **在真正加载最新 runtime 后，阻塞点前移为 `get_capture_status` 超时 + session `disconnected` + app crash**

因此，下一步应切换到更小的子任务：

> **`RC-001-C`：在真正加载最新 PlayTools runtime 的前提下，定位 `get_capture_status` 为什么会在真实 app 上超时并导致 session 断开。**
