## 2. 关键设计决策

### 2.1 为什么 wrapper-only

bridge 的 `frame-list` 与 `shader-of-rps` 都需要完整 `playAll`，整套链路两次 replay 不可避免（`frame-list` 装 swizzle、`shader-of-rps` 在 ObjectMap 上工作）。在 ObjC 端写一个新子命令可以省掉一次 Python 出入栈，但代价是：

- 需要在 bridge 内**复刻** R7.3 的 swizzle 安装路径 + R7.4 的 cacheKey 算法 + llvm-dis 调用（实质是把两个子命令的实现合并成一个，~150 行胶水），代码冗余。
- 必须重构 bridge 内的全局表（`g_draws_captured` / `g_rps_captured`）让两条逻辑并存而不冲突，复杂度非零。
- 集成测试要新加 bridge 端测试 + wrapper 端测试，工作量翻倍。

wrapper-only 路径直接复用 `ReplayBridge.frame_list()` + `ReplayBridge.shader_of_rps()` 两个已经测试通过的 Python 入口，胶水代码只有 ~120 行（含异常路径），bridge 二进制零变更，集成测试增量完全可控。性能差异（多一次 Python 进程出入）对单次调试任务可忽略。

### 2.2 错误模型

把 OOR 与"软错误"显式区分，避免用户分不清"我打错了 draw_index"vs"swizzle/反查链路异常"两类问题：

| 输入 | 模块 API | CLI exit |
|---|---|---|
| `draw_index >= draw_count` (含 `draw_count==0`) | 抛 `DrawIndexOutOfRange(draw_index, draw_count, trace_path)` | 12 + 结构化 JSON `{"error":"draw_index_out_of_range",...,"hint":"..."}` |
| `draw_index < 0` | `ValueError` | 2（catch-all） |
| `stage` 非 fragment/vertex | `ValueError`（argparse 也会拒） | 2 |
| `draw_to_rps_map[idx].rps_key is None`（swizzle 在该 draw 上漏掉） | 返回 `result.error="draw_has_no_rps_key"` + `hint`，**不抛**（保留 frame-list 上下文） | 11 |
| 下游 `shader-of-rps` 软错误（`rps_not_found` / `no_air_bitcode` 等） | 透传到顶层 `result.error / result.hint` + 嵌入完整 `shader_of_rps` 结果 | 11 |
| bridge 子进程错误（exit 4–10） | `BridgeError` | 原码 |

`draw_count == 0`（compute-only trace）走与普通 OOR 同一分支，但 hint 文案专门定制为"trace has no render draws"，引导用户换工具或换 trace。

### 2.3 顶层 schema 选择

CLI 输出结构刻意把 frame-list 元信息放在顶层：

```json
{
  "command": "shader-of-drawcall",
  "trace_path": "...", "draw_index": 0, "stage": "fragment", "output_dir": "...",
  "encoder_index": 2, "draw_in_encoder": 0, "call_index": 144,
  "rps_key": 472, "rps_label": "Papegame/Cloth/ClothStandard",
  "shader_of_rps": { ... }   // 嵌入完整 R7.4 子命令结果
}
```

理由：`rps_label` 这类语义字段对用户最有用，但在 `frame-list` 输出里藏在 `command_buffers[].encoders[].draws[]` 三层下；wrapper 在内部遍历树补齐到顶层。`shader_of_rps` 整块嵌入而非展开，是为了让 R7.4 的字段（`ir_ll_path` / `library_metallib_size` / `cache_key_metallib` 等）保持原始命名空间，不污染顶层。

## 5. 风险与盲点

| 风险 | 评估 | 缓解 |
|---|---|---|
| llvm-dis `.ll` 输出含 ModuleID 路径注释 → 字节比较失败 | 已知 — 不是封装层 bug，是 llvm-dis 写 IR 头时把临时文件路径写进去的固定行为 | 文档 + cli-reference.md 明确说明；测试以"除 ModuleID 行外字节一致"为弱判据 |
| compute-only trace 上 R7.3 原 T7l 断言 14 项 fail | 是 R7.3 的 trace-shape 假设盲点，本任务不修 | 在执行文档 + SKILL.md 显式标注；放进 R7.5 的"compute encoder dispatch 计数"附带处理 |
| LYSK trace 仅 3/96 lib 有 AIR 导致 `--with-ir` 多数情况返回 `no_air_bitcode` | 是 R7.4 已知盲点，由 R7.7 通过 SDI module.bc 路径补足 | wrapper 端把 `ir_error` 透传到顶层 `error` 字段，CLI exit 11 通知用户软失败 |
| Python wrapper 比 ObjC bridge 慢 ~50ms（进程起步 + JSON 解析） | 单次调试任务可忽略；批量场景仍可直接用模块 API | 文档建议批量用模块 API |
| `shader-of-drawcall` 不在 bridge `help` 输出里（因为它是 wrapper-only 子命令） | 是设计选择 | wrapper `--help` 已包含；SKILL.md / cli-reference.md 同步说明此能力来自 wrapper |

## 6. 后续工作（R7.5 起步参考）

- **R7.5 子项 A — depth/stencil blit export**：bridge 内置最小 RPS / blit pass，把 `Depth32Float` → `R32Float`、`Stencil8` → `R8Unorm` 写到 raw 文件后 `getBytes` 落盘。需要在 bridge 内编译一对最小 MSL（vertex 通过 + fragment 采样 depth/stencil 写到 color），无需私有 API。
- **R7.5 子项 B — compute encoder dispatch 计数**：在 R7.3 swizzle 体系上加 `MTLComputeCommandEncoder.dispatchThreadgroups:*` / `dispatchThreadgroupsWithIndirectBuffer:*` 三变体的拦截，每个 compute encoder 的 `compute_dispatch_count` 字段从 R7.3 的 placeholder 变为实数。reference_test_inject.gputrace 的 R7.3 T7l 14 项 fail 一并由 R7.5 修复（断言改成"draw 类断言仅在有 render encoder 时启用"）。
- **可选 — `shader-of-drawcall` bridge ObjC 子命令**：本次确认了 wrapper-only 路径就足以满足"一行命令"目标，CLI 形态对称对用户认知没有显著增量价值。除非未来 R7.6 子项 A/B 引入需要 bridge 内联落地的强约束，否则不再做。
