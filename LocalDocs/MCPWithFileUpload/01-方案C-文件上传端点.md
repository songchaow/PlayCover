## 方案 C：文件上传端点

### 一、核心设计

在现有 HTTP transport 上新增一个 **`/upload`** 端点，接受文件上传，将文件存入一个会话级暂存目录，并返回可被其他 tool 引用的文件名。

### 二、端点定义

#### `POST /upload`

| 项目 | 说明 |
|---|---|
| 路径 | `/upload` |
| Content-Type | `application/octet-stream` |
| 必需 Header | `Mcp-Session-Id`、`X-Filename`（原始文件名） |
| 可选 Header | `X-Checksum-SHA256`（用于校验） |
| 请求体 | 原始文件二进制内容 |
| 成功响应 | `200 OK`，JSON body |
| body 限制 | 默认最大 500 MB（可配置） |

#### 为什么用 `application/octet-stream` 而不是 `multipart/form-data`

- Agent 场景下通常是程序化调用，`octet-stream` 更简单直接
- 避免引入 multipart 解析依赖
- 文件名通过 header 传递，不需要 form field

#### 成功响应

```json
{
  "filename": "game.ipa",
  "storedName": "a1b2c3d4-game.ipa",
  "size": 123456789,
  "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "expiresIn": 3600,
  "reference": "@a1b2c3d4-game.ipa"
}
```

| 字段 | 说明 |
|---|---|
| `filename` | 客户端提供的原始文件名 |
| `storedName` | 实际存储的文件名（加了唯一前缀，防冲突） |
| `size` | 文件大小（字节） |
| `sha256` | 文件 SHA256 校验和 |
| `expiresIn` | 文件存活时间（秒），到期后自动清理 |
| `reference` | 可直接传给其他 tool 的引用字符串 |

#### 错误响应

| HTTP 状态码 | 场景 |
|---|---|
| `400` | 缺少 `X-Filename` header 或文件名不合法 |
| `404` | session 不存在 |
| `413` | 文件超过大小限制 |
| `422` | SHA256 校验失败（如果提供了 `X-Checksum-SHA256`） |
| `500` | 磁盘写入失败 |

### 三、暂存目录

#### 位置

```text
~/Library/Containers/io.playcover.PlayCover/tmp/mcp-uploads/
```

选择这个位置的原因：
- 在 PlayCover 的 container 内，权限一致
- 与 `Applications/`、`Entitlements/` 等已有目录同级
- `tmp/` 子目录表明临时性质

#### 目录结构

```text
mcp-uploads/
├── <session-id>/
│   ├── a1b2c3d4-game.ipa
│   ├── b5c6d7e8-config.plist
│   └── ...
└── <another-session-id>/
    └── ...
```

每个 MCP HTTP session 有独立的子目录，隔离不同客户端的上传。

#### 文件名规则

```text
<8位UUID前缀>-<sanitized-original-filename>
```

对原始文件名做安全处理：
- 移除路径分隔符 `/` `\`
- 移除 `..`
- 只保留字母、数字、`-`、`_`、`.`
- 长度上限 200 字符

#### 生命周期

| 事件 | 行为 |
|---|---|
| 上传成功 | 文件写入 session 子目录 |
| session 终止（DELETE /mcp） | 清理该 session 的所有上传文件 |
| session 过期（超时） | 清理该 session 的所有上传文件 |
| MCP server 停止 | 清理整个 `mcp-uploads/` 目录 |
| 文件 TTL 到期 | 单文件级清理（默认 TTL = 1 小时） |

### 四、`@filename` 引用机制

#### 设计

当任何 MCP tool 的参数中出现 `@<storedName>` 格式的值时，参数解析层自动将其替换为暂存目录中的绝对路径。

#### 规则

1. 以 `@` 开头的字符串参数触发引用解析
2. `@` 之后的部分作为 `storedName` 在当前 session 的暂存目录中查找
3. 找到 → 替换为绝对路径（如 `/Users/.../mcp-uploads/<session-id>/a1b2c3d4-game.ipa`）
4. 未找到 → 返回明确错误，而非静默传递
5. 如果参数值不以 `@` 开头 → 不做任何处理，保持原值

#### 示例

Agent 先上传文件：

```bash
curl -X POST http://127.0.0.1:19820/upload \
  -H "Mcp-Session-Id: sess-abc123" \
  -H "X-Filename: game.ipa" \
  --data-binary @/path/to/game.ipa
```

响应：
```json
{
  "storedName": "a1b2c3d4-game.ipa",
  "reference": "@a1b2c3d4-game.ipa",
  ...
}
```

然后用返回的 reference 调用 `install_ipa`：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "install_ipa",
    "arguments": {
      "ipaPath": "@a1b2c3d4-game.ipa"
    }
  }
}
```

MCP 侧自动将 `@a1b2c3d4-game.ipa` 解析为本地绝对路径，然后走现有安装流程。

### 五、`@filename` 解析的实施位置

有两个可选策略：

#### 策略 A：在 tool handler 层解析（推荐）

在 `InstallerTools`（及未来其他需要文件路径的 tool）的 handler 里，对路径类参数调用统一的解析函数：

```swift
// UploadManager 提供的解析函数
func resolveFileReference(_ value: String, sessionId: String) throws -> String
```

**优点**：
- 显式、可控，每个 tool 自己决定哪些参数需要解析
- 不会意外改变非路径参数
- 调试友好

**缺点**：
- 每个新 tool 都需要主动调用

#### 策略 B：在 transport 层全局拦截

在 `StreamableHTTPTransport.handlePost` 中，对所有 `tools/call` 请求的 `arguments` 做全局扫描和替换。

**优点**：
- 一劳永逸，新 tool 自动获得支持

**缺点**：
- 可能误替换非路径参数
- 与 transport 层耦合

**结论：采用策略 A**。显式解析更安全，且当前需要文件路径的 tool 数量有限。

### 六、需要新增的代码组件

#### 1. `UploadManager`

新文件：`PlayCoverMCP/Transport/UploadManager.swift`

职责：
- 管理暂存目录的创建和清理
- 写入上传文件
- 生成 `storedName`
- 解析 `@filename` 引用
- 按 session / TTL 清理过期文件
- SHA256 校验

关键接口：

```swift
public final class UploadManager {
    /// 暂存目录根路径
    let uploadRoot: URL

    /// 默认文件 TTL（秒）
    let defaultTTL: TimeInterval  // 3600

    /// 默认最大文件大小（字节）
    let maxFileSize: Int  // 500 * 1024 * 1024

    /// 保存上传文件，返回元数据
    func store(
        data: Data,
        filename: String,
        sessionId: String,
        sha256: String?
    ) throws -> UploadResult

    /// 解析 @filename 引用为绝对路径
    func resolveReference(_ value: String, sessionId: String) throws -> String

    /// 清理指定 session 的所有文件
    func cleanupSession(_ sessionId: String)

    /// 清理所有过期文件
    func cleanupExpired()

    /// 清理整个上传目录
    func cleanupAll()
}

public struct UploadResult {
    let filename: String
    let storedName: String
    let size: Int
    let sha256: String
    let expiresIn: TimeInterval
    let reference: String
    let localPath: String
}
```

#### 2. StreamableHTTPTransport 扩展

在 `StreamableHTTPTransport.runServer()` 中新增路由：

```swift
router.post(RouterPath("/upload")) { [weak self] request, _ -> Response in
    guard let self = self else {
        return Response(status: .internalServerError)
    }
    return await self.handleUpload(request: request, sessionManager: sessionMgr)
}
```

新增 `handleUpload` 方法，处理：
- session 验证（复用现有的 `resolveSessionContext`）
- Origin 校验（复用现有逻辑）
- 读取 `X-Filename` header
- 收集请求 body（需要调大 body size limit）
- 调用 `UploadManager.store()`
- 返回 JSON 响应

#### 3. InstallerTools 修改

在 `install_ipa` 和 `export_patched_ipa` 的 handler 中，对 `ipaPath` 参数增加引用解析：

```swift
var resolvedPath = ipaPath
if ipaPath.hasPrefix("@") {
    resolvedPath = try uploadManager.resolveReference(ipaPath, sessionId: sessionId)
}
```

这要求 handler 能获取到当前请求的 `sessionId`。

#### 4. Session ID 传递

当前 tool handler 的签名是：

```swift
server.registerTool(name: "install_ipa") { arguments in ... }
```

handler 只接收 `arguments`，不知道当前 session。需要扩展 handler 签名或通过上下文传递 session ID。

两种方式：

**方式 a：扩展 handler 闭包签名**

```swift
// 从 (AnyCodable?) -> CallToolResult
// 改为 (AnyCodable?, ToolContext?) -> CallToolResult

public struct ToolContext {
    let sessionId: String?
}
```

**方式 b：Thread-local / Task-local 存储**

在 transport 层设置当前 session ID，handler 通过 `ToolContext.current` 读取。

**结论：采用方式 a**，更显式，不依赖 Thread-local 魔法。这需要修改 `MCPServer.registerTool` 的签名，但改动可以向下兼容（`context` 参数可选）。

### 七、/upload 的 body size 限制

当前 `/mcp` 端点的 `maxBodySize` 是 1 MB，显然不适用于文件上传。

设计：
- `/upload` 端点使用独立的 body size 限制
- 默认 500 MB
- 通过 `UploadManager.maxFileSize` 配置
- 在 Hummingbird 层面，`/upload` 路由使用 **流式读取** 而非一次性 `collectBody`，避免内存爆炸

### 八、流式写入（大文件支持）

对于大 IPA 文件（可能数 GB），不应将整个 body 读入内存。

设计：
- 使用 Hummingbird 的 `request.body` `AsyncSequence` 接口
- 逐块写入磁盘
- 边写边计算 SHA256
- 达到 size limit 时提前终止并返回 413

### 九、安全考虑

| 风险 | 缓解 |
|---|---|
| 路径穿越 | 文件名严格 sanitize，禁止 `/`、`\`、`..` |
| 磁盘填满 | 文件大小限制 + TTL 自动清理 + session 清理 |
| 未授权上传 | 要求有效 `Mcp-Session-Id`（必须先 initialize） |
| DNS rebinding | 复用现有 Origin 校验 |
| 引用注入 | `@` 引用只在明确为路径的参数上解析，不做全局替换 |

### 十、`/upload` 不走 MCP 协议

注意：`/upload` 是一个**普通 HTTP 端点**，不是 MCP JSON-RPC method。

原因：
- MCP JSON-RPC 消息体必须是 JSON，无法直接传输二进制
- 虽然可以用 base64 编码嵌入 JSON，但对于大文件效率极差
- `/upload` 作为 transport 层的辅助端点，与 `/mcp` 并列，属于 PlayCover MCP HTTP transport 的扩展

### 十一、与 MCP 协议 tools/list 的关系

`/upload` 不是一个 MCP tool，因此不会出现在 `tools/list` 的返回里。

但应该在以下位置体现其存在：

1. **server capabilities**：在 `initialize` 响应中，可以在 `serverInfo` 或扩展 capabilities 中声明 `"upload": true"`
2. **tool description**：在 `install_ipa` 等工具的 description 中注明支持 `@filename` 引用
3. **文档**：在接入文档中说明 `/upload` 的用法

### 十二、对 CLI 的影响

CLI（stdio transport）不支持 `/upload`，因为 stdio 没有 HTTP 层。

CLI 场景下：
- `@filename` 解析逻辑仍然存在，但 `UploadManager` 可以不初始化
- 如果 CLI handler 收到 `@filename` 引用，返回明确错误："File references (@filename) are only supported in HTTP transport mode"

### 十三、MCPManager 集成

`MCPManager.start()` 中需要：

1. 创建 `UploadManager` 实例
2. 传给 `StreamableHTTPTransport`（transport 负责路由）
3. 传给 service 注册层（tool handler 负责解析引用）
4. 在 `MCPManager.stop()` 中调用 `UploadManager.cleanupAll()`

### 十五、curl 冒烟示例

#### 上传文件

```bash

SESSION_ID="<从 initialize 响应获取>"
```
