## 语义验证调研（2026-04-08）

## 背景

本调研用于回答一个非常具体的问题：

> 当前 Road E 的“截获 LLVM IR / 反编译为 MSL / 再编译替换”链路里，是否已经存在某种手段，能够保证“反编译后再次编译得到的 IR”和“最初截获的 IR”在语义上等价？

结论先行：

**当前没有严格的语义等价保证机制。**

更准确地说，当前实现做到的是：

- **翻译目标**上追求“逐指令语义等价”
- **工程守门**上要求“生成的 MSL 可编译、无明显 LLVM 泄漏”
- **回归流程**上具备 replay / compile / diff / `.gputrace` 检查 / render-structure 对照等能力

但**尚未建立**下面这些关键闭环：

- 原始 IR 与“经 MSL 再编译回来”的 IR 的 round-trip 比较
- 形式化的 IR 语义等价判定
- GPU ISA 级等价检查
- 固定输入下的 shader 输出 gold test
- 固定场景下的稳定像素级/attachment 级行为验证

因此，当前更合理的判断是：

**Road E 把“语义等价”作为最高目标明确写进了文档，但现状仍属于“工程近似保证”，而不是“已经证明的语义闭环”。**

## 二、文档层面对“语义等价”的定位

`00-Dashboard.md` 已经把这件事写得非常清楚：

1. **语义等价**
2. **可编译**
3. **可读性**

并且它不是泛泛地说“尽量接近”，而是明确写成：

- 生成的 MSL 必须与原始 IR **逐指令语义等价**
- 函数签名与原始 metallib 一致

这说明从 Road E 的设计目标上看，项目并不满足于“能编译就行”。

但是，目标和验证手段是两回事。当前的缺口恰恰在于：

**文档把语义等价列为第一优先级，但实现侧还没有把“语义等价”落成一套可自动执行、可重复回归、可证明失败/成功的验证闭环。**

## 三、当前已经具备的保证，属于什么层级

下面按“保证强度”从弱到强梳理当前已有能力。

### 1. 翻译策略层：追求语义保持

`IRToMSLConverter.swift` 的整体思路是“逐指令机械翻译”。

当前已覆盖或重点处理的内容包括：

- `addrspace(N)` → MSL 地址空间限定符
- `air.*` 内建 → MSL 等效 builtin / intrinsic
- SSA 寄存器 → MSL 表达式 / 临时变量
- `phi` → 前驱块赋值
- `extractvalue` / `insertvalue`
- `getelementptr` 的结构体/数组路径还原
- 各类 cast、load/store、icmp/fcmp、select、branch

这意味着当前转换器不是“拍脑袋重写 shader”，而是在尽量保持 IR 的结构和意图。

### 2. 结构卫生层：生成源码 preflight

运行时与离线回放都会检查生成的 MSL 里有没有明显的 LLVM 残留，例如：

- LLVM vector 语法
- `ptr`
- `addrspace(...)`
- `%ssa_name`
- `i32/i64` 这类原始 LLVM 整数类型字面
- `@symbol`
- `undef / poison / zeroinitializer`

这一步的价值是：

- 能快速发现 lowering 未完成
- 能避免把明显错误的源码继续送进 `metal -c` 或 `makeLibrary(source:)`

但它的边界也很明显：

**它只能证明“没有明显的 LLVM 语法泄漏”，不能证明“语义与原始 IR 一致”。**

### 3. 编译层：生成结果必须可编译

当前无论 runtime 还是离线 replay，都会把生成的 MSL 送进 Metal 编译器。

也就是：

- runtime：`makeLibrary(source:)`
- offline：`xcrun metal -c`

这一步是当前最实在的工程 gate。

它能证明：

- 生成结果在语法上和 Metal 类型系统上是可接受的
- lowering 至少没有把源码生成到 Metal 编译器完全拒绝的程度

但它依然不能证明：

- 重新编译后的 library 与原始 library 语义相同
- Metal 编译器在优化、重排、选择 builtin 实现时没有引入行为差异

### 4. 元数据层：函数名/类型被记录，但未形成强断言

当前在 `module.meta.json` 中会记录：

- `functionNames`
- `functionTypes`
- `generatedFunctionNames`
- `generatedFunctionTypes`

这说明实现已经意识到“原始函数集”和“生成函数集”是重要对照项。

但是当前状态是：

- **有记录**
- **没有看到统一的自动断言 gate**

也就是说，这些字段更多是为了排查和离线分析准备，而不是已经升级成“只要不一致就失败”的验证规则。

### 5. 回归层：replay / compile / baseline diff

`Scripts/corpus_replay_runner.py` 已经形成比较成熟的离线主回路：

- 对 `ShaderCorpus/` 或显式 `.ll` 做 replay
- 生成新的 `.metal`
- 继续做 batch compile
- 保存 baseline
- 与 baseline 做 diff
- compile regression 时直接返回非 0

这套能力的意义很大，它保证了：

- 当前 lowering 迭代不是只靠 live 肉眼试错
- 已收敛样本可以稳定回归
- 新改动会不会把已通过样本重新打坏，可以自动发现

但需要明确：

**这里比较的对象主要是“生成的 MSL 文本、编译结果和错误类别”，不是“原始 IR 与重编译后 IR 的语义”。**

### 6. 运行时行为侧：有结构化排查手段，但未闭环到语义证明

当前已经具备：

- `compare_capture_runs.py`
- `check_gputrace_sources.py`
- `e006d_render_diff.py`
- `.gputrace` 可见源码覆盖检查
- Command Buffer / Render Encoder / Pipeline State 结构差异检查

这使得项目可以进一步判断：

- 输入是否稳定
- 输出 MSL 是否稳定
- replacement 是否稳定命中
- draw-call / pipeline 结构是否在 off/on 之间出现偏移

这已经比“只看 compile green”强很多。

但当前 `E-006d` 也明确承认：

- “可编译”不等于“语义等价”
- 画面异常问题里，仍存在“当前 MSL 只是可编译，未必语义等价”的待验证假设

也就是说，**项目内部其实已经知道这条缺口存在。**

## 四、当前明确缺失的保证

### 1. 没有 IR round-trip

当前没有看到任何脚本或 runtime 逻辑在做下面这件事：

```text
原始 module.ll
  ↓
IRToMSLConverter
  ↓
generated.metal
  ↓
metal -c
  ↓
generated.air
  ↓
llvm-dis
  ↓
regenerated.ll
  ↓
与原始 module.ll 做结构化比较
```

这是当前最核心的缺口。

### 2. 没有形式化语义等价检查

当前没有看到：

- CFG 等价比较
- canonical IR 比较器
- resource / builtin / address-space 等价判定器
- fast-math flag / metadata 语义影响分析
- Alive2 / SMT 类等价证明器

换句话说，当前还没有“语义验证器”这个独立组件。

### 3. 没有 GPU ISA 级比较

研究文档里提到了 `applegpu`、`metal-objdump` 等工具，说明方向上是知道这条线的。

但目前没有看到它们进入日常验证主回路，也没有看到：

- 原始 library vs replacement library 的 GPU ISA 比较
- 关键 shader 的 ISA 稳定性检查

### 4. 没有行为级 shader 输出测试

当前 `test-data/` 更像是：

- lowering 模式覆盖样本
- 编译器行为探针
- replay/compile 的单点回归集

而不是：

- 在固定输入下运行 shader
- 比较 shader 输出 buffer / texture / return value
- 对比原始链路与重建链路的行为结果

因此它还不是“语义 gold test”。

### 5. 没有稳定的 render-output gold test

即使 `.gputrace` 可见、compile green、replacement hit，看起来链路都打通了，项目仍然在 `E-006d` 上遇到过画面异常。

这恰恰说明：

- compile 通过不够
- `.gputrace` 可见不够
- 输入/模块哈希稳定也不够

真正想证明“语义一致”，至少还需要某种输出层的稳定比较。

## 五、为什么“IR 一样”本身也不是最终目标

用户问题表述为：

> 能否保证反编译后再次编译的 IR，与最初截获的 IR，语义是一样的？

这里必须区分两件事：

### 1. IR 文本/结构相同

这通常意味着：

- 指令序列相同
- SSA 名字、块结构、类型展开、metadata 等高度一致

### 2. IR 语义相同

这只要求：

- 对同样输入，行为一致
- 资源读取、地址空间、builtin 语义、输出结果一致

但两者并不等价。

原因包括：

- Metal 编译器版本变化会导致 IR 结构变化
- 优化开关可能改变块结构或临时变量组织
- 一些 metadata 差异未必改变语义
- 相同语义可能对应多个不同的 LLVM IR 形式

因此，后续真正应该追求的，不是“字节级 identical IR”，而是：

**在可接受的 canonicalization 之后，证明“结构上足够接近 + 关键语义点一致 + 行为层无差异”。**

---

## 六、当前最准确的现状判断

可以把当前状态概括成下面这句话：

> **Road E 的“语义等价”目前仍是目标约束，而不是已经被独立验证闭环证明的事实。**

如果再展开一点，可以写成：

- 当前实现**不是盲翻译**，而是尽量做逐指令机械翻译
- 当前验证**不是没有**，而是已经有一套相当成熟的工程回归能力
- 但这套能力的重心仍然是：
  - lowering 是否漏翻
  - 生成 MSL 是否可编译
  - 回归是否退化
  - `.gputrace` 是否可见源码
  - off/on 运行路径是否出现结构性差异
- 这距离“可以严格宣称语义等价已经得到保证”还差一整层甚至两整层验证体系

因此，如果需要对外或对内下一个不误导人的结论，推荐使用下面的表述：

> **当前已建立的是“工程近似保证 + 多层回归观察”，不是“IR 语义一致性已被严格证明”。**

---

## 七、建议的验证分层模型

如果要系统性补齐这件事，建议不要一上来追求“一个工具解决全部问题”，而是分层推进。

### 第 1 层：Round-trip 结构验证（最优先）

目标：建立最小的 IR round-trip 闭环。

建议流程：

```text
module.ll
  ↓
IRToMSLConverter
  ↓
generated.metal
  ↓
metal -c
  ↓
generated.air
  ↓
llvm-dis
  ↓
regenerated.ll
```

然后对：

- 原始 `module.ll`
- `regenerated.ll`

做 canonical compare。

比较重点不应只是文本 diff，而应包括：

- shader entry 函数集合
- shader type（vertex/fragment/kernel）
- 参数个数、顺序、关键类型形态
- 地址空间
- 关键 builtin / intrinsic 使用
- 资源绑定语义（buffer / texture / sampler / stage_in / builtins）
- 返回类型和关键输出语义
- CFG 粗结构

### 第 2 层：Round-trip 结果分级

不要只输出“通过/失败”，建议分成：

- **L0 identical**：规范化后几乎一致
- **L1 structurally equivalent**：允许一些无关差异，但关键结构一致
- **L2 behavior-risk only**：结构看起来大致可接受，但存在需要人工复核的 builtin / fast-math / resource 变化
- **L3 mismatch**：关键语义面已偏离

这样更适合 Road E 当前大量真实样本的批量回归。

### 第 3 层：最小行为测试

对 `test-data/` 中部分样本，逐步补成“可验证输出”的最小行为测试。

例如：

- 固定输入向量/矩阵
- 固定纹理读取坐标
- 固定 sampler 行为
- 固定 select/phi/cast/compare 分支输入

比较：

- 原始逻辑的预期输出
- round-trip 链路下的输出

这层不必覆盖全部真实 shader，但要覆盖最容易出错的 lowering 模式。

### 第 4 层：真实场景输出验证

对少量代表性真实样本或真实 frame，对比：

- attachment
- 关键 pass
- pipeline state
- 如有条件，再到像素级或资源级差异

这层成本高，不应作为日常默认 gate，但它是“真正回答语义是否落到最终画面层”的必要证据层。

---

## 八、建议的最小落地路线

如果只做“最小、最值回报、可在当前仓库里落地”的方案，推荐顺序如下：

### 阶段 A：先补离线 IR round-trip harness

建议新增一个离线工具，职责仅限于：

1. 读取一个或多个 `.ll`
2. 调用 `IRToMSLConverter`
3. 生成 `.metal`
4. 调用 `xcrun metal -c`
5. 生成 `.air`
6. 调用 `llvm-dis`
7. 产出 `regenerated.ll`
8. 输出结构化 compare report

此阶段先不碰 live，不碰 `.gputrace`，只解决“有没有最小 round-trip 证据”的问题。

### 阶段 B：补 canonical compare

建议从最务实的比较开始：

- entry 函数名/类型
- 参数与返回类型摘要
- builtin / resource 使用摘要
- 关键类型签名
- CFG 摘要
- 关键 instruction family 统计

而不是第一版就上完整 IR AST 等价器。

### 阶段 C：把 compare 接入 `test-data/` 和 `ShaderCorpus`

先跑：

- `test-data/` 中最小样本
- 少量 `ShaderCorpus` 代表样本

将结果分级输出，优先找出：

- round-trip 失败样本
- 结构变化大但编译仍通过的样本
- 极可能存在语义风险的 builtin/资源映射样本

### 阶段 D：再决定是否进入 ISA 或输出层验证

只有当 A/B/C 已经跑通后，再决定是否要：

- 接 `applegpu`
- 做 GPU ISA 差异检查
- 做固定帧 output gold test

否则过早把问题拉到最重层，会再次回到高成本 live 试错模式。

---

## 九、对现有 Road E 工作流的建议影响

当前不建议把“语义验证”理解成“替换现有 replay/compile/diff 主回路”。

更合理的位置是：

### 现有主回路仍保留

```text
真实样本采集
  ↓
导出 corpus
  ↓
离线 replay
  ↓
compile / diff / 归因
  ↓
少量 live 复测
```

### 语义验证作为新的一条“更深一层”的离线能力插入

```text
module.ll
  ↓
IR -> MSL
  ↓
MSL -> AIR
  ↓
AIR -> IR
  ↓
canonical compare
  ↓
输出结构化语义风险报告
```

也就是说：

- 它不是替代当前的 E-005
- 它更像是 E-005 之后新增的一层“语义风险筛查器”

这样最符合当前仓库已经形成的 offline-first 组织方式。

## 十、最终总结

### 核心结论

**当前没有手段可以严格保证：反编译后再次编译得到的 IR，与最初截获的 IR 在语义上一定一样。**

### 当前已经做到的

- 逐指令机械翻译，目标上追求语义等价
- preflight 检查明显 LLVM 泄漏
- 生成 MSL 必须可编译
- 具备 replay / compile / baseline diff 回归能力
- 具备 `.gputrace` 可见性检查和 render-structure 对照能力

### 当前还没做到的

- IR round-trip 验证
- IR 语义等价验证器
- GPU ISA 级比较
- shader 行为级 gold test
- 稳定的 render-output gold test

### 最准确的现状表述

> **当前 Road E 的“语义等价”是设计目标，不是已经被验证闭环证明的事实；现状属于“工程近似保证”，而不是“严格语义保证”。**

### 最推荐的下一步

**优先补一个最小离线 IR round-trip harness。**

这是当前成本最低、收益最高、也最能直接回答“到底有没有语义闭环证据”的一步。
