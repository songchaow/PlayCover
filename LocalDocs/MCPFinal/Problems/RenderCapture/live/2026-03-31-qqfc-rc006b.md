本轮只做一件事：

> **把 `captureObject / scope / 时序` 差异落成最小可执行代码实验，并在真实 `QQ飞车` fresh session 上验证：`scope` 路径是否能把失败点从当前 `device` 路径上推进。**

### 二、本轮代码实验

本轮对 MCP / runtime 做了一个新的最小实验入口：

1. `capture_metal_frame` 新增可选参数：
   - `capture_target=device`
   - `capture_target=scope`
2. runtime `MetalCaptureService.captureFrame(...)` 新增 target 分支：
   - `device`：仍抓默认 `MTLDevice`
   - `scope`：创建一个绑定默认 `MTLDevice` 的临时 `MTLCaptureScope`
3. `scope` 路径的时序改为：
   - `startCapture(with: descriptor)` 成功后，不立即 `begin`
   - 等首个 vsync 到来时才 `scope.begin()`
   - 满足 `duration_ms` 且至少经过 2 个 vsync 后再 `scope.end()` + `manager.stopCapture()`
4. `capture_metal_frame` 失败文本现在会显式回传：
   - `target=...`
   - `captureObject=...`

本轮验证前还做了两项收敛：

### 五、本轮结论

本轮得到一条比上一轮更强的差异链：

1. `scope` 实验已经**确定命中新代码路径**，因为 runtime 错误文本里明确回出了：
   - `target=scope`
   - `captureObject=scope(...)`
2. 但即便把 capture target 从默认 `MTLDevice` 改成了**默认设备绑定的 `MTLCaptureScope`**，Apple API 仍然在 `startCapture` 阶段直接拒绝：
   - `Capturing is not supported.`
3. 同一 fresh session 上补做 `device` 对照后，失败点与 `scope` 完全同层：
   - 都失败在 `startCapture`
   - 都没有 `.gputrace` 落盘
   - 都不会把 session 打坏
4. 因此当前可以进一步排除：

> **“只要把 `captureObject` 从默认 `MTLDevice` 换成一个绑定默认设备的 `MTLCaptureScope`，PlayCover 就会接近 app 内成功路径。”**

答案是：

> **不会。**

当前最可信的新判断是：

- 问题已经不只是“`device` vs `scope(device)`”
- app 内成功按钮更可能依赖：
  - **真实渲染 `MTLCommandQueue`**
  - 或 **queue-bound `MTLCaptureScope`**
  - 或 app 内部更贴近真实渲染提交点的 begin/end 语义
