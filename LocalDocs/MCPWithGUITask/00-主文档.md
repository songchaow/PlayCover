# MCPWithGUI 任务执行主文档

> **所有 agent 必须首先读取本文件。** 本文件是全局导航入口，记录任务状态、工作流程和关键注意事项。

## 一、项目目标

将 `PlayCoverMCP`（独立 CLI）的 MCP 能力**嵌入 PlayCover.app GUI 进程**，采用**方案 A2：进程内 TCP Transport**。用户启动 GUI 即自动获得 MCP 服务（`localhost:19820`），无需手动启动 CLI。

## 五、每个 Agent 的标准工作流

### 5.1 开始前

1. **读取本文件**，确认任务状态看板，找到自己要做的任务
2. **读取 `01-架构与技术约束.md`**，了解技术约束
3. **读取对应的子任务文档**（如 `G03-TCPTransport实现.md`），了解详细要求
4. **读取 `99-经验教训.md`**，了解前序 agent 踩过的坑
5. 确认前置依赖任务已完成（看板状态为 ✅）

### 5.2 执行中

1. 遵循子任务文档中的实现指导和验收标准
2. **小步验证**：每次改动后立即构建验证
3. **先读后写**：编辑文件前先 `read_file` 确认当前内容
4. 遇到新的经验教训时，随时记录到 `99-经验教训.md`

### 5.3 完成后（四步收尾）

#### 步骤 1：验证与测试

- 运行本任务的验收标准中列出的所有测试
- **完整跑一遍回归测试**，确认未破坏前序任务的工作：
  ```bash
  # 构建 PlayCover GUI
  xcodebuild -project PlayCover.xcodeproj -scheme PlayCover -configuration Release build 2>&1 | tail -5
  
  # 构建 PlayCoverMCP CLI
  xcodebuild -project PlayCover.xcodeproj -scheme PlayCoverMCP -configuration Release build 2>&1 | tail -5
  
  # 运行 MCP 单元测试
  xcodebuild test -project PlayCover.xcodeproj -scheme PlayCoverMCP -destination 'platform=macOS,arch=arm64' 2>&1 | tail -20
  ```
- 将测试结果摘要写入子任务文档的「实际测试结果」节

#### 步骤 2：更新任务状态

- 在**本文件**的任务状态看板中，将自己的任务状态改为 ✅
- 如果发现问题需要后续处理，标为 ❌ 并注明原因

#### 步骤 3：整理经验教训

- 将本次遇到的问题、解决方案、踩过的坑追加到 `99-经验教训.md`
- 如果无新增经验，在 `99-经验教训.md` 中对应任务章节注明「无新增」

#### 步骤 4：Git Commit

```bash
# 添加本次修改的所有文件（代码 + 文档）
git add -A
# commit message 格式：[MCPWithGUI] G0X: 简要描述
git commit -m "[MCPWithGUI] G0X: 简要描述"
```

## 六、核心约束（所有 agent 必须遵守）

### 6.1 不可违反的红线

1. **不改变 MCP 对外协议**：JSON-RPC 消息格式、tool/resource 定义均不变
2. **保留独立 CLI**：`PlayCoverMCP` CLI target 继续存在，stdio 模式不受影响
3. **GUI 零功能回退**：嵌入 MCP 后，GUI 原有所有功能必须正常工作
4. **最小侵入原则**：优先新增代码，避免大规模重构现有 GUI 或 MCP 代码

### 6.2 pbxproj 修改三步验证

任何修改 `PlayCover.xcodeproj/project.pbxproj` 的操作，**必须**执行：

1. `plutil -lint PlayCover.xcodeproj/project.pbxproj` → 必须输出 OK
2. `git diff PlayCover.xcodeproj/project.pbxproj` → 确认只改了预期内容
3. 两个 scheme 都能编译通过

如果 `plutil -lint` 失败，**立即 `git checkout -- PlayCover.xcodeproj/project.pbxproj` 恢复**。

### 6.3 测试 Target 结构

- PlayCoverMCPTests 采用**源码直编模式**（直接编译被测源文件，不通过 `@testable import`）
- 新增 MCP 源文件时，**必须同时添加到 PlayCoverMCP target 和 PlayCoverMCPTests target**
- 每个 target 需要独立的 `PBXBuildFile` 条目

### 6.4 Shell 命名冲突

- GUI 侧：`class Shell: ObservableObject`（`PlayCover/Utils/Shell.swift`）— 不改名
- MCP 侧：`enum MCPShell`（`PlayCoverMCP/HostServices/MCPShell.swift`）— 类名和文件名均已改名（G01 改类名，G02 改文件名）
- MCP Shell 的引用点：`InstallerService.swift`（17处）、`InjectionService.swift`（9处）、`SigningService.swift`（5处）、`LaunchService.swift`（2处）

### 6.5 String: Error 冲突

- GUI 的 `PlayCover/Utils/Shell.swift` 包含 `extension String: Error` 和 `extension String: LocalizedError`
- MCP 侧没有此扩展，MCP 使用 `ShellError` 结构体
- 如果两者编译到同一 target，不会冲突（MCP 不依赖 String 作为 Error）
- 但要注意 `extension String: Error` 是全局的 protocol conformance，可能影响 MCP 代码的错误处理行为

### 6.6 构建命令速查

```bash
# GUI app 构建
xcodebuild -project PlayCover.xcodeproj -scheme PlayCover -configuration Release build

# MCP CLI 构建
xcodebuild -project PlayCover.xcodeproj -scheme PlayCoverMCP -configuration Release build

# MCP 测试（构建+运行）
xcodebuild test -project PlayCover.xcodeproj -scheme PlayCoverMCP -destination 'platform=macOS,arch=arm64'

# MCP 测试（只构建，不运行）
xcodebuild build-for-testing -scheme PlayCoverMCP -destination 'platform=macOS,arch=arm64'

# pbxproj 格式验证
plutil -lint PlayCover.xcodeproj/project.pbxproj
```

## 七、经验教训引用

详见 `99-经验教训.md`。以下是从 MCP Phase 0-1 继承的关键教训（完整版见 `LocalDocs/MCP/08-经验教训与常见陷阱.md`）：

1. **pbxproj 修改极其危险**：不要用 `str.replace()`，用精确定位插入；脚本中动态查找 ID，不硬编码
2. **测试 target 需同步添加源文件**：新增 .swift 必须同时加入业务 target 和测试 target
3. **先确认架构可行性再写代码**：先验证 target 依赖关系、API 签名，再动手实现
4. **小步验证**：每次改动后立即构建，不累积多个改动
5. **filter 语义是"保留"**：要移除元素时条件应取反
