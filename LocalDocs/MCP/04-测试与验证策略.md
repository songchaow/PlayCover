### 目标

确保每次新增一个 MCP 功能后，都尽量能以**自动化方式**验证它真的可用，而不是只停留在代码层面“看起来能跑”。

### 总体原则

- **优先自动化测试**
- **其次做 MCP 级冒烟测试**
- **最后才接受人工验证**
- 如果只能人工验证，必须写明原因与步骤

### 测试分层

#### 一、单元测试

适合验证：

- 参数解析
- schema 校验
- tool registry
- resource registry
- task state machine
- error mapping
- session command 编码 / 解码

#### 二、集成测试

适合验证：

- Host service 与文件系统 / fixture 交互
- MCP 请求 -> tool handler -> 结构化响应
- Session registry 与 bridge client 协作
- logging / task progress / resource read

#### 三、MCP 冒烟测试

适合验证：

- `initialize`
- `tools/list`
- 单个 `tools/call`
- 单个 `resources/read`
- 长任务创建、轮询、完成

推荐做法：

- 统一维护一个简单脚本或测试 helper
- 通过 `stdio` 启动 server
- 发送最小 JSON-RPC / MCP 请求序列
- 断言返回结构

#### 四、人工验证

只在以下情况下接受：

- 必须依赖真实已安装 app
- 必须依赖真实注入后的运行态
- 当前很难在 CI 或本地 fixture 中复刻

即便如此，也要：

- 给出完整步骤
- 说明前置条件
- 说明结果判断标准

### 每个任务的最低测试要求

#### Host-only 任务

至少要有：

- **自动化单元 / 集成测试** 一组
- **MCP 冒烟测试** 至少一条

#### Session 任务

至少要有：

- **协议 / command 层自动化测试**
- **host 与 fake runtime 的集成测试**
- 如能做到，再补真实运行态 smoke

#### 基础设施任务

至少要有：

- 新 target / 新 test target 可构建
- 最小 server 初始化冒烟通过

### 推荐测试资产

建议后续任务逐步建立：

- **fixture app 目录**
- **fixture keymap 文件**
- **fixture entitlements 文件**
- **fake host service**
- **fake runtime bridge server**
- **MCP stdio smoke helper**

### 长任务验证要求

对以下能力，必须验证 task 维度行为：

- `install_ipa`
- `export_patched_ipa`
- `resign_app`
- `inject_playtools`
- `remove_playtools`

至少验证：

- 能创建任务
- 能获取状态
- 成功时结果结构正确
- 失败时错误结构正确

### 测试结果记录要求

每个任务卡完成时，必须在任务卡里留下：

- **实际执行命令**
- **执行结果摘要**
- **未覆盖项**
- **未覆盖原因**

### 禁止事项

- 只写“已测试”但不写命令
- 只靠肉眼看代码就当验证通过
- 因为测试麻烦就完全不做验证
- 把本任务的测试债务全部留给后续任务
