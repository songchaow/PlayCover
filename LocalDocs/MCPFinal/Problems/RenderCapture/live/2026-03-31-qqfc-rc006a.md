## QQ飞车：RC-006-A live 样本（2026-03-31）

### 一、本轮目标

本轮只做一件事：

> **移除 PlayCover 当前 `capture_metal_frame` 的 `supportsDestination(.gpuTraceDocument)` 硬前置失败后，在真实 `QQ飞车` fresh session 上复测一次，确认真实失败点是否发生变化。**

---

### 二、本轮代码实验

本轮对 runtime 做了最小修正：

1. `MetalCaptureService.captureFrame(...)` 不再因为 `supportsGPUTrace == false` 直接提前返回
2. 即使 preflight 仍显示 `supportsGPUTrace=false`，也继续尝试 `manager.startCapture(with: descriptor)`
3. `BridgeListener` 现在会把 host 传入的 `duration_ms` 继续传给 runtime
4. runtime stop 语义改为：
   - 至少经过 2 个 vsync
   - 且达到 `durationMs`
   - 额外加 watchdog 防止异常悬挂

本轮构建 / 安装要求遵循用户约束：

- 使用 `BuildScripts/build_and_install.sh Release`
- 安装产物位于：`~/Applications/PlayCover.app`
- 从安装后的 app 启动 GUI，并通过其内嵌 MCP 继续验证

### 五、本轮结论

本轮最关键的新结论是：

1. **去掉 `supportsDestination(.gpuTraceDocument)` 的硬前置失败后，PlayCover 路径已经不再停在“我们自己预检就拒绝”。**
2. 但 runtime 继续向前走后，Apple API 真实返回的是：
   - **`startCapture failed: Capturing is not supported.`**
3. 因此：
   - `supportsGPUTrace=false` 并不只是“误伤性的 host 侧门禁”
   - 它与后续 `startCapture` 的真实拒绝是**一致的 live 现象**
4. 当前最可信的差异已经进一步收敛到：
   - **app 内成功按钮并不是“简单地对默认 `MTLDevice` 执行一次 `startCapture(.gpuTraceDocument)`”**
   - 其成功前提更可能在于：
     - capture scope / `captureObject` 不同
     - 触发时机更贴近真实渲染 command queue / command buffer
     - app 内走了不同的 capture session 语义，而不是当前 PlayTools 这条默认路径

### 六、对后续任务的直接影响

这轮实验已经回答了一个关键问题：

> **“是不是只要移除 `supportsDestination(...)` 的硬门禁，PlayCover 当前实现就能像 app 内按钮一样成功？”**

答案是：

> **不是。**

因为移除硬门禁后，真实失败点只是从“预检拒绝”推进到了“`startCapture` 被 Apple API 拒绝”。

所以下一步更值得做的是：

1. 继续对照 app 内成功按钮的行为特征
2. 优先调查是否存在不同的 `captureObject` / scope 选择
3. 重点收集 app 内成功按钮是否真的是“一次点击即 capture current frame”，还是内部还做了其他预备动作
