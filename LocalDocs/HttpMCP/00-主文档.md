# PlayCover MCP: TCP → Streamable HTTP Transport 改造

> **本文档是所有 agent 的必读首文件。** 包含总体规划、任务状态、工作流程和全局注意事项。
> 子文档仅在需要时读取。

## 一、项目概述

将 PlayCover MCP 的 GUI 内嵌传输层从 **TCP (行分隔 JSON-RPC)** 改造为 **Streamable HTTP (MCP 2025-11-25 规范)**，使 Agent 客户端可以通过标准 HTTP 接口接入。

**改造范围**：

- ✅ GUI 模式：`TCPTransport` → `StreamableHTTPTransport`（替换）
- ✅ CLI 模式：`StdioTransport` 保持不变
- ✅ MCPServer / Service / Tool / Resource 层：**基本不改**（纯函数式 `handle()` 接口）

**技术选型**：使用 **[Hummingbird](https://github.com/hummingbird-project/hummingbird)** 作为 HTTP 服务器框架（轻量、纯 Swift、基于 SwiftNIO），通过 **Swift Package Manager (SPM)** 引入依赖。

## 三、架构总览

### 3.1 改造前（TCP）

```
Agent (Claude/Cursor) ──TCP:19820──▶ TCPTransport ──handler()──▶ MCPServer
                                     (行分隔 JSON-RPC)            (同步响应)
```

### 3.2 改造后（Streamable HTTP）

```
Agent ──HTTP POST/GET──▶ Hummingbird HTTP Server
                              │
                              ├── POST /mcp (JSON-RPC request)
                              │     ├── Content-Type: application/json （简单响应）
                              │     └── Content-Type: text/event-stream （SSE 流响应）
                              │
                              ├── GET /mcp (SSE 监听流，服务端主动推送)
                              │
                              └── DELETE /mcp (终止会话)
                              │
                              ▼
                        SessionManager ──▶ MCPServer.handle()
                              │                    │
                              │              ┌─────▼──────┐
                              │              │ Service层   │
                              │              │(不改动)     │
                              │              └────────────┘
                              │
                        SSEEncoder ◀── 推送通知/日志/任务进度
```

### 3.3 关键接口变化

| 维度 | 改造前 | 改造后 |
|------|-------|-------|
| **MessageHandler** | `(JSONRPCMessage) -> JSONRPCMessage?` (同步) | 保持不变，MCPServer.handle() 接口零改动 |
| **服务端推送** | 无（TCPTransport 缺少 send 方法） | SSE 流 + `MCPServer.notificationSink` 回调 |
| **会话管理** | TCP 连接 = 会话 | `Mcp-Session-Id` HTTP Header |
| **线程模型** | GCD DispatchQueue | SwiftNIO EventLoop (Hummingbird 内部) |

## 四、HTTP Server 技术选型

### 4.1 选择 Hummingbird 的理由

| 方面 | Hummingbird | Vapor | 手写 NWListener HTTP |
|------|-------------|-------|---------------------|
| 轻量级 | ✅ 极轻（核心 ~5 个包） | ❌ 依赖多 | ✅ 零依赖 |
| HTTP 完整性 | ✅ 完整 HTTP/1.1 | ✅ 完整 | ❌ 需手写 |
| SSE 支持 | ✅ 内置 ResponseBody 流式写入 | ✅ 内置 | ❌ 需手写 |
| Swift Concurrency | ✅ 原生 async/await | ✅ | ❌ GCD |
| SPM 引入 | ✅ 简单 | ✅ | N/A |
| 社区活跃度 | ✅ 活跃 | ✅ 最活跃 | N/A |
| 学习曲线 | ✅ 低 | ⚠️ 中 | ❌ 高 |

**结论**：Hummingbird 在轻量级与功能完备之间取得最佳平衡，适合嵌入 GUI 应用。

### 4.2 SPM 与现有 Carthage 的共存

当前项目使用 Carthage 管理 PlayTools 依赖。SPM 包可以通过 Xcode 的 "Add Package" 功能添加，与 Carthage 互不干扰：

- Carthage：管理 PlayTools（构建为 framework，通过 Build Phase 脚本复制）
- SPM：管理 Hummingbird + SwiftNIO（Xcode 自动解析和链接）

### 5.3 冒烟测试脚本（H03 完成后可用）

```bash
# 1. 发送 initialize 请求（POST，期望 JSON 响应）
curl -X POST http://127.0.0.1:19820/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"test","version":"1.0"}}}'

# 2. 发送 initialized 通知（POST，期望 202）
curl -X POST http://127.0.0.1:19820/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Mcp-Session-Id: <从步骤1响应头获取>" \
  -H "Mcp-Protocol-Version: 2025-11-25" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'

# 3. 获取工具列表（POST，期望 JSON 响应）
curl -X POST http://127.0.0.1:19820/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Mcp-Session-Id: <session-id>" \
  -H "Mcp-Protocol-Version: 2025-11-25" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'

# 4. 打开 SSE 监听流（GET，期望 text/event-stream）
curl -N http://127.0.0.1:19820/mcp \
  -H "Accept: text/event-stream" \
  -H "Mcp-Session-Id: <session-id>" \
  -H "Mcp-Protocol-Version: 2025-11-25"

# 5. 终止会话（DELETE，期望 200）
curl -X DELETE http://127.0.0.1:19820/mcp \
  -H "Mcp-Session-Id: <session-id>"
```

## 七、关键技术约束与注意事项

### 7.1 从历史经验继承的关键教训

> 以下来自 `LocalDocs/MCPWithGUITask/99-经验教训.md` 和 `LocalDocs/MCP/08-经验教训与常见陷阱.md`，在本轮工作中同样适用：

1. **pbxproj 修改极其危险**：使用三步验证（`plutil -lint` → `git diff` → build），脚本中动态查找 ID
2. **测试 target 需同步添加源文件**：新增 `.swift` 必须同时加入业务 target 和测试 target
3. **先确认架构可行性再写代码**：先验证 SPM 包集成、Hummingbird API 可用性，再动手写大量代码
4. **小步验证**：每次改动后立即构建
5. **使用独立 DerivedData**：避免缓存污染（`-derivedDataPath /tmp/PlayCover-DerivedData`）
6. **PlayCoverMCP 不能导入 PlayCover 模块**：MCP 代码不依赖 GUI 模块
7. **GUI 编译需绕过环境依赖**：`FASTLANE=1 CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES`

### 7.2 本轮特有注意事项

1. **SPM 与 Carthage 共存**：通过 Xcode "Add Package" 添加 SPM 依赖，不影响 Carthage 管理的 PlayTools
2. **Hummingbird 仅链接到 PlayCover GUI target**：CLI target 和 Tests target 不需要 Hummingbird（CLI 继续用 StdioTransport）
3. **SwiftNIO EventLoop vs GCD**：Hummingbird 内部使用 SwiftNIO，回调在 EventLoop 上。调用 `MCPServer.handle()` 需要注意线程安全（MCPServer 已有 NSLock 保护）
4. **SSE 格式严格遵守规范**：`data: {...}\n\n` 格式，每个事件以双换行结束
5. **保留 TCPTransport**：不删除 `TCPTransport.swift`，只是 GUI 默认使用 HTTP Transport，保持向后兼容选项
6. **HTTP 端口复用现有设置**：复用 `MCPManager` 中的 `savedPort` / `savedHost` UserDefaults 配置

### 7.3 MCP Streamable HTTP 规范要点速查

> 详见 `mcp-docs/modelcontextprotocol/docs/specification/2025-11-25/basic/transports.mdx`

| 要点 | 规范要求 |
|------|---------|
| **端点** | 单一 HTTP 端点（如 `/mcp`），支持 POST + GET + DELETE |
| **POST 请求** | 客户端发送 JSON-RPC 消息。请求 → JSON 或 SSE 响应；通知/响应 → 202 Accepted |
| **GET 请求** | 建立 SSE 监听流，服务端可主动推送通知/请求。或 405 不支持 |
| **DELETE 请求** | 终止会话。或 405 不支持 |
| **Accept Header** | POST: 必须包含 `application/json` 和 `text/event-stream`；GET: 必须包含 `text/event-stream` |
| **Session** | `Mcp-Session-Id` Header，initialize 响应中返回，后续请求必须携带 |
| **Protocol Version** | `Mcp-Protocol-Version` Header，所有后续请求必须携带 |
| **Origin 验证** | 必须验证 Origin Header 防 DNS rebinding；无效返回 403 |
| **SSE 格式** | `data: {json}\n\n`；可选 `id:` 字段；可选 `retry:` 字段 |
| **断线恢复（可选）** | `Last-Event-ID` Header + 消息重放。本轮暂不实现 |
