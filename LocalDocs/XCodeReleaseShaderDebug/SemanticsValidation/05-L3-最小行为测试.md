## L3：最小行为测试

## 文档职责

本文只记录 L3 的**方法、harness 设计、样本选择原则、比较策略与产物形式**。

**任务状态、进展、优先级、TODO、完成判定与是否进入 L3，统一只在 `00-Dashboard.md` 维护。** 本页不重复动态控制面信息。

## 目标

在少量高价值样本上建立：

```text
固定输入
  ↓
执行 shader
  ↓
校验输出
```

L3 主要回答：

- 某些结构上“看起来差不多”的样本，行为是否真的一致
- 哪些 lowering 模式需要从“结构风险”升级为“行为风险”

## 总体策略

### 原则 1：compute-first

最小行为测试优先从 **compute shader** 开始，因为它：

- 容易自动化
- 不依赖窗口或 UI
- 输出校验相对直接
- 更适合作为第一批行为 oracle

### 原则 2：render-second

只有当问题明显属于 vertex/fragment 或 render pipeline 行为时，再补：

- 离屏 render
- 小尺寸 attachment 比较
- 关键顶点/片元输出检查

### 原则 3：先少量高价值样本

L3 不追求大覆盖，而追求：

- 信息量高
- 可以稳定自动执行
- 结果容易解释
- 可与 L2 风险形成明确映射

## harness 设计

### compute 行为 harness

L3 的最小 compute harness 应承担：

1. 读取 L1/L2 产物
2. 选择少量待验证候选
3. 载入 reference MSL 与 round-trip 生成的 MSL
4. 创建 `MTLDevice` 并执行 compute pipeline
5. 读回输出并按既定策略比较
6. 产出结构化行为报告与中间 artifact

相关实现与测试入口包括：

- `Scripts/ir_semantics_behavior_runner.py`
- `Scripts/metal_compute_behavior_runner.swift`
- `Scripts/test_ir_semantics_behavior_runner.py`

### render-second harness

对于 vertex/fragment 样本，L3 的离屏 render 扩展应优先保持：

- 小尺寸 render target（如 `1x1`、`4x4`、`16x16`）
- 固定顶点输入
- 固定纹理/常量
- 结构化输出结果
- 全流程本地、离屏、无 UI

相关实现包括：

- `Scripts/metal_fragment_behavior_runner.swift`

## 输入与输出

### 典型输入

L3 通常复用 L1/L2 已生成的报告与 artifact，例如：

- `gate-summary.json`
- `roundtrip-summary.json`
- 参考 MSL
- round-trip 生成的 MSL

### 典型产物

推荐产物包括：

- `behavior-summary.json`
- `behavior-artifacts/<sample>.spec.json`
- `behavior-artifacts/<sample>.result.json`

行为报告应至少能表达：

- 输入样本标识
- reference / generated 路径
- 比较策略
- 结果状态
- 偏差摘要
- 中间 artifact 位置

## 浮点比较策略

行为测试不应一律要求 bit-exact。

建议支持：

- `abs` / `rel` tolerance
- `strict` 与 `approx` 两类模式
- 对 fast-math 相关样本单独记录比较策略

原则是：

- 不要因为阈值过严制造大量噪声
- 也不要宽松到掩盖真实问题

## 样本选择原则

### 第一优先来源

- 固定代表集中的少量高信息量样本
- 能与 L2 风险结论直接对应的样本

### 第二优先来源

- 少量可稳定复现的真实样本
- 少量 failure-path 中适合最小化的样本

总体要求：

- 样本数量小
- 输入固定
- 输出可自动比较
- 不依赖用户摆场景或人工观察

## 与 L2 的衔接

建议遵循：

- `L0 / L1`：通常不急于升级到 L3
- `L2`：先做聚类，再挑极少量代表样本进入 L3
- `L3`：若仍无法解释，再决定是否进入 L4

也就是说，L3 的职责是把**少量结构风险样本**转化为**行为证据样本**，而不是接管整套批量验证。

## 不建议的做法

- 一上来就为全部样本建立行为 oracle
- 一上来就做真实 app 行为验证
- 把大量 GUI / live 流程塞进 L3
- 让用户手动观察画面当作默认测试方式
- 因缺少样本而要求用户额外准备环境
- 把本该属于 L4 的重流程提前搬进 L3

## 最小完成形态

一个可用的 L3 最小路径通常应满足：

1. 已建立 compute-first 的最小行为 harness
2. 至少有一组样本可以自动执行并比较输出
3. 行为测试结果可以结构化落盘
4. 流程不依赖用户频繁介入

是否真正启用、扩样或升级，统一由 `00-Dashboard.md` 决定。
