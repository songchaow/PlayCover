## 一、Xcode 工程文件（pbxproj）相关

### 1.1 不要用 Python 脚本随意修改 pbxproj

pbxproj 是一个严格格式化的 OpenStep plist 文件，**任何微小的格式错误都会导致 `plutil -lint` 失败，Xcode 无法解析**。实际踩过的坑：

- `replace_in_file` 工具的 `old_str` 如果复制粘贴时丢失了空白字符，会静默地把正确内容替换成错误内容
- Python 脚本用 `str.replace()` 时，如果 pbxproj 中有多处相同子串（如两个 target 的 Sources build phase 都有同一个文件），会**全部被替换**导致重复条目
- 脚本中硬编码的 group ID（如 `6D5A783BCD8844EF91870961`）可能已过期，运行后实际没有生效但报告 "OK"

**推荐做法**：

1. 修改 pbxproj 前先 `plutil -lint` 确认当前状态
2. 每次修改后立即 `plutil -lint` 验证
3. 用 `git diff` 对比修改范围，确认只改了预期内容
4. 集成脚本中的关键 ID 应从 pbxproj 动态查找（grep），不要硬编码
5. **如果脚本修改后 `plutil -lint` 失败，立即 `git checkout` 恢复，不要尝试手动修**

### 1.2 理解 PlayCoverMCPTests 的 target 结构

PlayCoverMCPTests 的 Sources build phase **直接包含所有被测源文件**，而不是通过链接 PlayCoverMCP framework。这意味着：

- 新增业务文件（如 `InjectionService.swift`）时，**必须同时添加到 PlayCoverMCP target 和 PlayCoverMCPTests target 的 Sources build phase**
- 每个 target 需要独立的 `PBXBuildFile` 条目（同一个 `fileRef` 可以被多个 `PBXBuildFile` 引用，但每个 `PBXBuildFile` ID 必须唯一）
- 测试文件不需要 `@testable import PlayCoverMCP`，因为源码直接编译进测试 target

**实践验证**：H10 的 `add_h10_files.py` 最初漏掉了将 `KeymapService.swift` 添加到 PlayCoverMCPTests 的 Sources build phase，导致测试编译时找不到 `KeymapService` / `KeymapError` 类型。

### 1.3 PBXFileReference 的 path 与 group path 的关系

- 如果文件在 group 内（如 `HostServices/Injection/` group），group 自身有 `path = Injection`，则 group 内的 `PBXFileReference` 只需要 `name = InjectionService.swift; path = InjectionService.swift`（相对路径由 group 提供）
- `PBXFileReference` 的 `sourceTree` 必须是 `"<group>"`，不要写成其他值

### 1.4 向 PBXGroup children 插入条目的正确方法

向 group 的 children 列表添加新条目时，**在 `);\n`（children 关闭标记）之前插入**，而不是在最后一项的换行之后：

```python
# 正确 ✅
close_idx = c.find(');\n', group_start)
insertion = f'\t\t\t\t{file_ref_id} /* FileName.swift */,\n'
c = c[:close_idx] + insertion + c[close_idx:]

# 错误 ❌ — 会导致格式错乱（多余的逗号、缩进不对）
last_child_end = c.rfind('\n', group_start, close_idx)
insertion = f',\n\t\t\t{file_ref_id} ...'
c = c[:last_child_end + 1] + insertion + c[last_child_end + 1:]
```

原因：children 列表中每项已以 `,` 结尾，闭合 `);\n` 之前的最后一项也有逗号。在最后一项之后插入会破坏 `);\n` 的位置。

### 1.5 集成脚本使用绝对路径

Python 脚本中用 `subprocess.run()` 调用外部工具（`plutil`、`xcodebuild`）时，如果传入相对路径，实际解析取决于 `cwd` 参数。**应使用 `os.path.abspath()` 构造所有路径**：

```python
PBX = os.path.abspath(os.path.join(os.path.dirname(__file__), "..", "PlayCover.xcodeproj", "project.pbxproj"))
# 后续 subprocess.run(['plutil', '-lint', PBX]) 无论 cwd 是什么都正确
```

H10 中因为 `PBX` 是相对路径，配合 `cwd=PBXDIR` 导致 `plutil` 检查的路径被双重拼接，误报失败并触发 `git checkout` 恢复了正确写入的文件。

## 二、跨模块依赖

### 2.1 PlayCoverMCP 不能导入 PlayCover 模块

PlayCoverMCP 是一个独立的 command-line tool target，**不链接 PlayCover framework**。这意味着：

- 不能 `import PlayCover`
- 不能直接使用 `PlayTools`、`PlayApp`、`Entitlements` 等 PlayCover 模块中的类
- 需要使用命令行工具（`codesign`、`otool`、`install_name_tool`、`plutil` 等）重新实现功能
- 参考 `InstallerService.swift` 和 `SigningService.swift` 的模式：通过 `Shell.run()` 调用系统命令

**在实现新 HostService 前，先确认功能是否依赖 PlayCover 模块，如果是，需要寻找替代方案。**

## 三、Swift / Foundation API 使用

### 3.1 `NSMutableDictionary.write(to:)` 返回 Void

- `plist.write(to: url)` 在旧版本 Swift 中可能返回 `Bool`，但在当前版本中 `write(to:atomically:)` 返回 `Void`
- 如果需要检查写入是否成功，使用 `plist.write(toFile: path, atomically: true)` 返回 `Bool`
- 或使用 `try plist.data(fromPropertyList:format:options:)` 然后 `Data.write(to:)`

### 3.2 ShellError 的 output 字段

- `Shell.run()` 抛出 `ShellError` 时，可以通过 `err.output` 获取命令的标准输出（包含错误信息）
- 用这个来判断错误是否可忽略（如 `install_name_tool` 的 "rpath already exists"）

### 3.3 plist 不支持 URL 类型

`URL` 对象（`CFURL`）不是合法的 plist 值类型。将 `[String: Any]` 字典通过 `(dict as NSDictionary).write(to:)` 写入 plist 时，如果字典中包含 `URL` 值，会抛出：

> `Property list invalid for format: 100 (property lists cannot contain objects of type 'CFURL')`

**正确做法**：config plist 中所有 URL 用 `.path`（`String`）存储，读取时用 `URL(fileURLWithPath:)` 转回。

```swift
// 写入
let config: [String: Any] = [
    "defaultKm": defaultURL.path,        // String, not URL
    "keymapOrder": order.map(\.path)     // [String], not [URL]
]

// 读取
let path = dict["defaultKm"] as? String ?? fallbackPath
let url = URL(fileURLWithPath: path)
```

### 3.4 URL 比较不可靠，用文件名去重

`URL(fileURLWithPath:)` 构造的 URL 与 `FileManager.contentsOfDirectory()` 返回的 URL，即使指向同一文件，`==` 比较也可能失败（路径规范化方式不同）。

**正确做法**：用 `lastPathComponent`（文件名）进行去重和比较：

```swift
var seenNames = Set<String>()
for url in config.keymapOrder {
    seenNames.insert(url.lastPathComponent)
    // ...
}
for url in directoryContents where !seenNames.contains(url.lastPathComponent) {
    // ...
}
```

## 四、任务执行流程

### 4.1 先确认架构可行性，再写大量代码

在 H09 中，先写了完整的 `InjectionService.swift` 使用 `PlayTools` 类，编译时才发现 PlayCoverMCP 不能导入 PlayCover 模块。**浪费了一轮完整的编写 + 编译尝试。**

**正确顺序**：

1. 先确认目标 target 的依赖关系（能否导入需要的模块）
2. 确认关键 API 签名（参数、返回值、sync/async）
3. 确认测试 target 的结构（如何被测文件可见）
4. 然后再写实现代码

### 4.2 先运行集成脚本再验证

H09 的集成脚本 `add_h09_files.py` 有多个 bug（硬编码错误 ID、group children 语法错误），导致 pbxproj 被破坏。**每次运行脚本后必须立即验证**：

1. `plutil -lint PlayCover.xcodeproj/project.pbxproj`
2. `git diff PlayCover.xcodeproj/project.pbxproj` 检查修改内容
3. `xcodebuild build` 验证文件能否被找到

### 4.3 测试构建和运行的正确命令

- 构建（含测试 target）：`xcodebuild build-for-testing -scheme PlayCoverMCP -destination 'platform=macOS,arch=arm64'`
- 运行测试（不重新构建）：`xcodebuild test-without-building -scheme PlayCoverMCP -destination 'platform=macOS,arch=arm64'`
- PlayCoverMCPTests 没有独立的 scheme，必须通过 PlayCoverMCP scheme 测试

## 五、文档与脚本维护

### 5.1 集成脚本应动态查找 ID

`Scripts/add_h09_files.py` 的核心问题是把 group ID（如 HostServices group）硬编码为 `6D5A783BCD8844EF91870961`，但实际 ID 是 `BFD73CC363EA45C09A0972AF`。**后续脚本应**：

- 从 pbxproj 中 grep 查找目标 group 的 ID
- 或将 ID 作为参数传入
- 验证关键 ID 存在后再操作

### 5.2 脚本运行失败不应静默成功

`add_h09_files.py` 打印了 "OK: Injection group added to HostServices" 但实际没有添加成功（因为 ID 找不到，`str.replace()` 没有匹配）。**脚本应在关键操作后验证是否成功。**

### 5.3 脚本恢复机制要谨慎

H10 的脚本在 `plutil -lint` 检查失败后执行 `git checkout -- PBX` 恢复文件，但由于路径 bug（见 1.5），plutil 对正确写入的文件误报失败，导致 `git checkout` 把正确内容也恢复了。**经验**：

- 验证失败时不要自动恢复，改为打印 WARNING 并继续，让外部 `git diff` 确认
- 或将恢复逻辑改为需要手动确认的步骤
- 验证工具（plutil / xcodebuild）使用绝对路径

## 六、通用原则

1. **小步验证**：每次改动后立即构建验证，不要累积多个改动再一起验证
2. **善用 `git checkout`**：pbxproj 修改出问题时，立即恢复到已知良好状态，不要尝试手动修补损坏的文件
3. **参考已有模式**：新增 HostService 时，先读已有的 Service 实现（如 `InstallerService`、`SigningService`），理解其模式后再动手
4. **先读后写**：在编辑文件前，先用 `read_file` 确认文件当前内容，避免基于过时信息编辑
5. **config 与实际文件保持一致**：创建 config 元数据文件（如 `.config.plist`）时，如果 config 引用了其他文件（如默认 keymap），应同时创建这些被引用文件，否则后续读写操作会因文件不存在而失败
6. **目录扫描排除元数据文件**：扫描目录中的 plist 文件时，显式排除 `.config.plist` 等元数据文件，不能仅依赖 `.skipsHiddenFiles`（文件可能不以 `.` 开头）

## 七、NWConnection / 网络层陷阱

### 7.1 `filter` 条件反转 — removeConnection bug

`RegistrationListener.removeConnection()` 中的过滤逻辑：

```swift
// 错误 ❌ — 保留了匹配的连接，删除了不匹配的
activeConnections = activeConnections.filter { $0.value === connection }

// 正确 ✅ — 删除匹配的连接
activeConnections = activeConnections.filter { $0.value !== connection }
```

**表现**：runtime 断连后 session 不会从 `activeConnections` 中移除，registry 状态也不会更新为 `.disconnected`，导致后续命令依然尝试使用已断开的 session（进而超时失败）。

**教训**：`filter` 的语义是"保留满足条件的元素"，要移除特定元素时条件应取反。写完后立刻用单元测试验证断连行为。

### 7.2 removeStaleSessions() 无调用方

`SessionRegistry.removeStaleSessions()` 在 S01 中就已实现，但直到 S05 才发现它从未被任何定时器或后台任务调用。**仅实现方法不等于功能生效**——必须在适当位置（启动路径或后台监控）中调用它。

S05 创建了 `SessionHealthMonitor` 类封装定时调用逻辑，但未在 `main.swift` 中集成（留给后续正式上线时启用）。
