## 总体技术路线

## 文档职责

本文只描述 `SemanticsValidation` 的**分层模型、层间关系、方法约束、止损规则与推荐产物**。

**任务状态、进展、优先级、TODO、完成判定与默认执行顺序统一只在 `00-Dashboard.md` 维护。** 本页不重复动态控制面信息。

## 目标

本目录的目标是把 `SemanticsValidation` 收口成一套**offline-first、报告优先、按需升级**的验证体系，用来回答两类问题：

1. 当前差异更像 compare 口径问题、compile posture 问题，还是 `IRToMSLConverter` / 参数建模 / emission 的真实实现问题
2. 本轮修改有没有在单 case 与 full-batch 上带来统计收益，且没有制造新的高风险回归

这套分层模型用于组织证据、解释问题与约束方法，不用于承载任务进展。

## 基本约束

- 任何默认流程都不应把 GUI、人工登录、工作区外修改、人工批量枚举样本或人工准备环境写回日常方法
- 日常构建、调试、测试、验证应优先保持为 agent 可独立完成的命令链路
- 结构化报告应优先作为事实载体；描述文字只能辅助解释，不能替代报告本身
- 高层验证用于补充低层证据，不能反向替代低层职责
- **涉及 PlayCover 构建、重建、安装时，必须优先使用 `BuildScripts/` 的标准脚本**
- **不要把 `xcrun metal -c` 的结果直接当作 runtime compile 真值；涉及 aggregate / runtime-like compile 时，优先使用 `Scripts/aggregate_replay_runner.py --compile-backend mtl-device`**

## 分层模型（背景参考）

### L1：IR Round-trip 结构验证

目标：建立最小闭环：

```text
module.ll
-> IRToMSLConverter
-> generated.metal
-> SharedCompilePlanner 驱动的 Metal compile
-> generated.air
-> llvm-dis
-> regenerated.ll
```

L1 回答的问题：

- 哪些样本能完成 round-trip
- 哪些样本卡在生成 MSL、Metal 编译或反汇编阶段
- compile posture 最终落成了什么 CLI 参数
- 哪些样本可以继续进入结构比较

L1 提供的是**闭环能力、失败分层与 compile posture 证据**，不是语义证明。

### L2：Canonical Compare + 风险分级

目标：把“文本 diff”升级为“结构化 compare + 风险分级 + gate 决策”。

重点比较：

- entry 集合与 shader 类型
- 参数 / 返回摘要
- 地址空间
- builtin / resource 使用
- CFG 粗结构
- instruction family 分布
- fast-math / compile posture / 关键属性

L2 提供的是**批量可运行、可解释、可回归的语义风险筛查器**。

### L3：最小行为测试

目标：在少量高价值样本上建立“固定输入 -> 固定输出”的自动验证。

默认方法约束：

- compute-first
- 必要时 render-second
- 仍然保持本地、离屏、可脚本化、无 GUI
- 通过 `gate-summary.json` 的 `layeredDecision` 驱动候选选择

L3 是**按需启用的补充证据层**，不是默认验证入口。

### L4：真实场景验证

目标：在真实 shader、真实 `.gputrace`、真实 app 场景中做最终后置确认。

L4 解决的是：

- 低层证据是否足以解释问题
- 某些问题是否只能在 runtime / live 条件下暴露
- replacement / `.gputrace` / render 结构是否真正命中

L4 是**最后升级的专项证据层**，不是默认主战场。

## 使用原则（背景参考）

### 1. 先看结构化报告，再决定下一步验证层级

当前默认从以下报告开始理解问题：

- `roundtrip-summary.json`
- `compile-summary.json`
- `compare-summary.json`
- `risk-report.json`
- `gate-summary.json`

如果问题已经能在这些结构化事实里被解释，就不需要升级到更高层。

### 2. 先单 case，再 full-batch

任何实现修改都应先回答：

- 单个代表样本是否命中新问题
- full-batch 风险数量是否下降
- 是否出现新的 `L3` / blocked 回归

### 3. 先单模块，再按需升级到 aggregate runtime-like compile

默认路径是单模块 `round-trip -> compare -> risk -> gate`。

只有当问题明确涉及以下任一情况时，才补多模块 aggregate 证据：

- compile posture 在 aggregate 形态下才暴露
- 多模块顺序 / dedupe / preflight 会影响结果
- 需要更贴近 `MTLDevice.newLibraryWithSource(...)` 的 runtime-like compile 结论

这类问题默认优先使用：

- `Scripts/aggregate_replay_runner.py --compile-backend mtl-device`

### 4. 先自动化，再人工兜底

任何验证路径都应优先证明：

- 可以本地执行
- 可以脚本化
- 可以稳定落盘
- 不需要用户频繁介入

### 5. 先复用已采集样本，再考虑新增样本

样本优先顺序应是：

1. 固定代表集 / 内置测试样本
2. 本地已存在的 `ShaderCorpus`
3. 本地已导出的 `ShaderSourceDiagnostics`
4. aggregate replacement 样本
5. 仅在必要时新增更高成本样本

## 与现有工作流的关系

`SemanticsValidation` 提供的是一条更早暴露问题、且更容易批量复跑的离线证据支路：

```text
module.ll
-> round-trip
-> compare
-> risk grading
-> gate decision
```

对于 aggregate / runtime-like compile 问题，补充支路是：

```text
replacement modules
-> aggregate.generated.metal
-> aggregate_replay_runner.py --compile-backend mtl-device
-> aggregate compile summary / report
```

这两条支路当前的职责，都是帮助更快发现、解释并回归 `ShaderCorpus` / `ShaderSourceDiagnostics` 里的 blocker；它们本质上是**方法标准与证据层级**，不是任务进展本身。

## 推荐产物结构

```text
build/
  semantics-validation/
    roundtrip/
      <preset-or-run>/
        replay-summary.json
        compile-summary.json
        roundtrip-summary.json
        compare-summary.json
        risk-report.json
        high-risk-samples.json
        gate-summary.json
        preset-manifest.json
        generated-sources/
    behavior/
      <run>/
        behavior-summary.json
  shader-aggregate-replay/
    <run>/
      aggregate-replay-summary.json
      _internal/
      <bundle-or-replacement>/
        aggregate.generated.metal
        *.compile.json
```
