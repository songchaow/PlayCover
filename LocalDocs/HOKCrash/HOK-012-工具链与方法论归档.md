## 工具链总览

HOK-012 分三层：

- **HOK-012-A（诊断 env 注入）**：`PlayApp.effectiveLaunchEnvironment()`
  与 `LaunchService.effectiveLaunchEnvironment()` 两侧对
  `minimalStartupCompatBundleIdentifiers` 注入
  `DYLD_PRINT_INITIALIZERS=1` + `DYLD_PRINT_APIS=0`；两处共用
  `minimalStartupCompatDiagnosticEnvironment` 常量。
- **HOK-012-B（LLDB 自动化扩展）**：`LLDBRunOptions` 类型
  （`watchAddress` / `watchSize` / `preRunCommands` /
  `dyldInitializersLogPath` / `deferWatchpointInstall` /
  `teardownTimeoutSeconds`）贯穿 `LaunchService.launchAppWithLLDB` →
  `runLLDBHeadless` → `launch_app_with_lldb` MCP schema →
  `Scripts/hok006_ngr_lldb_runner.py` CLI；watchpoint 模式下
  `parseLLDBEvidence` 优先挑选非 watchpoint stop 作为 fault 字段，
  `parseWatchpointHits` 把每段 `stop reason = watchpoint …` 切成带
  `oldValue`/`newValue`/`frame #0`/`backtrace` 的结构化 `WatchpointHit`；
  watchpoint 模式子进程 stderr 用 `process launch -e <path>` 重定向到
  独立 dyld log 文件。
- **HOK-012-C（实战与证据口径）**：在真实 NGR 环境上跑四种 live run
  形态（legacy baseline / pre-run watchpoint / deferred-install
  watchpoint / deferred-install + SIGABRT 拦截 + sheet modal 拦截 +
  b.0 对话框 gate），为后续 HOK-013/014 提供"slot 当前值 / writer bp
  hit / 污染检测"的直接证据。

## HOK-012-C：三种 run 的角色分工

- **legacy baseline**：`python3 Scripts/hok006_ngr_lldb_runner.py
  --skip-build-install`，不传 `--watch-address`，走 HOK-006 的
  stop→quit 路径。用于确认一次"app 是否跨过原 faulting window / 当
  轮是否出现新 `.ips`"。
- **pre-run watchpoint**：`python3 Scripts/hok006_ngr_lldb_runner.py
  --watch-address 0x10e2146f8 --watch-size 8 --skip-build-install`，
  脚本自动把 `DYLD_PRINT_INITIALIZERS=1` 子进程 stderr 重定向到
  `build/hok-012-ngr-dyld-initializers.log`、在 `run` 前装
  `watchpoint set expression -s 8 -- 0x10e2146f8`、每次 watchpoint
  stop 抓 backtrace 后 `continue`，累计多次命中写入
  `build/hok-012-ngr-watchpoint-report.json`。
- **deferred-install watchpoint**：`--defer-watchpoint-install` 额外加
  `breakpoint set --address <writer> -C "watchpoint set expression -s 8
  -- 0x10e2146f8" -C "continue" --auto-continue true --one-shot true`
  到 `preRunCommands`（`--writer-address` 默认 `0x103a29b7c`）。
  watchpoint 只在 writer 函数入口 bp 命中后才装入，消除 pre-run 装入
  与 child dyld 接管之间的 race。

## 对话框污染 gate（HOK-012-C.3-b.0）

`com.tencent.ngr` 启动期会通过 `NSAlert` 以 sheet modal 形式 attach
到 parent window，backtrace 链：`-[NSAlert beginSheetModalForWindow:
completionHandler:]_block_invoke` → `-[NSWindow
_beginWindowBlockingModalSessionForSheet:service:completionHandler:
isCritical:]` → `-[NSApplication _orderFrontModalWindow:
relativeToWindow:]` → `-[NSWindow(NSSheets) _orderFrontRelativeToWindow:]`
→ `-[NSWindow orderFront:]`。sheet 的 `windowLayer=0` 是 sheet 特征。
sheet 一旦 order front，UI 线程进入 sheet modal session、其它线程
继续跑但永不前进——transcript 看似"健康"、所有 slot/bp/watchpoint
读数都是冻结态快照。

**判据**：`evidence.blockingDialogWindows.isEmpty == false` 为 hard-fail，
本轮证据视为 invalid。

实现（`LaunchService.runLLDBHeadless` 收尾阶段）：

1. 解析 transcript 得到 child inferior PID（`parseProcessIdentifier`）；
2. `/bin/ps -axo pid=,ppid=` 做闭包得到子进程孙进程全集（NGR 会派生
   helper XPC 服务，光看 direct child 不够）；
3. `CGWindowListCopyWindowInfo(.optionOnScreenOnly |
   .excludeDesktopElements, kCGNullWindowID)` 枚举 on-screen 窗口，过
   滤 `ownerPID ∈ descendants` + `alpha ≥ 0.05`；
4. 对 descendants 里仍 alive 的 PID 调 `kill(pid, SIGKILL)`，记录
   `residualProcessesKilled`；
5. `LLDBLaunchEvidence` 新增 `blockingDialogWindows: [BlockingDialogInfo]`
   / `residualProcessesKilled: [Int32]` 字段；`launch_app_with_lldb`
   JSON response 透出；Python runner `determine_overall_pass` 在
   `blockingDialogDetected=True` 时强制 `overallPass=False`、exit 非零。

注意：b.0 gate 只检测"窗口是否属于 NGR descendants + onscreen"，**不
区分 sheet vs 主游戏窗口**。在 app 启动成功后 `blockingDialogs` 会因为
主游戏窗口本身存在而 >=1——这是 gate 的语义边界，**不**代表 app 崩了。
HOK-014 之后的正确读法：结合 window size 与 ownerPID 关系判断是不是
sheet（sheet 典型 260×204，主窗口 1478×859）。

## SIGABRT 拦截下 abort-stop 的自动证据采集（HOK-012-C.3-b.1/b.2）

`runLLDBHeadless` 对每一次新出现的 `stop reason =` 行做分流：

- 行内含 `"watchpoint "` 字样：继续走 legacy `thread backtrace` +
  `frame variable` + `continue`。
- 行内不含 `"watchpoint "` 字样（SIGABRT / sheet modal bp 命中 /
  其它 breakpoint）：改发 `thread backtrace all` + `frame variable` +
  `memory read -fx -s 8 -c 1 <watchAddress>`（仅 watchAddress 非空）+
  `breakpoint list` + `watchpoint list` + `kill` + `quit`。

这套序列执行时间超过 legacy 2.0s 收尾窗口，由
`LLDBRunOptions.teardownTimeoutSeconds` 参数化（默认 2.0 保持 legacy，
defer 模式由 `hok006_ngr_lldb_runner.py` 自动拉到 6.0s；
`--teardown-timeout` 可手工指定）。

**两条硬性约束**：

1. **`memory read` 必须显式 `-fx`**：不带 format 的
   `memory read -s 8 -c 1 <addr>` 与 LLDB 默认 `bytes/bytes with ASCII`
   模式冲突，LLDB 返回 `error: display format ... conflicts with the
   specified byte size 8` 并静默丢弃——transcript 看似"命令被发出"，slot
   值其实没落到证据里。正确命令是 `memory read -fx -s 8 -c 1 <addr>`。
2. **尾部发 `kill\nquit`，不发 `continue`**：`continue` 会让 app 跑到
   `-[NSWindow orderFront:]` 把 sheet 订上屏幕污染 b.0 gate；SIGABRT
   stop 发 `continue` 也不会得到有用 `.ips`（UE4 fatal 路径会被 Apple
   对话框挂住 UI 线程）。`kill\nquit` 让 LLDB 自己杀 process + 退出会
   话，收敛于 `blockingDialogs=0 residualPIDsKilled=0` 的干净 run。

## sheet modal 拦截 bp 的覆盖面（HOK-012-C.3-b.3）

`preRunCommands` 里追加三条拦截 bp：

- `breakpoint set --name "-[NSWindow orderFront:]"`：主力。sheet modal
  最终要 order 自己进入 parent window overlay，必经
  `-[NSWindow orderFront:]`。
- `breakpoint set --name "-[NSApplication runModalForWindow:]"`：
  top-level modal window 路径的冷备。sheet modal 不走这个入口；作为
  最快的"显式 modal"探针保留。
- `breakpoint set --name CGSOrderWindow`：CoreGraphics 实际 order
  window 的入口（macOS 上 re-export 到 `SkyLight.SLSOrderWindow`）。
  作为 AppKit 私有 API 被绕开时的最后一道冷备。

SIGABRT 拦截生效时（见上节）app 可能在 sheet order front 之前就
`abort()` 了，这三条 bp 的 `hit=0` 是正常且期望的。它们是冷备保险丝，
在换条代码路径或新 build 让 sheet 先于 abort 到达时，是唯一能拦住
sheet order front、避免 b.0 gate 污染的防线。

## 相关脚本与工具

- `Scripts/hok006_ngr_lldb_runner.py`：唯一的 CLI 入口。默认写
  `build/hok-012-ngr-watchpoint-report.json` +
  `build/hok-012-ngr-dyld-initializers.log`。详细 CLI 清单见附录。
- `PlayCoverMCP/HostServices/Launch/LaunchService.swift`：
  `LLDBRunOptions` / `WatchpointHit` / `parseWatchpointHits` /
  `parseLLDBEvidence`（fault vs watchpoint 分流）/ abort-stop handler
  / `blockingDialogWindows` + `residualProcessesKilled` 字段定义。
- `PlayCover/Model/PlayApp.swift` /
  `PlayCoverMCP/HostServices/Launch/LaunchService.swift`：
  `minimalStartupCompatDiagnosticEnvironment` 两侧必须保持同值；任何
  对 `DYLD_PRINT_INITIALIZERS` / `DYLD_PRINT_APIS` 的改动要两侧对齐，
  否则 `launch_app` 和 `launch_app_with_lldb` 会写出不同环境的子进程
  stderr。
