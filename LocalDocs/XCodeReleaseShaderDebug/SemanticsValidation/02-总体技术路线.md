## 总体技术路线

## 目标

在不打乱当前 offline-first 工作流的前提下，为“语义验证”新增一条分层、渐进、可止损的测试体系。

核心思想：

- **不追求一步到位**
- **先建立离线证据，再逐步增加行为与真实场景证据**
- **最终做到哪一层，由当时的人力余量决定**

## 四层模型

### L1：IR Round-trip 结构验证

目标：建立最小闭环：

```text
IR -> MSL -> AIR -> IR
```

回答的问题：

- 当前链路能不能把 `module.ll` round-trip 回 `regenerated.ll`
- 哪些样本在 round-trip 的编译阶段就失败
- 哪些样本可以继续进入结构比较

这是本专项最优先、最基础的一层。

### L2：Canonical Compare + 风险分级

目标：不再只看文本 diff，而是比较：

- entry 函数集合
- shader 类型
- 参数/返回类型摘要
- 地址空间
- builtin / resource 使用
- CFG 粗结构
- instruction family 统计
- 关键 attribute / fast-math 语义点

输出不应只是“same/diff”，而应分级：

- **L0**：几乎一致 / 低风险
- **L1**：存在非关键差异 / 可接受
- **L2**：存在需要人工复核的差异
- **L3**：关键语义面明显不一致

### L3：最小行为测试

目标：在少量高价值样本上建立“固定输入 → 固定输出”的自动验证。

推进顺序：

1. **compute-first**：最容易自动化
2. **必要时补离屏 render**：覆盖 vertex/fragment 的关键路径

这一层的意义是：

- 把“结构相近”推进到“行为更可信”
- 对历史高风险 lowering 模式形成回归样本

### L4：真实场景验证

目标：在真实 shader / 真实 capture / 真实 app 上做最终后置验证。

这一层默认只在下面任一情况启用：

- L1/L2/L3 已基本收敛，需要真实确认
- 某类问题只有 `.gputrace` / live 渲染结构才能暴露
- 新修复影响 runtime/library replacement 主链路

默认使用自动化脚本 / MCP；若必须人工介入，需先取得用户确认。

## 推进顺序

### 阶段 P0：现状定稿

已完成：

- 现状调研
- 缺口确认
- 分层模型成型

对应：`SV-000`

### 阶段 P1：打通 round-trip 主链路

交付目标：

- 新增离线 round-trip runner
- 先对 `test-data/` 跑通
- 产出第一版结构化 JSON 报告

当前状态：**已完成。**

对应：`SV-001`

### 阶段 P2：把结构比较从“文本 diff”升级为“风险分级”

交付目标：

- 新增 IR canonical summary
- 对 round-trip 结果做风险分类
- 在 `test-data/` 形成首批基线
- 挑少量 `ShaderCorpus` 样本试跑

当前状态：

- `SV-002`：**已完成**
- `SV-003`：**进行中**

这意味着当前阶段的 active work 已经不是“继续发明 compare 指标”，而是：

- 用 `--preset test-data-representatives / test-data-batch` 固化 `test-data` 默认 gate
- 用 `--preset local-corpus-representatives` 固化一小组**已有本地样本**的代表性 `ShaderCorpus` 入口
- 用 `--preset daily-default` 把 quick gate 收口成单命令默认入口
- 用 `gate-summary.json` / `--gate-profile` / `--enforce-gate` 把已知 baseline 变成可执行的 pass / warn / fail 判定
- 继续让 L2 报告真正变成后续任务的分流器

对应：`SV-002`、`SV-003`

### 阶段 P3：补最小行为测试

交付目标：

- 建立 compute-first 行为测试 harness
- 选 5~10 个高风险 lowering 模式做首批行为样本
- 对关键样本形成稳定 oracle

当前状态：**未开始，必须等待 `SV-003 / SV-006` 收敛后再进入主线。**

对应：`SV-004`

### 阶段 P4：收口真实场景验证

交付目标：

- 明确默认代表集
- 明确进入 L4 的前置条件
- 把 `.gputrace` / render-diff / MCP live 使用场景收口为后置 gate

当前状态：**未开始，保持后置。**

对应：`SV-005`

## 预算与止损策略

### 人力余量较低时

优先做到：

- **L1 完整落地**
- **L2 第一版 summary compare**
- **`SV-003` 的 `test-data` 默认 gate 固化**

此时已经能显著提高“语义风险可见度”，也是当前最现实、最高性价比的停点。

### 人力余量中等时

继续做到：

- L2 风险分级完善
- 接入代表性 `ShaderCorpus`
- 建立明确的升级/止损规则（`SV-006`）
- 建立最小 compute 行为测试

这是推荐的“中期完整度”目标。

### 人力余量充足时

再补：

- 更丰富的行为样本
- 离屏 render 行为测试
- 真实场景自动化验证
- 必要时更深一层的 canonical compare / AST compare / ISA 验证

## 与现有工作流的关系

现有主回路仍然成立：

```text
真实样本采集
  ↓
导出 corpus
  ↓
离线 replay / compile / diff
  ↓
少量 live 复测
```

本专项新增的是一条**更深一层的离线语义验证支路**：

```text
module.ll
  ↓
round-trip
  ↓
canonical compare
  ↓
risk grading
  ↓
（必要时）behavior test
  ↓
（必要时）real-scene validation
```

它不是替代现有 E-005/E-006，而是让“语义风险”在更早、更自动化的阶段暴露出来。

补充约束：

- 若前置任务仍在处理更靠前的运行时 blocker，这里应优先提供更强的离线证据，而不是过早把默认流程切到 live
- `SV-003` 默认只复用本地已有 `test-data/` 与 `ShaderCorpus`；若缺样本，不应自动升级为需要用户介入的 fresh capture 流程

## 当前推荐的默认 gate

### 必须优先满足

- `SV-001` 的 round-trip 能稳定跑 `--preset test-data-representatives --allow-failures --enforce-gate`
- `SV-002` 能对 `test-data-representatives / test-data-batch / local-corpus-representatives` 生成结构化 compare 报告
- 代表 preset 能继续产出 `gate-summary.json`，并在 `--enforce-gate` 下仅对新增回归执行阻断
- `Scripts/test_ir_canonical_compare.py`、`Scripts/test_ir_semantics_roundtrip_runner.py` 保持通过
- 默认优先使用固定输出目录：
  - `build/semantics-validation/roundtrip/test-data-representatives/`
  - `build/semantics-validation/roundtrip/test-data-batch/`
  - `build/semantics-validation/roundtrip/local-corpus-representatives/`
  - `build/semantics-validation/roundtrip/daily-default/`
- 若改动触及 `IRToMSLConverter`，应补一次 `FORCE_PLAYTOOLS_REBUILD=1 ./BuildScripts/sync_playtools_xcframework.sh`

### 可以作为第二阶段 gate

- `python3 Scripts/ir_semantics_roundtrip_runner.py --preset test-data-batch --allow-failures`
- `python3 Scripts/ir_semantics_roundtrip_runner.py --preset local-corpus-representatives --allow-failures`
- 最小 compute 行为测试通过

### 不应作为默认日常 gate

- 需要用户反复介入的 live 流程
- 高成本 GUI 操作
- 手动打开 Xcode 的视觉确认
- 工作区外分析
- 因缺少现成样本就要求用户协助准备环境

### 样本建议

- `test-data/`：最小模式覆盖
- `ShaderCorpus/`：真实样本代表集
- 本目录后续若需新增专门样本选择策略，可另开子文档维护
- 首轮基线与历史细节下沉到 `07-首轮基线与历史进展归档.md`

## 当前结论

当前最优技术路线不是直接冲向 L4，而是：

1. **先把 L1/L2 的既有能力收口成稳定日常 gate（`SV-003`）**
2. **把升级/止损规则写清楚（`SV-006`）**
3. **再按预算决定是否推进 L3/L4**

这条路线最符合当前仓库的工具现状，也最能保证 agent 自主推进时对用户依赖最低。
