## 总体技术路线

## 目标

在不打乱当前 offline-first 工作流的前提下，为“语义验证”新增一条分层、渐进、可止损的测试体系。

核心思想：

- **不追求一步到位**
- **先建立离线证据，再逐步增加行为与真实场景证据**
- **最终做到哪一层，由当时的人力余量决定**

补充约束：

- 当前控制面事实应以结构化报告为准；更细的事实优先级、preset / manifest / baseline 契约与自动化前置条件统一见 `08-当前代表集与Gate契约参考.md`（工作参考，当前主线推进**不必须读取**）
- 任何新路线若会把 GUI、人工登录、工作区外修改、人工批量枚举样本或人工准备环境重新写回日常验证，就不应进入默认主线

## 四层模型

### L1：IR Round-trip 结构验证

目标：建立最小闭环：

```text
IR -> MSL -> AIR -> IR
```

回答的问题：

- 当前链路能不能把 `module.ll` round-trip 回 `regenerated.ll`
- 哪些样本在 round-trip 的编译阶段就失败
- 哪些样本可以继续进入结构比较

这是本专项最优先、最基础的一层。

### L2：Canonical Compare + 风险分级

目标：不再只看文本 diff，而是比较：

- entry 函数集合
- shader 类型
- 参数/返回类型摘要
- 地址空间
- builtin / resource 使用
- CFG 粗结构
- instruction family 统计
- 关键 attribute / fast-math 语义点

输出不应只是“same/diff”，而应分级：

- **L0**：几乎一致 / 低风险
- **L1**：存在非关键差异 / 可接受
- **L2**：存在需要进一步复核或升级验证的差异
- **L3**：关键语义面明显不一致

### L3：最小行为测试

目标：在少量高价值样本上建立“固定输入 → 固定输出”的自动验证。

推进顺序：

1. **compute-first**：最容易自动化
2. **必要时补离屏 render**：覆盖 vertex/fragment 的关键路径

这一层的意义是：

- 把“结构相近”推进到“行为更可信”
- 对历史高风险 lowering 模式形成回归样本

### L4：真实场景验证

目标：在真实 shader / 真实 capture / 真实 app 上做最终后置验证。

这一层默认只在下面任一情况启用：

- L1/L2/L3 已基本收敛，需要真实确认
- 某类问题只有 `.gputrace` / live 渲染结构才能暴露
- 新修复影响 runtime/library replacement 主链路

默认使用自动化脚本 / MCP；若必须人工介入，需先取得用户确认。

## 预算与止损策略

### 人力余量较低时

优先做到：

- **L1 完整落地**
- **L2 第一版 summary compare**
- **`SV-003` 的 `test-data-representatives` 硬默认 gate 固化**
- **`SV-003F` 至少把当前 `ShaderCorpus` 全量样本纳入可自动执行的离线路径**

此时已经能显著提高“语义风险可见度”，也是当前最现实、最高性价比的停点。额外约束是：默认 gate 必须仍可由 agent 自主完成，不能把用户配合、fresh capture、权限交互或人工批量整理路径带回主路径。

### 人力余量中等时

继续做到：

- failure-path `ShaderSourceDiagnostics` 样本也能以**agent 可自主执行**的形式进入 L1/L2
- 建立明确的升级/止损规则（`SV-006`）
- 从稳定结果里挑极少量样本建立最小 compute 行为测试
- 仅在仍有高价值 fragment 候选时，评估是否要补最小 render-second

这是推荐的“中期完整度”目标。

### 人力余量充足时

以下只作为远期参考，**不构成当前 TODO**：

- 更丰富的行为样本
- 离屏 render 行为测试
- 真实场景自动化验证
- 必要时更深一层的 canonical compare / AST compare / ISA 验证

## 与现有工作流的关系

现有主回路仍然是“真实样本采集 → 导出 corpus → 离线 replay / compile / diff → 少量 live 复测”。

本专项新增的是一条**更早暴露语义风险的离线验证支路**：`module.ll → round-trip → canonical compare → risk grading → （必要时）behavior test → （必要时）real-scene validation`。

它不是替代现有 E-005/E-006，而是在更低成本、更自动化的阶段提前暴露风险。

补充约束：

- 若前置任务仍在处理更靠前的运行时 blocker，这里应优先提供更强的离线证据，而不是过早把默认流程切到 live
- `SV-003F` 当前只应复用**本地已存在**的 `test-data/`、`ShaderCorpus` 和 failure-path 导出产物；若某条路径还需要用户协助才能成立，就不能先写成默认主线
- 若后续新增 render-second，也应先证明它仍属于本地、离屏、自动化优先的 L3，而不是提前把 L4 的人工成本引回来

## 当前推荐的默认 gate

### 必须优先满足

当改动涉及离线语义验证脚本、preset / gate profile / report contract 或 `IRToMSLConverter` 时，默认优先满足：

- `Scripts/test_ir_canonical_compare.py`、`Scripts/test_ir_semantics_roundtrip_runner.py` 保持通过
- `SV-001` 的 round-trip 能稳定跑 `--preset test-data-representatives --allow-failures --enforce-gate`
- `SV-002` 能对代表 preset 生成结构化 compare 报告
- `SV-003F` 能继续对已采集 `ShaderCorpus` 样本执行批量 `roundtrip / compare / risk`
- `daily-default` / `local-corpus-representatives` 需要继续作为参考入口存在，但不应反向定义当前最高优先级
- 若改动触及 `IRToMSLConverter`，应补一次 `FORCE_PLAYTOOLS_REBUILD=1 ./BuildScripts/sync_playtools_xcframework.sh`

推荐默认顺序：

1. **跨机器硬默认**：先保持 `Scripts/test_ir_canonical_compare.py`、`Scripts/test_ir_semantics_roundtrip_runner.py` 通过，再执行 `python3 Scripts/ir_semantics_roundtrip_runner.py --preset test-data-representatives --allow-failures --enforce-gate`
2. **当前最高优先级本机主线**：执行 `python3 Scripts/ir_semantics_roundtrip_runner.py --corpus-root ~/Library/Containers/io.playcover.PlayCover/ShaderCorpus --allow-failures`
3. **failure-path 定向补充**：仅在已有明确 blocker 样本、且无需人工批量整理路径时，才执行 `python3 Scripts/ir_semantics_roundtrip_runner.py --ll <path_to_failure_module.ll> --allow-failures`
4. **L3/L4 后置能力**：只在前面三步仍不足以支撑判断时，才回到 `05-L3-最小行为测试.md` 或 `06-L4-真实场景验证.md`

只要前两步已经稳定给出“代表 gate 无新增回归 + 全量已采集成功样本继续可批量进入 L1/L2”这组边界，本轮日常语义验证闭环就视为完成；默认不再为了覆盖率抢跑 L3/L4。

### 可以作为第二阶段 gate

- `local-corpus-representatives`、`test-data-batch` 与 `SV-004F` 白名单行为路径都继续保留，但职责是补充证据或后置升级，而不是替代当前主线
- 对当前 failure-path 样本，优先使用 `--diagnostics-root` 做**批量补充验证**，必要时再以显式 `--ll` 做**定向复核**；它不应被提升成日常默认 gate
- 必要时使用 `./BuildScripts/build_and_install.sh` 进行运行时链路验证；默认保持脚本自带的 `user` 安装模式，不主动切到可能触发 `sudo` 的 `auto/system`

### 不应作为默认日常 gate

- 需要用户反复介入的 live 流程
- 高成本 GUI 操作
- 手动打开 Xcode 的视觉确认
- 工作区外分析
- 因缺少现成样本就要求用户协助准备环境
- 跳过现有 `--diagnostics-root` 入口，转而让用户人工批量枚举 `ShaderSourceDiagnostics` 里的样本路径

## 当前结论

当前最优技术路线不是直接冲向 L3/L4，而是：

1. **先持续守住 `SV-003` 的默认 gate 不回退**
2. **把 `SV-003F` 收口为“全量已采集样本尽可能进入 L1/L2”的唯一实际执行面**
3. **在这条路径仍保持 automation-first 的前提下，优先吃进 `ShaderCorpus`，再补齐 failure-path 样本入口**
4. **只在 L1/L2 全量样本证据仍不足时，最后才考虑 `SV-004 / SV-005`**

这条路线最符合当前仓库的工具现状，也最能保证 agent 自主推进时对用户依赖最低。
