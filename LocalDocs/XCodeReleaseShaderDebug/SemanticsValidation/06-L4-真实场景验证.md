## L4：真实场景验证

## 目标

在 L1/L2/L3 已提供较充分离线证据后，用真实 shader、真实 `.gputrace`、真实 app 场景做**最终后置验证**。

这层的核心问题不是“能不能跑”，而是：

- 何时值得启用
- 默认如何自动化
- 哪些情况下必须停下来征求用户确认

补充定位：

- L4 是**后置 gate**，不是当前默认主战场
- 若前置任务仍在处理更靠前的运行时 blocker，这里只保留语义验证视角下仍然必要的 L4 规则，不抢跑 live
- 若只是推进当前主线，这份文档当前**不必须读取**；只有在正式进入 live / `.gputrace` 验证时才需要细读

## 启用前提

默认只有在以下任一条件满足时，才进入 L4：

1. L1/L2 已基本收敛，需要真实确认
2. 某类问题只会在真实 runtime / `.gputrace` / render 结构中暴露
3. 本轮改动直接影响 runtime replacement 主链路
4. L3 行为测试无法覆盖该风险面

补充约束：

- 若本机没有现成 app / capture / corpus 条件，不得自动把“用户协助准备环境”写成默认 gate
- 若当前目标只是日常离线回归，应停在 L1/L2 或 L3，不应为做 L4 强行扩大流程

## 默认工具

优先使用已存在的自动化工具：

- `Scripts/check_gputrace_sources.py`
- `Scripts/compare_capture_runs.py`
- `Scripts/e006d_render_diff.py`
- `Scripts/runtime_launch_diagnostics_summary.py`
- PlayCover MCP 能力（如 `launch_app` / `create_session` / `capture_metal_frame` / 输入事件）
- 必要时使用 `./BuildScripts/build_and_install.sh` 完成标准构建/安装；默认保持脚本自带的 `user` 安装模式，不主动切到可能触发 `sudo` 的 `auto/system`
- 若未来新增 L4 验证方法，必须优先保证它仍能以脚本 / MCP 方式由 agent 自主执行；否则它只能作为经用户确认的专项步骤，不能回流为日常 gate

## 默认验证顺序

### 第一步：先看源码与 replacement 闭环

优先确认：

- replacement 是否稳定命中
- `.gputrace` 是否能看到对应源码
- run 间输入与 replacement attempt 是否稳定

### 第二步：再看渲染结构

若源码可见、replacement 也命中，但仍怀疑行为差异，则进入：

- `compare_capture_runs.py`
- `e006d_render_diff.py`

优先比较：

- Command Buffer 数量
- Render Encoder 结构
- Pipeline State 摘要
- 关键 pass 差异

### 第三步：必要时再做更重的 live/GUI 分析

只有当自动化结构证据仍不够时，且已满足下文“用户确认规则”时，才考虑：

- Xcode GUI 自动化
- 更细粒度的 key pass details
- 更长链路的 live 对照

## 用户确认规则

以下情况**必须先得到用户确认**：

- 需要人工登录/摆场景/点击 UI
- 需要 GUI / Accessibility / `cliclick`
- 需要工作区外静态分析
- 需要修改工作区外文件或 app bundle
- 需要长时间占用机器做大规模 live 对照

执行前必须先把：

- 需要用户做什么
- 为什么必须做
- 能否进一步缩小步骤

说明清楚。

## 不应成为默认 gate 的内容

- 人工打开 Xcode 肉眼确认
- 依赖登录后的复杂场景摆放
- 需要用户反复点按钮
- 无脚本化的长链路 GUI 分析
- 因为当前机器缺少现成 live 条件，就要求用户协助补环境

这些都只能作为后置专项升级路径，而不能成为“日常验证必须做”的步骤。

## 推荐代表集策略

L4 不应该追求样本越多越好，而应该有一组小而稳定的代表集。

建议按两类维护：

### A 类：源码可见性 / replacement 闭环代表集

用于回答：

- 生成源码是否进入 `.gputrace`
- replacement 是否仍稳定

### B 类：渲染结构 / 行为敏感代表集

用于回答：

- 是否出现 render structure 偏移
- 是否出现关键 pass 差异

具体样本与 bundle 选择可以后续按项目进展维护，但不应让主 dashboard 膨胀。

## 完成标准

满足以下条件后，可认为 L4 已形成第一版流程：

1. 已明确 L4 的启用前提
2. 已明确哪些验证可以全自动完成
3. 已明确哪些情况必须先征求用户确认
4. 已形成至少一条自动化优先的后置验证路径
5. 主流程不会把用户人工操作写成默认 gate

## 与主线的关系

L4 的职责是：

- 做阶段性真实确认
- 为“离线语义验证是否足够可信”提供外部证据

L4 **不是**：

- 默认主战场
- 先于 L1/L2/L3 的入口
- 可以替代离线验证体系的捷径
