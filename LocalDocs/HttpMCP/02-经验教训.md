## 一、Xcode 工程文件（pbxproj）

### 1.1 三步验证铁律

**每次修改 pbxproj 后**必须执行：

```bash
# 步骤 1: 语法检查
plutil -lint PlayCover.xcodeproj/project.pbxproj

# 步骤 2: 变更审查
git diff PlayCover.xcodeproj/project.pbxproj

# 步骤 3: 编译验证
xcodebuild -scheme PlayCover -configuration Release build \
  -derivedDataPath /tmp/PlayCover-DerivedData \
  FASTLANE=1 CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES 2>&1 | tail -20
```

**不要跳过任何一步。** `plutil -lint` 只检查语法，`git diff` 确认改动范围，`build` 验证语义正确。

### 1.2 修改 pbxproj 优先用 replace_in_file

| 方式 | 推荐度 | 原因 |
|------|:------:|------|
| `replace_in_file` 多行精确匹配 | ✅ 首选 | 可包含上下文，精确定位到正确 section |
| Python 脚本 `str.replace()` | ⚠️ 慎用 | 同一 ID 在多个 section 出现，容易替换到错位置 |
| 手动编辑 | ❌ 禁止 | 格式极其严格，空格/缩进错误即导致不可解析 |

pbxproj 修改需要在 **4 个 section** 分别操作：
1. `PBXBuildFile` — 添加构建文件条目
2. `PBXFileReference` — 添加文件引用
3. `PBXGroup` — 在 `children` 列表中插入引用
4. `PBXSourcesBuildPhase` — 在 `files` 列表中插入构建文件

### 1.3 Target membership 同步规则

新增 `.swift` 文件时，必须根据 Target 归属矩阵添加到所有需要的 target：

| 文件类型 | PlayCover (GUI) | PlayCoverMCP (CLI) | PlayCoverMCPTests |
|---------|:-:|:-:|:-:|
| 通用 MCP 业务文件 | ✅ | ✅ | ✅ |
| GUI 专属文件（View / Manager） | ✅ | ❌ | ❌ |
| CLI 专属文件（main.swift 等） | ❌ | ✅ | ❌ |
| 测试文件 | ❌ | ❌ | ✅ |
| **Hummingbird 依赖文件（StreamableHTTPTransport 等）** | **✅** | **❌** | **❌** |
| **无外部依赖的工具文件（SSEEncoder、MCPSessionManager）** | **✅** | **✅** | **✅** |

> ⚠️ PlayCoverMCPTests 直接编译源文件，不链接 framework。因此每个需要测试的文件必须在 Tests target 有独立的 PBXBuildFile 条目。

### 1.4 首次引入 SPM 对 pbxproj 的影响

本项目首次使用 SPM（添加 Hummingbird），会在 pbxproj 中新增以下 section：

| Section | 作用 |
|---------|------|
| `XCRemoteSwiftPackageReference` | SPM 包的 URL 和版本约束 |
| `XCSwiftPackageProductDependency` | 引用的具体 product |
| `packageReferences` | 在 project object 中注册包引用 |
| `packageProductDependencies` | 在 target 中注册 product 依赖 |

这些由 Xcode "Add Package" 自动生成，手动修改风险极高。**推荐通过 Xcode 添加 SPM 包后再 `git diff` 审查变更。**

## 二、构建与签名

### 2.1 标准构建参数

所有构建命令必须包含以下参数：

```bash
FASTLANE=1                    # 跳过 Carthage Bootstrap 和 SwiftLint
CODE_SIGN_IDENTITY="-"        # ad-hoc 签名
CODE_SIGNING_REQUIRED=NO      # 跳过严格签名检查
CODE_SIGNING_ALLOWED=YES      # 允许 ad-hoc
-derivedDataPath /tmp/PlayCover-DerivedData  # 避免缓存污染
```

### 2.2 FASTLANE=1 跳过的与不跳过的 Build Phase

`FASTLANE=1` 通过 `if [[ -z "$FASTLANE" ]]` 条件，跳过以下 Build Phase 脚本：

| Build Phase | 是否被 FASTLANE=1 跳过 |
|-------------|:---------------------:|
| Carthage Bootstrap | ✅ 跳过 |
| SwiftLint | ✅ 跳过 |
| Copy Carthage frameworks | ❌ 仍执行（需 carthage 可用） |
| Codesign sparkle | ❌ 仍执行（已有 ad-hoc fallback） |

使用完整构建参数（`FASTLANE=1` + ad-hoc 签名），所有 Build Phase 均可正常通过，**BUILD SUCCEEDED 即为编译成功的判定标准**。

> 前提：环境中 carthage 已安装（`/opt/homebrew/bin/carthage`），且 `Carthage/Checkouts/` 目录已存在。首次 clone 仓库后需先运行一次 `carthage checkout`。

### 2.3 独立 DerivedData 必要性

Yams（Hummingbird 的间接依赖）仓库包含 Bazel 的 `BUILD` 文件。macOS 文件系统不区分大小写时，会与 Xcode 需要创建的 `build` 目录冲突。使用 `-derivedDataPath /tmp/PlayCover-DerivedData` 可绕过。

## 三、跨模块依赖

### 3.1 PlayCoverMCP ≠ PlayCover

`PlayCoverMCP` 是独立的 CLI target，**不链接 PlayCover framework**：

- ❌ 不能 `import PlayCover`
- ❌ 不能使用 `PlayTools`、`PlayApp`、`Entitlements` 等 GUI 类
- ✅ 通过 `Shell.run()` 调用系统命令实现功能

### 3.2 Hummingbird 的依赖隔离

Hummingbird + SwiftNIO 仅链接到 **PlayCover GUI target**：

- CLI target 不需要 HTTP 服务器（继续用 StdioTransport）
- Tests target 不需要 Hummingbird（SSEEncoder 和 MCPSessionManager 无外部依赖，可独立测试）
- `StreamableHTTPTransport.swift` 仅编译到 GUI target

### 3.3 SwiftNIO EventLoop vs GCD

| 层 | 线程模型 | 注意事项 |
|---|---------|---------|
| Hummingbird route handler | SwiftNIO EventLoop | 不可执行阻塞操作 |
| MCPServer.handle() | NSLock 保护 | 已线程安全，可在任何线程调用 |
| @Published 属性 | 必须在主线程 | 从 EventLoop 回到主线程用 `DispatchQueue.main.async` |

## 四、Swift / Foundation API 注意事项

### 4.1 plist 类型限制

`URL` 对象不是合法 plist 值。写入 plist 时用 `.path`（String），读取时用 `URL(fileURLWithPath:)` 转回。

### 4.2 URL 比较不可靠

用 `lastPathComponent` 比较文件身份，不要用 `==`（路径规范化方式不同可能导致 false negative）。

### 4.3 filter 语义是"保留"

```swift
// 删除特定元素 — 条件取反！
array = array.filter { $0 !== targetToRemove }
```

### 4.4 WMO 下同名文件冲突

Whole Module Optimization 不允许同一 target 中有两个同名 `.swift` 文件（即使内部类名不同）。新增文件名避免与现有文件重复。

### 4.5 AnyCodable 初始化陷阱

WMO 模式下，`AnyCodable(["key": "value"])` 可能被推断为 `init(from:) throws`。显式声明参数类型为 `Any?` 以强制使用 `init(_ value: Any?)` 初始化器。

## 五、网络层 / Transport 相关

### 5.1 NWConnection 异步生命周期

`NWConnection.start()` 是异步的，必须在 `stateUpdateHandler` 检测到 `.ready` 后才能开始 `receive()`。

### 5.2 TCP 行分隔协议

测试中发送 JSON-RPC 请求时，**必须以 `\n` 结尾**，否则 TCPTransport 不处理该消息。

### 5.3 HTTP/SSE 格式要求

MCP 规范的 SSE 格式：

```
data: {"jsonrpc":"2.0",...}\n
\n
```

- 每个事件以 `data: ` 前缀开头
- JSON 中不能有裸换行（需 escape 或单行输出）
- 事件之间用**空行**分隔（即两个 `\n`）
- 可选 `id:` 字段（用于断线恢复，本轮暂不实现）

### 5.4 Origin 验证

MCP 规范要求服务端对 HTTP 请求做 Origin 验证以防 DNS rebinding 攻击：

- `localhost`、`127.0.0.1`、`[::1]` 视为合法
- 无 Origin Header 的请求也应放行（curl/CLI 客户端不发 Origin）
- 其他 Origin → 返回 403

### 5.5 Session 管理陷阱

- TCP 模型：连接 = 会话，断开即清理
- HTTP 模型：无连接概念，需显式管理 `Mcp-Session-Id` 的创建、验证、超时和清理
- 过期 Session 要通过定时器或 LRU 策略清理，否则会内存泄漏

## 六、任务执行通用原则

### 6.1 先确认架构可行性再写代码

1. 验证 target 依赖（能否导入需要的模块）
2. 验证关键 API 签名（参数、返回值、sync/async）
3. 验证测试 target 结构（被测文件可见性）
4. **然后**才写实现代码

### 6.2 小步验证

每次改动后立即构建验证，不要累积多个改动再一起验证。

### 6.3 先读后写

编辑文件前先 `read_file` 确认当前内容，避免基于过时信息编辑。

### 6.4 善用 git checkout 恢复

pbxproj 修改出问题时，立即 `git checkout -- PlayCover.xcodeproj/project.pbxproj` 恢复，不要尝试手动修补。

### 6.5 脚本使用绝对路径

Python 脚本中所有路径都用 `os.path.abspath()` 构造。避免相对路径 + `cwd` 参数导致的路径双重拼接问题。

对 GUI 冒烟尤其如此：

- `open -a PlayCover` 可能命中 `/Applications` 中的旧安装版，而不是当前验证包
- 应优先使用 `open /绝对路径/PlayCover.app`
- 进程存活检查也应按 **完整二进制路径** 匹配，而不只是按进程名 `PlayCover` 模糊判断
- 临时验证包最好使用不同 bundle 目录名（如 `PlayCover-H05-Verify.app`），减少路径歧义和误命中风险

### 6.6 脚本失败时不要静默成功

`str.replace()` 匹配不到时返回原字符串且不报错。关键操作后必须验证是否真正生效（如检查目标字符串是否存在）。

## 八、各任务经验记录

> 以下由各任务执行 agent 在完成后填写。**请结合上文通用经验做整合，如果新发现使上文某条需要修正或补充，请直接修改上文。**

### H01：SPM 依赖与项目配置

1. **项目已有 SPM 基础设施**：PlayCover 已通过 SPM 管理 7 个依赖（Yams、Sparkle、DataCache 等），因此 `XCRemoteSwiftPackageReference`、`XCSwiftPackageProductDependency` 等 section 均已存在，添加新包只需在现有 section 末尾追加条目，不需要创建新 section。

2. **SPM 包添加需修改 6 处**：
   - `PBXBuildFile` — `{isa = PBXBuildFile; productRef = <DEP_ID>;}`
   - `PBXFrameworksBuildPhase` — 在 PlayCover GUI target 的 `files` 列表中
   - `PBXNativeTarget.packageProductDependencies` — PlayCover target 的产品依赖列表
   - `PBXProject.packageReferences` — 项目级包引用列表
   - `XCRemoteSwiftPackageReference` — 包的 URL 和版本约束
   - `XCSwiftPackageProductDependency` — 引用的产品名和包引用

3. **Hummingbird 需要 macOS 14+**：Hummingbird 2.x 基于 Swift Concurrency 和 SwiftNIO，API 标注了 `@available(macOS 14, *)`。所有使用 Hummingbird API 的代码必须添加 `@available(macOS 14, *)` 注解。

4. **Hummingbird 2.21.1 实际引入的依赖**：SwiftNIO、swift-log、swift-service-lifecycle、swift-collections、swift-metrics、swift-distributed-tracing、swift-http-types、swift-async-algorithms、swift-atomics、swift-nio-extras、swift-nio-http2、swift-nio-transport-services、swift-nio-ssl、swift-crypto、swift-certificates、swift-asn1、swift-http-structured-headers、async-http-client、swift-system、swift-argument-parser、swift-numerics、swift-algorithms。依赖链较长，首次解析耗时较长。

5. **SPM 与 Carthage 共存验证成功**：Hummingbird 通过 SPM 引入后，Carthage 管理的 PlayTools 不受影响，CLI target 和 Tests target 编译正常（624 tests, 0 failures）。

### H02：SSE 编码与会话管理

1. **SSE 空 data 处理陷阱**：`String.split(separator: "\n", omittingEmptySubsequences: false)` 对空字符串 `""` 会返回 `[""]`（一个空 Substring 元素），而非空数组。如果同时用 `isEmpty` 判断来补充 `data: \n`，会导致重复输出。正确做法是先判断 `isEmpty`，用 if-else 分支处理空和非空两种情况，避免重复。

2. **pbxproj 新增文件的 4+1 处修改模式已验证**：对于纯 Foundation 文件（不依赖 SPM 包），需要修改 pbxproj 的 4 个 section（PBXBuildFile、PBXFileReference、PBXGroup、PBXSourcesBuildPhase）。无需修改 PBXFrameworksBuildPhase 或 SPM 相关 section。每个 target 一个独立的 PBXBuildFile 条目，指向同一个 PBXFileReference。

3. **测试文件 Target membership 规则**：源文件（SSEEncoder、MCPSessionManager）需要加入全部三个 target（PlayCover、PlayCoverMCP、PlayCoverMCPTests），测试文件仅加入 PlayCoverMCPTests target。这与 H01 经验中的 Target 归属矩阵一致。

4. **AnyCodable WMO 陷阱仍需注意**：在测试中构造 `AnyCodable` 时需显式标注类型为 `Any?`（如 `AnyCodable(["ok": true] as [String: Any] as Any?)`），避免 WMO 下类型推断错误。

### H03：StreamableHTTPTransport 实现

1. **Hummingbird API 调研是前提**：Hummingbird 2.x 的 API 与文档示例有差异（如 `Router` 需要 `RouterPath` 类型、`Application` 的 `init(router:)` 便捷初始化器、`onServerRunning` 回调获取实际端口等）。实现前应直接阅读 SPM 解析后的源码（`/tmp/PlayCover-DerivedData/SourcePackages/checkouts/hummingbird/Sources/`），确认关键类型签名。

2. **Request body 读取方式**：Hummingbird 的 `Request.collectBody(upTo:)` 是 `mutating` 方法（会将收集后的 ByteBuffer 存回 Request），使用时需要 `var mutableRequest = request`。或者可以直接使用 `request.body.collect(upTo:)` 但后者来自 NIOCore 的 AsyncSequence 扩展。

3. **HTTPField.Name 自定义 header 是可失败初始化器**：`HTTPField.Name("Mcp-Session-Id")` 返回 `Optional`，需要 `!` 或 `guard let` 解包。常用做法是定义为 computed property 使用 `!` 强制解包（因为这些 header 名都是合法 token）。

4. **`#if canImport(Hummingbird)` 条件编译**：由于 `StreamableHTTPTransport.swift` 仅添加到 GUI target（有 Hummingbird SPM 依赖），使用 `#if canImport(Hummingbird)` 包裹整个文件。如果不小心被其他 target 引用，文件会编译为空，不会报错。

5. **仅 GUI target 的 pbxproj 模式**：与通用文件（SSEEncoder、MCPSessionManager 需要 3 个 PBXBuildFile 条目对应 3 个 target）不同，Hummingbird 依赖的文件只需要 1 个 PBXBuildFile 条目（GUI target），修改 4 处即可：PBXBuildFile、PBXFileReference、PBXGroup、PlayCover GUI 的 PBXSourcesBuildPhase。

6. **Hummingbird Application.run() 的生命周期**：`app.run()` 是 async 且会阻塞直到服务关闭。需要在独立的 `Task` 中运行，并通过 `Task.cancel()` 触发优雅关闭。`onServerRunning` 回调在服务端口绑定后被调用，是获取实际端口（端口 0 时系统分配）的正确时机。

7. **Phase 1 不含测试文件**：由于 `StreamableHTTPTransport` 依赖 Hummingbird，而 Tests target 未链接 Hummingbird，无法在 Tests target 中直接编写单元测试。端到端集成测试推迟到 H06，可通过 curl 冒烟测试验证（需 H05 完成 GUI 集成后）。

### H04：MCPServer 双向通道

1. **最小侵入性设计有效**：通过添加可选的 `notificationSink: ((JSONRPCMessage) -> Void)?` 回调，不改变 `handle()` 签名，所有现有调用方（Tools、Resources、Services）零改动。`notificationSink` 为 nil 时行为与改造前完全一致，保证了向后兼容。

2. **`wireNotifications()` 的 `isInitialized` 守卫很重要**：logger 和 task manager 的回调可能在 `initialize` 握手阶段就被触发（例如初始化过程中的日志）。必须在回调中检查 `self.isInitialized` 才能发送通知，否则会在客户端尚未准备好时推送消息，违反 MCP 规范。

3. **`AnyCodable(Encodable)` 是 throwing 的**：`AnyCodable` 的 `init(_ encodable: some Encodable) throws` 会经过 JSON 编码-解码往返。在 `wireNotifications` 的回调中使用 `try?` 来静默处理编码失败，而不是 crash。

4. **SSEStreamManager 的线程安全设计**：`notificationSink` 可能从任何线程调用（MCPLogger 在 log 所在线程回调，TaskManager 在 `updateTask` 的线程回调），SSEStreamManager 的所有操作都需要自己的 `NSLock` 保护，与 `MCPSessionManager` 的锁互相独立。

5. **POST SSE 流 vs GET SSE 流的区别**：GET 流是长连接，由 SSEStreamManager 管理生命周期，用于接收服务端主动推送；POST 流是短暂的，请求处理完就关闭。两者通过 `StreamInfo.StreamType` 枚举区分，服务端推送只发到 GET 流。

6. **`JSONRPCResponse` 是 struct 不是 enum**：在测试中不能用 `guard case .success = response` 进行模式匹配。应通过 `XCTAssertNil(response.error)` 或检查 `response.result != nil` 来判断成功/失败。这是编写测试时容易犯的错误。

7. **测试文件只需加入 Tests target**：`MCPServerNotificationTests.swift` 只需要 1 个 PBXBuildFile 条目（PlayCoverMCPTests target），因为它测试的是无外部依赖的 MCPServer 功能。这比通用源文件（需要 3 个 target）更简单。

### H05：MCPManager 适配

1. **GUI 集成必须处理运行时可用性，而不只是编译可用性**：项目部署目标仍是 macOS 12，但 `StreamableHTTPTransport` / Hummingbird 需要 macOS 14。`MCPManager` 不能只在编译期通过，还必须在运行时把不支持 HTTP 的环境自动回退到 TCP，并把归一化后的传输方式写回 `UserDefaults`，否则设置界面和真实运行状态会长期不一致。

2. **不要把 `0.0.0.0` 直接当作用户可复制的 endpoint**：它是监听地址，不是可靠的客户端访问地址。设置界面应同时展示“可复制的本地 endpoint”（如 `http://127.0.0.1:19820/mcp`）和“实际监听地址”（如 `0.0.0.0:19820`），避免用户复制到一个无法直接访问的 URL。

3. **Transport 切换最好抽象成统一生命周期**：`TCPTransport` 和 `StreamableHTTPTransport` 的状态回调形状相似，但具体类型不同。GUI 侧不必强行抽公共协议，使用统一的 `start/stop + state callback` 适配层和 `AnyObject` 持有活跃 transport，更容易在不改底层 transport 的前提下完成切换。

4. **HTTP 集成时不要重复手动接 notificationSink**：`StreamableHTTPTransport` 初始化时已经会接入 `MCPServer.notificationSink` 并调用 `wireNotifications()`。`MCPManager` 侧只需要把 `mcpServer` 传进去，避免二次接线导致行为分散或后续维护混乱。

### H06：集成测试与文档

1. **不要直接启动 `build/.../PlayCover.app` 做 GUI 冒烟**：PlayCover 的 `AppIntegrity` 会检查自身是否位于 `/Applications/PlayCover.app`，直接打开构建产物会弹出“移到应用程序文件夹”对话框，干扰自动化。GUI 验证应先通过 `BuildScripts/build_and_install.sh`（或等效流程）安装到 `/Applications`，再用绝对路径 `open /Applications/PlayCover.app` 启动。

2. **H06 更适合集成测试而不是 Hummingbird 单元测试**：`StreamableHTTPTransport.swift` 只编译进 GUI target，Tests target 未链接 Hummingbird；与其强行扩 tests 依赖，不如把 H06 验证重点放在 `curl` 驱动的端到端脚本上，覆盖握手、SSE、Origin 校验、Session 校验和协议版本校验。

3. **协议细节需要按规范收紧，否则文档/脚本会和真实行为脱节**：POST 必须校验 `Accept: application/json, text/event-stream`；后续请求缺失或携带无效 `Mcp-Protocol-Version` 应返回 400；缺失 `Mcp-Session-Id` 也应返回 400，已失效 session 才返回 404。先把 transport 行为修正到位，再写 H06 脚本，文档和验证才能一致。

4. **CLI 回归断言要基于真实 serverInfo**：GUI server 名是 `playcover-mcp-gui`，CLI server 名是 `playcover-mcp`。H06 的 stdio 回归不要误用 GUI 名称断言，否则脚本会在最后一步假失败。
