## 三、PlayTools 修改

_（待实际开发时补充）_

### 3.1 PlayTools 是 Carthage 依赖，修改会被覆盖

- `Carthage/Checkouts/PlayTools/` 被 `.gitignore` 忽略，不在 PlayCover 仓库 git 跟踪范围内
- 每次 Carthage bootstrap（xcodebuild 构建时的 build phase 脚本）会重新 checkout PlayTools 源码，**覆盖所有本地修改**
- R01 时发现修改后构建一次就丢失了

**解决方案：Patch 文件 + Apply 脚本**

- `Patches/playtools-*.patch` — 以 unified diff 格式保存对 PlayTools 的修改，纳入 git 版本管理
- `Patches/apply_playtools_patches.sh` — 幂等 apply 脚本，支持：
  - 从干净状态 apply（`--forward`）
  - 检测已 apply 跳过（`--reverse --dry-run`）
  - 批量处理所有 `playtools-*.patch` 文件
- **使用方式**：Carthage bootstrap 后（或本地 checkout 后）执行 `./Patches/apply_playtools_patches.sh`
- **新增 PlayTools 修改时**：更新或新增 `Patches/playtools-*.patch` 文件即可

### 3.2 修改 PlayTools 的工作流程

1. 先确认 `Carthage/Checkouts/PlayTools/` 目录存在（如不存在需先 `carthage checkout`）
2. 直接编辑 `Carthage/Checkouts/PlayTools/` 下的文件
3. 从 GitHub 下载原始版本：`curl -sL "https://raw.githubusercontent.com/PlayCover/PlayTools/<commit>/path/to/file" -o /tmp/original`
4. 生成 patch：`diff -u /tmp/original Carthage/Checkouts/PlayTools/path/to/file`（注意调整路径前缀为 `a/` `b/`）
5. 保存到 `Patches/playtools-<feature>.patch`
6. 验证：还原文件 → `./Patches/apply_playtools_patches.sh` → 确认修改生效

## 四、构建环境

### 4.1 PlayCover GUI scheme 的完整构建命令

```bash
xcodebuild -project PlayCover.xcodeproj -scheme PlayCover -configuration Release build \
  CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES \
  FASTLANE=1
```

| 参数 | 作用 |
|------|------|
| `CODE_SIGN_IDENTITY="-"` | ad-hoc 签名 |
| `CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES` | 跳过严格签名检查 |
| `FASTLANE=1` | 跳过 Carthage Bootstrap 和 SwiftLint build phase |

### 4.2 FASTLANE=1 跳过 Carthage Bootstrap 和 SwiftLint

- PlayCover.xcodeproj 中有两个 build phase 脚本被 `if [[ -z "$FASTLANE" ]]` 包裹：**Carthage Bootstrap** 和 **SwiftLint**
- 设置 `FASTLANE=1` 环境变量可以同时跳过这两个步骤
- 跳过 Carthage Bootstrap 后，构建会使用 `Carthage/Checkouts/` 中已有的源码（含本地 patch），不会重新 checkout 覆盖修改
- **注意**：跳过 Carthage Bootstrap 的前提是 `Carthage/Checkouts/` 目录已存在且内容完整。首次 clone 仓库后需先运行一次 `carthage checkout`
- 此技巧来自 `LocalDocs/MCPWithGUITask/99-经验教训.md` G02 条目

### 4.3 Codesign sparkle 脚本的 "Sign to Run Locally" 坑

- 使用 `CODE_SIGN_IDENTITY="-"` 进行 ad-hoc 签名时，Xcode 会将 `EXPANDED_CODE_SIGN_IDENTITY_NAME` 设置为 `"Sign to Run Locally"`（而非 `"-"` 或空字符串）
- Codesign sparkle build phase 脚本中的 fallback 逻辑需要将 `"Sign to Run Locally"` 也作为 ad-hoc 的判定条件，否则 `codesign --sign "Sign to Run Locally"` 会因找不到 identity 而失败
- 已修复：在判断条件中增加了 `|| [ "$IDENTITY" = "Sign to Run Locally" ]`

1. 从 `LocalDocs/MCP/08-经验教训与常见陷阱.md` 继承的关键原则：
