### 这份文档的用途

每个 agent 在动手之前，都必须按这里的固定流程执行，避免越界、漏测试、漏提交。

### 开工前固定动作

#### 一、先读文档

必须按以下顺序阅读：

1. `00-README-导航.md`
2. `01-总体规划与架构.md`
3. `03-共享前置信息.md`
4. `04-测试与验证策略.md`
5. `05-提交与文档更新规范.md`
6. `06-全局任务看板.md`
7. 本次任务卡

#### 二、确认仓库状态

至少确认：

- 当前工作目录正确
- 当前分支正确
- `git status` 干净或仅包含本任务应有改动
- 上游依赖任务已完成

#### 三、只领取一个任务

- **一次只处理一个任务卡**
- 如果实现过程中发现范围明显膨胀，不要顺手做下一个任务
- 需要跨任务修改时，优先停下并更新文档，等待新的任务卡处理

### 实施中固定动作

#### 一、遵守任务边界

任务卡中所有这些字段都是硬边界：

- **范围内**
- **范围外**
- **依赖任务**
- **预期改动目录**
- **验收标准**

#### 二、优先补自动化验证

只要这次任务新增了 MCP 功能，就要尽量补：

- 单元测试
- 集成测试
- MCP 冒烟测试

如果暂时无法自动化，必须在任务卡结果里留下：

- 原因
- 人工验证步骤
- 后续补测建议

#### 三、同步更新 dashboard

任务开始时：

- 把对应任务卡与 `06-全局任务看板.md` 状态改成 `IN_PROGRESS`

任务完成时：

- 改成 `DONE`
- 记录本次运行的测试命令
- 记录 commit hash

如果阻塞：

- 改成 `BLOCKED`
- 写清楚阻塞原因

### 收工前固定动作

#### 一、运行验证

至少完成：

- 与本任务相关的自动化测试
- 至少一条 MCP 冒烟路径验证
- 记录命令与结果

#### 二、更新文档

至少更新：

- 当前任务卡
- `06-全局任务看板.md`
- 如有架构变化，再更新 `01-总体规划与架构.md`
- 如有执行顺序变化，再更新 `07-任务依赖与推荐执行顺序.md`

#### 三、提交代码

每个任务结束都要单独 `git commit`，且 commit 必须包含：

- 代码修改
- 测试修改
- 文档更新

### 越界处理规则

遇到以下情况时，不要继续扩展：

- 需要实现新 transport
- 需要引入新的大型架构调整
- 需要跨越两个以上任务卡的职责边界
- 需要额外修改 Session runtime，但当前任务是 Host-only

正确做法：

- 停在当前任务边界
- 在任务卡里写明新发现
- 更新全局看板
- 把剩余工作留给后续任务
