# 技术方案详解

## 一、TCPTransport 实现

### 1.1 设计目标

- 基于 Apple `Network.framework`（`NWListener` + `NWConnection`）
- 仅监听 `127.0.0.1`（loopback），安全可控
- 行分隔 JSON-RPC 协议，与现有 `StdioTransport` 语义完全一致
- 支持多客户端并发连接
- 后台线程运行，不阻塞 SwiftUI 主线程

### 1.2 核心类设计

```swift
import Network

public final class TCPTransport {
    public typealias MessageHandler = @Sendable (JSONRPCMessage) -> JSONRPCMessage?
    
    private let handler: MessageHandler
    private let listener: NWListener
    private let queue: DispatchQueue
    private var connections: [NWConnection] = []
    
    public init(port: UInt16 = 19820, handler: @escaping MessageHandler) throws {
        self.handler = handler
        self.queue = DispatchQueue(label: "io.playcover.mcp.tcp", qos: .userInitiated)
        
        let params = NWParameters.tcp
        params.requiredLocalEndpoint = NWEndpoint.hostPort(
            host: .ipv4(.loopback),
            port: NWEndpoint.Port(rawValue: port)!
        )
        self.listener = try NWListener(using: params)
    }
    
    public func start() { ... }
    public func stop() { ... }
}
```

### 1.3 协议格式

与 stdio 完全一致：**每行一个完整的 JSON-RPC 消息，以 `\n` 分隔**。

```
客户端 → 服务器:  {"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}\n
服务器 → 客户端:  {"jsonrpc":"2.0","id":1,"result":{...}}\n
```

### 1.4 连接生命周期

```
NWListener.start()
  ├── 新连接到达 → newConnectionHandler
  │     ├── connection.start(queue:)
  │     ├── 循环读取行数据
  │     │     ├── 解析 JSONRPCMessage
  │     │     ├── 调用 handler(message)
  │     │     └── 将 response 写回连接
  │     └── 连接断开 → 从 connections 移除
  └── listener.cancel() → 所有连接断开
```

### 1.5 与 StdioTransport 的对比

| 维度 | StdioTransport | TCPTransport |
|------|---------------|--------------|
| 传输介质 | stdin/stdout | TCP socket |
| 并发连接 | 1（单进程 pipe） | 多（每连接独立） |
| 线程模型 | `RunLoop.main.run()` 阻塞 | 后台 DispatchQueue |
| 适用场景 | CLI 工具 | 嵌入 GUI / 远程调试 |
| 日志通道 | stderr | 独立 log 机制 |

## 二、命名冲突解决

### 2.1 Shell 冲突

| 模块 | 当前定义 | 用途 |
|------|---------|------|
| GUI | `class Shell: ObservableObject` | 执行 shell 命令，带 UI 可观察状态 |
| MCP | `enum Shell` | 静态方法集合，执行 codesign/install_name_tool 等 |

**解决方案**：将 MCP 的 `Shell` 改名为 `MCPShell`（或 `ShellHelper`）。

理由：
- MCP 的 `Shell` 是无状态的 enum，改名影响面更小
- GUI 的 `Shell` 被广泛引用且是 `ObservableObject`，改名影响大
- 后续也方便区分两套 shell 调用的来源

### 2.2 其他潜在冲突

需要全面编译验证，但已知无重大冲突的类型：
- `AppInfo` (GUI) vs `AppRecord` (MCP) — 不冲突
- `PlayApp` (GUI) vs 无对应 (MCP) — 不冲突
- `Keymapping` (GUI) vs `KeymapService` (MCP) — 不冲突

## 三、MCP 代码集成到 GUI Target

### 3.1 方案选择

| 方案 | 说明 | 推荐度 |
|------|------|--------|
| 直接加 target membership | 把 41 个文件勾选 PlayCover.app target | ⭐⭐ 简单但粗暴 |
| 共享 Framework（PlayCoverMCPCore） | 已存在的概念，MCP CLI 和 GUI 都链接它 | ⭐⭐⭐ 推荐 |
| 静态库 | 编译为 .a 静态库 | ⭐ 过于复杂 |

**推荐共享 Framework**：当前 MCP 文件头已有 `// PlayCoverMCPCore` 注释，说明架构上已预留了这个概念。

### 3.2 需要排除的文件

GUI target 不需要编译以下文件：
- `PlayCoverMCP/main.swift`（CLI 入口，GUI 有自己的 @main）
- `PlayCoverMCP/Transport/StdioTransport.swift`（GUI 用 TCPTransport）

## 四、MCPManager 生命周期管理

### 4.1 职责

```swift
/// 管理嵌入式 MCP Server 的生命周期。
/// 在 GUI app 启动时自动启动 TCP MCP 服务，退出时停止。
class MCPManager: ObservableObject {
    static let shared = MCPManager()
    
    @Published var isRunning = false
    @Published var connectedClients = 0
    @Published var port: UInt16 = 19820
    
    private var server: MCPServer?
    private var transport: TCPTransport?
    
    func start() { ... }
    func stop() { ... }
}
```

### 4.2 集成点

```swift
// PlayCoverApp.swift → AppDelegate
func applicationDidFinishLaunching(_ notification: Notification) {
    // ... 现有代码 ...
    MCPManager.shared.start()   // 新增
}

func applicationWillTerminate(_ notification: Notification) {
    MCPManager.shared.stop()    // 新增（需新增此方法）
}
```

### 4.3 Server 初始化

`MCPManager.start()` 内部需要复现 `main.swift` 中的 server bootstrap 逻辑，但：
- 使用 `TCPTransport` 替代 `StdioTransport`
- 所有 Service 使用与 CLI 相同的 `defaultService()` 工厂方法
- Transport 在后台队列运行

## 五、GUI-MCP 状态联动

### 5.1 核心问题

GUI 的 `AppsVM.fetchApps()` 只在特定事件触发时才重新扫描磁盘。MCP 在后台安装/卸载应用后，GUI 不会自动感知。

### 5.2 解决方案：操作完成回调

在 MCP 的关键 Service 操作完成后，通知 GUI 刷新：

```swift
// 方案 1：直接调用（推荐，因为同一进程）
// InstallerService 安装完成后：
Task { @MainActor in
    AppsVM.shared.fetchApps()
}

// 方案 2：NotificationCenter
NotificationCenter.default.post(name: .mcpAppsChanged, object: nil)
// GUI 侧监听：
NotificationCenter.default.addObserver(..., selector: #selector(refreshApps), name: .mcpAppsChanged)
```

### 5.3 需要联动的操作清单

| MCP 操作 | GUI 需要刷新的对象 |
|---------|-------------------|
| `install_ipa` | `AppsVM.shared.fetchApps()` |
| `uninstall_app` | `AppsVM.shared.fetchApps()` |
| `update_app_settings` | 对应 app 的 `AppSettings` 重新加载 |
| `create_keymap` / `delete_keymap` / `rename_keymap` | 对应 app 的 `Keymapping` 重新加载 |
| `inject_playtools` / `remove_playtools` | `AppsVM.shared.fetchApps()`（因为 app 状态变了） |
| `clear_app_data` / `clear_app_settings` | 对应 app 视图刷新 |
| `resign_app` | 无需刷新（不改变列表状态） |
| `launch_app` | 可选：更新运行状态指示 |

### 5.4 实现策略

优先使用 `NotificationCenter` 方案——解耦更好，MCP Service 层不需要直接依赖 GUI 的 ViewModel：

```swift
// 定义通知名
extension Notification.Name {
    static let mcpAppsChanged = Notification.Name("io.playcover.mcp.appsChanged")
    static let mcpSettingsChanged = Notification.Name("io.playcover.mcp.settingsChanged")
    static let mcpKeymapsChanged = Notification.Name("io.playcover.mcp.keymapsChanged")
}

// MCP Service 端发通知
// InstallerService.install() 完成后：
NotificationCenter.default.post(name: .mcpAppsChanged, object: nil)

// GUI 端监听
// AppsVM.init() 中：
NotificationCenter.default.addObserver(
    forName: .mcpAppsChanged, object: nil, queue: .main
) { [weak self] _ in
    self?.fetchApps()
}
```

## 六、Agent 侧配置变更

### 6.1 当前 CLI 模式

```json
{
  "mcpServers": {
    "playcover": {
      "command": "/path/to/PlayCoverMCP"
    }
  }
}
```

### 6.2 嵌入 GUI 后的 TCP 模式

Agent 需要改用 TCP 连接方式。具体配置取决于 Agent 客户端（如 Claude Desktop、Cursor 等）对 TCP MCP 的支持方式。

典型配置可能为：

```json
{
  "mcpServers": {
    "playcover": {
      "transport": "tcp",
      "host": "127.0.0.1",
      "port": 19820
    }
  }
}
```

### 6.3 兼容性

保留独立的 `PlayCoverMCP` CLI target（stdio 模式），供不使用 GUI 的场景继续使用。两种模式并存。
