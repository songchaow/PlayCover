# 任务与协议问题

## RT05：`install_ipa` 提示使用 `tasks/get`，但 MCP tool 层未暴露 task 查询能力

### 现象

调用 `install_ipa` 后，返回的是后台任务 ID（如 `task-1`），并提示调用方通过 `tasks/get` 查询进度。

但当前 `playcover` 对外暴露的 MCP tool 列表里，**没有可直接调用的 task 查询工具**。

### 影响

- 正常 MCP tool 使用者无法追踪安装、导出等长任务的进度
- `install_ipa` / `export_patched_ipa` 的可观测性不完整
- 调用方容易误以为任务“卡住”或“丢失”

### 实际验证

代码搜索结果表明：

- `tasks/get`
- `tasks/list`
- `tasks/cancel`

确实作为底层 JSON-RPC method 注册存在；只是当前工具封装层未把它们暴露为等价 MCP tool。

### 预期

至少应满足以下任一方案：

1. 对外暴露 `get_task` / `list_tasks` / `cancel_task` 等 tool
2. 在 `install_ipa` 返回值里明确说明“这不是 tool，而是底层 JSON-RPC method，需要走原始 HTTP / MCP 调用”

### 建议排查

1. 补齐 task 能力的 tool 封装
2. 如果短期不封装，先修正文案，避免误导调用方

## RT06：`tasks/get` / `tasks/cancel` 参数形状与常见对象风格不一致

### 现象

底层 JSON-RPC 调用测试表明：

- `tasks/get` 需要的 `params` 是 **裸字符串**，例如 `"task-1"`
- `tasks/cancel` 也需要 **裸字符串**

而不是更常见、更自描述的对象形式，例如：

```json
{"taskId":"task-1"}
```

### 影响

- 容易与其他 method 的对象参数风格不一致
- 客户端如果按对象参数发送，会直接失败
- 增加协议接入成本和踩坑概率

### 实际验证

- `params: "task-1"`：成功
- `params: {"taskId":"task-1"}`：不符合当前实现预期

### 预期

更稳妥的接口形状应是对象参数，例如：

- `{"taskId":"task-1"}`

至少也应在文档中明确声明当前实现采用裸字符串。

### 建议排查

1. 确认该参数设计是否有意为之
2. 若非强约束，考虑兼容两种形状
3. 若继续使用裸字符串，需在文档和错误提示中写清楚

## RT07：SSE 任务通知 method 实际为 `notifications/tasks/update`，与文档预期不一致

### 现象

通过原始 HTTP + SSE 监听 `install_ipa` 任务状态变更时，实际收到的通知 method 为：

- `notifications/tasks/update`

而不是测试前预期的：

- `notifications/tasks/status`

### 影响

- 订阅端如果按另一套 method 名实现，将收不到任务状态
- 会造成“服务端明明在推，客户端却完全无感”的兼容性问题

### 实际验证

SSE 流中确实收到了任务更新事件，说明：

1. 流式推送能力本身存在
2. method 命名与文档 / 预期不一致才是关键问题

### 预期

文档、实现、客户端示例三者应统一使用同一个 method 名。

### 建议排查

1. 统一任务状态通知的 method 命名
2. 若历史兼容需要，考虑短期同时兼容旧名和新名
3. 检查本地文档、README、测试脚本、客户端接入示例是否都已同步
