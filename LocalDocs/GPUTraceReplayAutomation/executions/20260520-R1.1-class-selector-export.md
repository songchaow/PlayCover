## 8. 关键发现与结论

1. **GPUToolsReplayService.xpc 只是一个 bootstrap stub**：它只做了 `xpc_main` + 调用 `GTMTLReplayController_init` + `GTMTLReplayClient_createNewTransport` + mach memory 共享。所有实际 replay 逻辑在 `GPUToolsReplay.framework`。

2. **`GPUToolsReplay.framework` 暴露了清晰的 C API**：`GTMTLReplayController_{init,playAll,playTo,rewind}` 构成了 replay 的控制面。`GTMTLReplayClient_{init,createNewTransport,destroyNewTransport,preferDevice}` 构成了传输面。

3. **`GTMTLReplay_CLI` 的存在暗示有 CLI 入口**：这是自动化最有价值的线索。如果能确定其参数签名，可能实现 headless replay。

4. **`replayerLaunchDictionary` 由 `DYCaptureSession` 持有**，而 `finalLaunchDictionary` 由 `DYGuestAppSession` 持有。两者可能有依赖关系。

5. **Harvester API 是只读数据提取的最佳候选**：`GTHarvesterGetData`、`GTHarvesterGetMetadata`、`GTHarvesterGetTexturePlane` 可能不需要触发新 replay 即可从已有 capture 中提取数据。

6. **`g_runningInCI` / `g_runningValidationCI` 全局变量暗示存在 CI 模式**：在 CI 环境下 replay 行为可能有所不同（可能更宽松或有特殊路径）。

## 9. 对后续任务的建议

- **R1.2** 应优先从 `GTMTLReplay_CLI` 符号入手，尝试通过 disassembly 或 runtime 观察确定其参数签名。
- **R1.3** 应针对 `_replayerLaunchDictionary` 和 `_finalLaunchDictionary` 的 setter 调用链做交叉引用。
- **R2** 的只读 bridge 应优先利用 `GTHarvesterGet*` 系列函数，这些是目前看来最安全的数据提取入口。
