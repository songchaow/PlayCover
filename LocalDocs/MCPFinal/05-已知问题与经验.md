## PlayCover MCP 已知问题与经验

### 一、当前仍需保留的已知问题

#### P01：`install_ipa` 的 MCP 路径与 GUI 原生安装路径行为不一致

当前最重要的未关闭问题不是“任务不可观测”，而是：

- 同一 IPA 通过 MCP `install_ipa` 会稳定进入失败任务
- 失败信息为：`MachO conversion failed: No ARM64 architecture found in fat binary`
- 但用户反馈相同 IPA 在 GUI 中可以安装成功

这说明当前更合理的判断是：

1. `PlayCoverMCP/HostServices/Install/InstallerService.swift` 与 GUI 原生 `PlayCover/AppInstaller/Installer.swift` 很可能没有完全走同一套语义
2. 差异点可能在 Mach-O 预检、可执行文件定位、转换分支、注入分支或 GUI 额外容错
3. 在完成对比前，不能把该 IPA 简单定义成“稳定无 ARM64 的负例”

#### P02：旧 raw TCP 手测 SOP 已过期

旧文档中的如下手测方式：

- `nc localhost 19820`
- 直接发 raw JSON-RPC initialize

已经不再代表当前 GUI 默认形态。

当前 GUI 暴露的是：

- **Streamable HTTP MCP**
- 端点：`http://127.0.0.1:19820/mcp`

因此后续联调、回归、文档和脚本都应以 HTTP 主路径为准。

### 二、重要环境注意事项

#### E01：残留 CLI 占用 `52741` 会导致 GUI `create_session` 超时

已确认的环境冲突现象：

- GUI MCP 的 `19820` 正常监听
- 但 runtime 注册端口 `52741` 被旧 `PlayCoverMCP` CLI 进程占用
- 结果是 GUI 路径下 `create_session` 超时

处理方式：

1. 清理残留 CLI `PlayCoverMCP` 进程
2. 重启 GUI
3. 重新 `initialize`
4. 再进行 `create_session` / touch / input / capture 联调

这更像**测试环境冲突**，但对 live 回归影响非常大，必须提前排除。

#### E02：GUI 重启后旧 HTTP session 会失效

只要 GUI 发生以下动作：

- 重装
- 重启
- 切换 transport

旧的 `Mcp-Session-Id` 都应视为失效。

因此：

- 不要在 GUI restart 后继续复用旧 session
- 遇到 `Invalid or expired session ID` 时，先判断是不是 session 过期，而不是立刻判定成业务回归

### 三、工程经验

#### 1. GUI 与 CLI 有两套入口，bootstrap 相关改动必须双查

凡是以下改动：

- tool 注册
- resource 注册
- task 能力暴露
- session infrastructure 启动
- runtime 注册监听

都要同时检查：

- `PlayCoverMCP/main.swift`
- `PlayCover/Services/MCPManager.swift`

否则很容易出现：

- GUI 通，CLI 不通
- CLI 通，GUI 不通

#### 2. Session / runtime 问题一定要看三层

排查 `create_session` 或输入自动化问题时，至少同时检查：

1. **Host bootstrap**：`MCPManager.swift` / `main.swift`
2. **Host runtime infrastructure**：`RegistrationListener.swift` / `SessionRegistry.swift` / `SessionHealthMonitor.swift`
3. **Runtime side**：PlayTools bridge 是否真的生效

#### 3. 改了 `Carthage/Checkouts/PlayTools/` 并不等于 live app 已经在跑新代码

需要再确认：

- PlayTools 真的被重新构建
- live framework 真的被替换
- 目标 app 真的被重新注入 / 重装
- 运行时真的走到了新的 bridge 代码

#### 4. 长任务能力不能只停留在底层 method

对像 `install_ipa` 这样的长任务，必须保证调用方能通过**标准 tool 路径**继续观测。

当前这部分已经补齐为：

- `get_task`
- `list_tasks`
- `cancel_task`

后续新增长任务能力时，也应继续遵守这个原则。

#### 5. 协议修正应优先让规范路径成为默认路径

例如 task 查询相关接口，应优先确保：

- 文档写的路径
- tool 层暴露的路径
- 测试覆盖的路径
- JSON-RPC method 的默认用法

保持一致，不要再让旧形状成为默认教学入口。

### 四、构建与工程文件经验

#### 1. 构建建议统一使用 ad-hoc 签名参数

推荐统一带上：

- `FASTLANE=1`
- `CODE_SIGN_IDENTITY="-"`
- `CODE_SIGNING_REQUIRED=NO`
- `CODE_SIGNING_ALLOWED=YES`
- `-derivedDataPath /tmp/PlayCover-DerivedData`

#### 2. `pbxproj` 修改要三步验证

每次动 `PlayCover.xcodeproj/project.pbxproj` 后，至少做：

1. `plutil -lint`
2. `git diff`
3. build 验证

#### 3. 新文件的 target membership 要按角色区分

尤其要注意：

- Hummingbird 相关文件只属于 GUI target
- 通用 MCP 文件需要同步到业务 target 与 tests target
- 测试文件只属于 tests target

### 五、文档维护原则

#### 1. 以最终状态为中心，不再以历史任务卡为中心

从现在开始，MCP 文档应该回答：

- 当前推荐怎么接
- 当前实现怎么跑
- 当前有哪些能力
- 当前有哪些问题

而不是继续维护：

- Gxx / Hxx / Rxx 的阶段性施工路线
- 已弃用 transport 的手工 SOP
- 只适用于历史阶段的说明

#### 2. 旧 transport 可以保留代码，但不应再作为主文档中心

保留代码的意义是：

- 兼容
- 回退
- 测试

不是让后续使用者继续按旧 transport 的视角理解整个系统。

### 六、当前排查优先级建议

如果后续继续推进 MCP 质量，建议优先级如下：

1. **最高优先级**：对齐 `install_ipa` 的 GUI / MCP 行为
2. **高优先级**：确保 live 联调 SOP 全部切到 HTTP 主路径
3. **中优先级**：继续稳定 session / touch / input / capture 的真实 app 回归
4. **中优先级**：把新发现的 live 验证方式沉淀到脚本或测试中

### 七、结论

当前最重要的经验不是某个 Swift 语法细节，而是：

> **PlayCover MCP 已经收敛到“GUI 以 HTTP 为主、CLI 保留 stdio、TCP 只作兼容”的最终形态；后续所有文档、测试和联调都应该围绕这个事实展开。**
