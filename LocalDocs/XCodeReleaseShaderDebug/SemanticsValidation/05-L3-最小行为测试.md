## L3：最小行为测试

## 目标

在少量高价值样本上建立：

```text
固定输入
  ↓
执行 shader
  ↓
校验输出
```

用来回答：

- 某些结构上“看起来差不多”的样本，行为是否真的一致
- 哪些 lowering 模式需要从“结构风险”升级到“行为风险”

补充定位：

- 当前 `L3` 仍然**不是**默认主线
- 默认只有在 `SV-003` 已把 L1/L2 收口成稳定日常 gate，且 `SV-006` 已明确升级规则后，才进入这一层
- 若只是推进当前主线，这份文档当前**不必须读取**；只有在正式进入 `SV-004` 时才需要细读

## 总体策略

### 原则 1：compute-first

最小行为测试优先从 **compute shader** 开始，因为它：

- 容易自动化
- 不依赖窗口/UI
- 输出校验简单（buffer / texture）
- 最适合作为首批行为 oracle

### 原则 2：render-second

只有当某类问题明显属于 vertex/fragment 或 render pipeline 行为时，再补：

- 离屏 render
- 小尺寸 attachment 比较
- 关键顶点/片元输出检查

### 原则 3：先少量高价值样本

第一阶段不追求覆盖面，而追求：

- 历史容易出错的 lowering 模式
- L2 标为中高风险的样本
- 可以稳定自动执行的样本

## 建议的样本分组

### A 组：控制流与选择

- `phi`
- `select`
- 条件分支
- 向量/标量选择

### B 组：类型与转换

- cast
- `extractvalue` / `insertvalue`
- 向量 element 操作
- fast-math 相关模式

### C 组：内存与地址空间

- `addrspace`
- `load/store`
- `getelementptr`
- buffer 索引与结构体字段路径

### D 组：builtin / texture / sampler

- `air.*` builtin 映射
- texture read/sample/gather
- sampler state
- stage builtin

## 第一版实现建议

### Phase 1：compute 行为 harness

建议新增一个最小行为 harness，职责：

1. 载入生成的 MSL 或参考 MSL
2. 创建 `MTLDevice`
3. 准备固定输入 buffer / texture
4. 运行 compute pipeline
5. 读回输出
6. 与 reference/oracle 比较

输出：

- `behavior-summary.json`
- 每个样本的输入、输出、误差、通过/失败状态

补充约束：

- 第一版必须是一条**完全本地、无 UI、无人工介入**的命令链路
- 若某个候选样本必须依赖 live 场景或人工操作，说明它不适合作为 L3 第一批样本

### Phase 2：reference/oracle 选择

建议按难度分层：

#### 优先级最高：CPU 可直接算出的样本

例如：

- 标量/向量算术
- compare/select
- 一些简单 cast

这类样本最容易形成稳定 oracle。

#### 第二优先级：用手写 MSL 作为参考实现

对于 CPU 不方便完全模拟的样本，可以：

- 保留一个手写参考 MSL
- 让“生成 MSL”和“参考 MSL”在同样输入下执行
- 对比输出

#### 第三优先级：render 行为作为 reference

只在前两种都不合适时考虑。

### Phase 3：离屏 render（必要时）

对于 vertex/fragment 样本，建议：

- 小尺寸 render target（如 `1x1`、`4x4`、`16x16`）
- 固定顶点输入
- 固定纹理/常量
- 对比颜色、深度或关键 attachment

## 浮点比较策略

行为测试不能一律要求 bit-exact。

建议：

- 默认支持 `abs` / `rel` tolerance
- 区分 `strict` 与 `approx` 模式
- 对 fast-math 相关样本单独记录比较策略

原则：

- 不要因为过严阈值制造大量噪声
- 也不要宽松到掩盖真实问题

## 样本来源建议

### 第一优先来源

- `SV-003` 已稳定下来的 `test-data-representatives`
- 如有必要，再从 `test-data-batch` 中补少量新增代表样本

原因：

- 已经是当前默认 gate 的控制面样本
- 输入规模小、最容易控制
- 最适合补 compute-first 行为 harness

### 第二优先来源

- L2 标出的代表性高风险 `ShaderCorpus` 样本

原则：

- 只引入少量、可稳定跑通的真实样本
- 只复用本地已有样本，不把 fresh capture 写成默认依赖
- 不要一上来就把大样本当默认行为测试集

## 与 L2 的衔接规则

默认应当：

- L0/L1 样本：不急着进入 L3
- L2 样本：先做聚类，再优先选一部分进入 L3
- L3 高风险样本：若能最小化，则进入行为测试；若不能最小化，再视情况后置到 L4

补充说明：

- 当前 `SV-003` 结束前，不建议直接从当前批量 `L2 = 3 / L3 = 20` 结果跳到“大量行为测试”
- 更合理的顺序是：先固定代表集，再从代表集里选 5~10 个最有信息量的样本

## 当前不建议的做法

- 一上来就为全部 `test-data/` 建行为 oracle
- 一上来就做真实 app 的行为验证
- 把大量 GUI/render live 流程塞进 L3
- 让用户手动观察画面当作默认测试方式
- 因缺少现成样本就让用户协助准备环境

## 完成标准

满足以下条件后，可认为 `SV-004` 有了第一阶段结果：

1. 已建立 compute-first 的最小行为 harness
2. 至少有一组样本可以自动执行并比较输出
3. 至少覆盖 1~2 类高风险 lowering 模式
4. 行为测试结果可以结构化落盘
5. 整个流程无需用户频繁介入

## 后续扩展

若 compute-first 路线证明有价值，再逐步补：

- 更多 oracle 类型
- 离屏 render harness
- 与 L2 风险分级的自动联动
