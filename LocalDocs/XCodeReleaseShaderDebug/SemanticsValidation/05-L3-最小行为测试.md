## L3：最小行为测试

## 目标

在少量高价值样本上建立：

```text
固定输入
  ↓
执行 shader
  ↓
校验输出
```

用来回答：

- 某些结构上“看起来差不多”的样本，行为是否真的一致
- 哪些 lowering 模式需要从“结构风险”升级到“行为风险”

补充定位：

- `L3` 仍然**不是**跨机器日常默认 gate
- 但 `SV-004` 当前已经是本目录主线；主线的含义是把极少量 `L2` 候选推进为纯离线、agent 可自主完成的行为证据，而不是把 L3 扩成大批量默认流程
- 默认只有在 `SV-003` 已把 L1/L2 收口成稳定日常 gate，且 `SV-006` 已明确升级规则后，才进入这一层
- 若只是维护 `SV-003` 或规划 `SV-005`，本文件按需阅读即可；若推进当前主线，建议与 `00-Dashboard.md`、`02-总体技术路线.md` 一起读

## 总体策略

### 原则 1：compute-first

最小行为测试优先从 **compute shader** 开始，因为它：

- 容易自动化
- 不依赖窗口/UI
- 输出校验简单（buffer / texture）
- 最适合作为首批行为 oracle

### 原则 2：render-second

只有当某类问题明显属于 vertex/fragment 或 render pipeline 行为时，再补：

- 离屏 render
- 小尺寸 attachment 比较
- 关键顶点/片元输出检查

补充约束：

- render-second 仍应优先视为 **L3 的最小离线扩展**，而不是提前跳到 `SV-005`
- 若新方案需要 GUI、人工登录、工作区外修改或外部 app 介入，就已经越过当前 L3 的自动化边界，不应写回默认流程

### 原则 3：先少量高价值样本

第一阶段不追求覆盖面，而追求：

- 历史容易出错的 lowering 模式
- L2 标为中高风险的样本
- 可以稳定自动执行的样本

## 第一版实现建议

### Phase 1：compute 行为 harness

当前已落地一版最小 harness，职责为：

1. 读取 `gate-summary.json` / `roundtrip-summary.json`
2. 直接从 `layeredDecision.l3Plan.candidateSampleKeys` 选择第一批 compute 候选
3. 载入 reference MSL 与 round-trip 生成的 MSL
4. 创建 `MTLDevice` 并执行 compute pipeline
5. 读回输出并按 `exact` / `approx` 策略比较
6. 产出结构化 `behavior-summary.json` 与每个样本的中间 artifact

当前入口：

```bash
python3 Scripts/test_ir_semantics_behavior_runner.py
python3 Scripts/ir_semantics_behavior_runner.py --gate-summary build/semantics-validation/roundtrip/test-data-representatives/gate-summary.json
```

当前产物：

- `build/semantics-validation/roundtrip/test-data-representatives/behavior-summary.json`
- `build/semantics-validation/roundtrip/test-data-representatives/behavior-artifacts/<sample>.spec.json`
- `build/semantics-validation/roundtrip/test-data-representatives/behavior-artifacts/<sample>.result.json`

补充说明：这条命令默认复用已有的 `gate-summary.json` / `roundtrip-summary.json` 固定产物；它当前新增的是行为层报告与 artifact，而不是重新生成整套 L1/L2 报告。与此同时，runner 在真正调用 Swift harness 前也会先校验 reference MSL 与 `.ll` 的 entry / shader kind / 返回类型 / 参数语义契约，若 sample oracle 已漂移，则直接在准备阶段失败，避免把噪声带进行为对跑结果。

补充约束：

- 当前默认入口必须继续保持为**完全本地、无 UI、无人工介入**的命令链路
- 若某个候选样本必须依赖 live 场景或人工操作，说明它不适合作为当前 L3 默认样本
- 当前默认执行面已从纯 compute-only 收口为 **compute-first + 白名单 render-second**：`test_fast_math_select` 走 compute，`test_intrinsic_vector_icmp_zext` 走最小离屏 render；后续候选若做不到单命令、本地、离屏、无 UI、无工作区外修改，就继续 defer，不强行塞回默认链路
- 当前默认输出目录直接复用 `gate-summary.outputRoot`；这样重复执行时，agent 无需人工整理报告落点

### Phase 2：reference/oracle 选择

建议按难度分层：

#### 优先级最高：CPU 可直接算出的样本

例如：

- 标量/向量算术
- compare/select
- 一些简单 cast

这类样本最容易形成稳定 oracle。

#### 第二优先级：用手写 MSL 作为参考实现

对于 CPU 不方便完全模拟的样本，可以：

- 保留一个手写参考 MSL
- 让“生成 MSL”和“参考 MSL”在同样输入下执行
- 对比输出

#### 第三优先级：render 行为作为 reference

只在前两种都不合适时考虑。

### Phase 3：离屏 render（必要时）

对于 vertex/fragment 样本，建议：

- 小尺寸 render target（如 `1x1`、`4x4`、`16x16`）
- 固定顶点输入
- 固定纹理/常量
- 对比颜色、深度或关键 attachment

`SV-004D` 当前已落地首个最小 render-second：

- 新增 `Scripts/metal_fragment_behavior_runner.swift`
- 当前只对白名单样本 `test_intrinsic_vector_icmp_zext` 开启
- 固定使用 helper fullscreen triangle + `4x4` `rgba16Float` offscreen target
- 仍保持**单命令、本地、离屏、无 UI、无工作区外修改**
- 当前产物直接写回 `behavior-artifacts/test_intrinsic_vector_icmp_zext.{spec,result}.json`
- 当前结果已收口为 `pass`：此前的 fragment `fail` 已确认是 sample oracle 漂移而非新的 lowering 回归；修正 `test_intrinsic_vector_icmp_zext.metal` 与 `.ll` 的同步性并复跑后，这条 fragment 候选已完成从“是否升级”到“如何收口”的切换，不再继续停在 deferred

这一步当前仍有明确边界：

- **只对白名单里的高价值 fragment 候选开放，不自动扩到更多 render/live 样本**
- **必须继续保持单命令、本地、离屏、无 UI、无工作区外修改**
- 若后续候选做不到这三个条件，就继续 deferred，不把 live/人工流程混进 L3

## 浮点比较策略

行为测试不能一律要求 bit-exact。

建议：

- 默认支持 `abs` / `rel` tolerance
- 区分 `strict` 与 `approx` 模式
- 对 fast-math 相关样本单独记录比较策略

原则：

- 不要因为过严阈值制造大量噪声
- 也不要宽松到掩盖真实问题

## 样本来源建议

### 第一优先来源

- `SV-003` 已稳定下来的 `test-data-representatives`
- 如有必要，再从 `test-data-batch` 中补少量新增代表样本

原因：

- 已经是当前默认 gate 的控制面样本
- 输入规模小、最容易控制
- 最适合补 compute-first 行为 harness

### 第二优先来源

- L2 标出的代表性高风险 `ShaderCorpus` 样本

原则：

- 只引入少量、可稳定跑通的真实样本
- 只复用本地已有样本，不把 fresh capture 写成默认依赖
- 不要一上来就把大样本当默认行为测试集

## 与 L2 的衔接规则

默认应当：

- L0/L1 样本：不急着进入 L3
- L2 样本：先做聚类，再优先选一部分进入 L3
- L3 高风险样本：若能最小化，则进入行为测试；若不能最小化，再视情况后置到 L4

补充说明：

- 当前 `SV-006` 已完成并提供升级边界，但仍不建议直接从当前批量 `L2 / L3` 结果跳到“大量行为测试”
- 更合理的顺序是：先守住固定代表集，再从代表集里选极少量最有信息量的样本
- 当前硬默认 gate 的活跃 `L2` 样本只剩 `test_fast_math_select`、`test_intrinsic_vector_icmp_zext`；`test_casts` 已在本轮通过 `air.convert` unsigned 语义修复退出活跃 debt，`test_struct_array_field` 当前仍属于 `blockedBeforeLive`，不应作为 L3 第一批默认入口
- 当前首版实际执行边界已进一步收敛为：`test_fast_math_select` 进入 compute harness；`test_intrinsic_vector_icmp_zext` 进入最小 offscreen render-second，并在修正 sample oracle 漂移后回到稳定 `pass`；`test_casts` 只在涉及转换语义回归时作为定向复核样本重新执行
- 当前最重要的已经不再是“要不要让 fragment 候选进入 render-second”，而是**继续守住这条最小离线行为边界的稳定性**：样本 oracle 要与 `.ll` 保持同步，新增候选只有在仍满足 automation-first 契约时才继续纳入

## 当前不建议的做法

- 一上来就为全部 `test-data/` 建行为 oracle
- 一上来就做真实 app 的行为验证
- 把大量 GUI/render live 流程塞进 L3
- 让用户手动观察画面当作默认测试方式
- 因缺少现成样本就让用户协助准备环境
- 因为想尽快覆盖 fragment 候选，就直接把 `SV-005` 的流程搬进 L3

## 完成标准

满足以下条件后，可认为 `SV-004` 有了第一阶段结果：

1. 已建立 compute-first 的最小行为 harness
2. 至少有一组样本可以自动执行并比较输出
3. 至少覆盖 1~2 类高风险 lowering 模式
4. 行为测试结果可以结构化落盘
5. 整个流程无需用户频繁介入

当前状态：以上五条已经满足；`test_fast_math_select` 与 `test_intrinsic_vector_icmp_zext` 也都已通过 reference-vs-generated 对跑，其中后者本轮已确认旧 `fail` 来自 sample oracle 漂移而非 lowering 回归。因此 `SV-004` 后续的重心不再是“有没有 harness”，而是继续守住当前白名单样本的稳定默认执行边界，并在未来只对白名单里的新增候选继续套用同样 automation-first 的 render-second 准入契约。

## 后续扩展

若 compute-first 路线证明有价值，再逐步补：

- 更多 oracle 类型
- 更多仍满足 automation-first 契约的 render-second 白名单样本
- 与 L2 风险分级的自动联动

补充约束：后续扩展只有在**仍能保持 agent 自主、单命令、本地、无人工介入**时，才适合纳入默认 L3 路径；否则应保持为后置专项流程。
