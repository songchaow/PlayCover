## 背景与目标

后续所有 Host 任务都需要一个统一的 MCP 宿主骨架，否则每个 agent 都会各自定义工具注册方式、返回结构和错误格式，最后很难收口。

本任务的目标是：

- 建立 Host MCP 的基础代码组织
- 建立工具注册与分发入口
- 定义统一返回结构
- 定义统一错误模型
- 提供公共 app 定位 / bundle id 解析 / 路径解析能力

---

## 范围（In Scope）

- 设计 Host MCP 的目录结构与入口类型
- 定义公共返回结构，例如：
  - `ok`
  - `message`
  - `data`
  - `warnings`
- 定义公共错误分类，例如：
  - app 不存在
  - 参数非法
  - 文件不存在
  - 运行前置不满足
  - 内部执行失败
- 设计 Host 工具注册方式
- 设计公共上下文或服务容器
- 实现 app 解析辅助：
  - 通过 `bundle_id` 找到 `PlayApp`
  - 通过路径定位 app 或 IPA
- 为后续任务提供稳定调用位

---

## 明确不做（Out of Scope）

- 不在本任务内实现 `install_ipa`
- 不在本任务内实现 `launch_app`
- 不在本任务内实现 `clear_cache`
- 不在本任务内实现 Session bridge
- 不在本任务内设计 attach 调试能力

如果需要示例工具，可只放一到两个极小占位工具，用于证明骨架通路可用。

---

## 建议代码落点

可优先考虑新建宿主侧 MCP 目录，例如：

- `PlayCover/MCP/Host/`
- 或 `PlayCover/Services/MCP/Host/`

建议至少拆出：

- 工具入口 / registry
- 公共 result / error 类型
- app resolver
- 参数校验辅助

如果现有项目结构更适合其他路径，可以调整，但必须在结果里说明。

---

## 建议交付接口

本任务不要求把所有功能都实现，但至少要为后续任务预留稳定入口，例如：

- `HostMCPServer` 或等价入口
- `HostToolRegistry` 或等价注册层
- `HostToolResult` / `HostToolError`
- `HostAppResolver`

---

## 完成标准

满足以下条件即可视为完成：

- Host MCP 已有明确入口文件与注册点
- 后续任务不需要再重复定义返回结构或错误模型
- 已有公共 app 查找逻辑，后续任务可复用
- 至少能证明“调用一个 Host 工具 -> 返回结构化结果”的通路可工作
- 文档中说明了新增骨架文件的位置与职责

---

## 给 agent 的执行提示

- 优先做“薄骨架”，不要一上来过度抽象
- 能复用现有 `PlayApp` / `AppsVM` / `AppInfo` 时，不要另造模型
- 如果发现需要为 Session 任务预留通道，只做最小扩展点，不要提前实现 Session bridge
- 结果里请明确写出：后续任务应该复用哪些新增类型

2. 将当前 task 的全部修改一起纳入本次提交，但不要混入其他 task 的无关变更：

除非上层明确要求不要提交，否则不要把本任务留在“已改未提交”状态交付给下一位 agent。
