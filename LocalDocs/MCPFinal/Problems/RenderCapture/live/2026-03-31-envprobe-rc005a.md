### 四、普通 Swift 进程环境探针

为排除“只有 PlayCover runtime 进程不支持”这一假设，本轮额外在 **普通 Swift 进程** 中直接执行：

- `MTLCaptureManager.shared().supportsDestination(.gpuTraceDocument)`
- `MTLCaptureManager.shared().supportsDestination(.developerTools)`
- `MTLCreateSystemDefaultDevice()?.name`

#### 1. 普通进程结果

```text
supports_gpu_trace=false
supports_developer_tools=false
default_device=Apple M4 Pro
```

#### 2. 带 `METAL_DEVICE_WRAPPER_TYPE=1` 结果

```text
supports_gpu_trace=false
supports_developer_tools=false
default_device=Apple M4 Pro
```

这说明：

- 即使完全脱离 PlayCover / runtime session / bridge，当前机器上的普通进程仍然看不到 `.gpuTraceDocument` 与 `.developerTools` 支持
- 社区案例里提到的 `METAL_DEVICE_WRAPPER_TYPE=1`，在本机上**不会改变**这一结果

### 五、安装态差异对照

本轮额外读取两款已安装 app 的 `Info.plist`：

- `QQ飞车`：`MetalCaptureEnabled == true`
- `原神`：**缺少** `MetalCaptureEnabled`

但它们当前 live 结果仍然完全一致：

- 都 `available=true`
- 都 `enabled=true`
- 都 `supports_gpu_trace=false`
- 都 `supports_developer_tools=false`
- 都 `failure_reason=gpu_trace_document_unsupported`

因此至少可以得出：

> **安装包里是否存在 `MetalCaptureEnabled` key，不足以解释本轮 `supports_gpu_trace=false` 的主症状。**

### 六、本轮结论

本轮已经拿到足够强的环境级证据：

1. 最新 `PlayCover.app`、最新 GUI MCP、最新真实 session 链路都正常
2. 两款真实 app 的 live 症状完全一致
3. 失败后 session 仍保持 `ready`，没有本轮新增 crash
4. **更关键的是：普通 Swift 进程里也同样得到 `supports_gpu_trace=false / supports_developer_tools=false`，且默认 Metal device 可见**

因此当前更可信的判断是：

> **阻塞点主要位于当前机器 / 当前 Xcode-Metal 运行环境对 `.gpuTraceDocument` / `.developerTools` destination 的支持策略，而不是 PlayCover MCP session 自身。**

### 七、对后续任务的影响

`RC-005` 本轮后可以认为已经达到“强证据支持的根因假设”完成标准。
