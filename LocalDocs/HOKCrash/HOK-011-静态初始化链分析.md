## HOK-011 静态初始化链分析

> 本文只沉淀 HOK-011 的**方法论**（`__common` 槽位 writer 扫描器 + 反向 call graph BFS）、**离线分析结论**（writer 在 NGR 自身 `__init_offsets` 上不可达）、**HOK-012 live-trace 的技术假设分类（H1/H2/H3）**与**HOK-012-B 给 LLDB 自动化引入的 watchpoint / stderr 重定向口径**。任务状态、某一轮 live run 是否已执行、下一步做什么，统一以 `LocalDocs/HOKCrash/00-Dashboard.md` 为准。

### 目标

- 回答"为什么候选 E 掩盖的那个 null deref 在 iOS 上不会发生，在 macOS/PlayCover 下会发生"。
- 只做离线静态分析：**不跑 app、不改 binary、不涉及 live**。
- 产出可复用的 store-site 扫描器与反向调用图方法论，后续再有 "某个 `__common` 槽位应该被谁写" 的问题可以直接复用。

### 证据收敛过程

#### 1. faulting callsite 的语义

HOK-007A 已确认 faulting PC = `0x10480df08: ldr x8, [x19]` / `x19 = 0`。faulting 指令所在函数入口是 `0x10480de8c`（`___lldb_unnamed_symbol272374`），是一个 stripped 的 anonymous 内部函数；ObjDump 有时把离 PC 最近的 exported symbol（如 `physx::PxVehicleConstraintShader::visualiseConstraint`）当作函数名显示，定位函数入口时以 `bl` 边与 prologue 为准、不依赖 ObjDump 的 symbol 标注。

#### 2. 锁定 caller 的参数来源

HOK-006 的 31 帧 backtrace 证明 faulting 发生在 `dyld findAndRunAllInitializers` 内部，frame #1 的 LR `0x1047e8444` 指向 caller 函数 `0x1047e83f4`。该函数的关键代码：

```
0x1047e8424: adrp x8, 0x10e214000
0x1047e8428: ldr  x0, [x8, #0x6f8]        ; x0 = *(0x10e2146f8)
0x1047e8440: bl   0x10480de8c             ; 调 faulting 函数
```

即 caller 直接从 `__common` 槽位 `0x10e2146f8` 读取对象指针，**没有任何 null 检查**。这是典型的"依赖别人先初始化好了"的代码。

#### 3. 定位 writer

- `0x10e2146f8` 位于 `__DATA,__common`（vmaddr `0x10e183f00` / size `0xe4128`），dyld 零填。
- `dyld_info -fixups` 没有任何 rebase/bind 指向这个地址——说明**它只能由运行时代码写入**。
- 用 `Scripts/hok011_ngr_common_init_chain.py` 以 `__init_offsets` 为扫描起点做 adrp+add+str 跟踪：**0 个命中**。
- 改为**全二进制 `__text`** 反汇编并以符号化 adrp/add/mov 状态跟踪扫所有 store（`str` / `stur` / `stp`）：**只找到 1 个 store 点**——`0x103a29f7c: str x0, [x8, #0x6f8]`，其中 `x8` 来自 `adrp 0x10e214000`。

#### 4. 反向 call graph：writer 在 `__init_offsets` 上不可达

- writer 指令位于函数 `0x103a29b7c` 内，该函数形式上是 `__cxa_guard_acquire` 保护的 Meyers-singleton accessor；其入口前有对 `0x10e1fc930`（guard byte）和 `0x10e1fc928`（singleton 指针）的标准双重检查锁定。
- `0x103a29b7c` 在整个 NGR `__text` 里只有 **5 个 `bl` 调用点**，5 个全部来自同一个函数 `0x107e5df10`（像是 Logger accessor）。
- `0x107e5df10` 在整个 NGR `__text` 里只有 **1 个 `bl` 调用点**。
- 该调用点的宿主函数**不属于 `__init_offsets`**。
- 以 `0x107e5df10` 为起点做反向 BFS（只沿 NGR 自身 `bl` 边），能到达的函数共 2 个，**其中没有任何一个属于 `__init_offsets`**。
- ⇒ **NGR 自身的 static initializer 链在任何顺序下都不会触发 writer**。

#### 5. 顺序验证（一致性交叉）

- `dyld_info -inits` 列出 3008 个 initializer，与手工 parse `__TEXT,__init_offsets` 一致。
- writer 宿主函数 `0x103a29b7c` 附近的唯一 init 入口是 `0x103a29958`（index 1006），但它是一个 5 指令 log-wrapper，不是 writer 路径。
- faulting caller `0x1047e83f4` 的所在 init 入口是 `0x10460e2c0`（index 1563），该 init 一路走到 frame#1 → frame#0 / faulting。
- 即使把"writer 宿主"硬算到 `__init_offsets[1006]`，它也确实排在 reader (`[1563]`) 之前；但由于 writer 宿主**不是 init 入口本身**，而是被更深层调用触发，这条 "1006 < 1563" 的顺序并没有被 dyld 自动兑现。

### 方法论产出（供后续任务复用）

- `Scripts/hok011_ngr_common_init_chain.py`：`__common` / `__data` 槽位 writer 扫描器；默认目标 `0x10e2146f8`，可通过 `--target-address` 切换。核心算法是 adrp+add+mov 的符号化状态机。
- `Scripts/test_hok011_ngr_common_init_chain.py`：11 个单元测试覆盖指令解码、`__init_offsets` 解析、scanner 命中/误报/提前停止行为。
- 反向 call graph + BFS 套路：
  1. `llvm-objdump --disassemble` 全二进制 dump；
  2. grep 所有 `stp xA,xB,[sp,#-0xNN]!` 风格 prologue，建立"地址 → 其宿主函数入口"的索引；
  3. grep 所有 `bl 0xXXXX` 指令，生成 `target → {caller_fn}` 的反向边；
  4. 从目标函数开始 BFS，求可达的 caller 集合；
  5. 和 `__init_offsets` / ObjC `+load` / `dyld_info -inits` 交叉比对。

### 已获取的辅助证据（非本任务核心，但相关）

- 裸跑 `DYLD_PRINT_INITIALIZERS=1 NGR` 时，dyld 会在 ObjC runtime 初始化阶段报告 **3 组 duplicate class warnings**：
  - `PxFrameworkLoader` in `PixUI_PXPlugin.framework` vs `PxKit3.framework`
  - `AReachability` in `GCloudCore.framework` vs `g6base.framework`
  - `PxDyLibFrameworkLoader` in `PxKit3.framework` vs **NGR main binary**
- ObjC runtime 在 macOS vs iOS 上对 duplicate class 的挑选策略受 dylib 加载顺序影响；这是 HOK-012 live-trace 必须观察的一个强候选维度。
- NGR 主二进制的 `+load` 方法只有 5 个（`KSCrash`、3 个 `MSDKPIXResUtils`、`WKWebView`），不太可能是 prime `0x10e2146f8` 的直接路径。

### 离线结论

- **`0x10e2146f8` 不可能由 NGR 自己的初始化链在 iOS 上 prime**——真正 prime 它的代码必然存在于**外部 embedded framework**（或极少数情况：系统 framework 的 `+load` 通过 `objc_msgSend` 回调 NGR）。
- 候选 E（HOK-007B）本质是"让 NGR 的 reader init 跨过 null deref"的 workaround，**没有**改变 `0x10e2146f8` 的最终 null 状态；候选 E apply 后 app 会暴露更下游的、依赖同一批 `__common` 槽位未初始化的问题。
- **要对齐 iOS 行为**，必须通过 live-trace 观察"哪个 image 的哪个 initializer / `+load` 真正 prime 了这个 slot"——这是 HOK-012 的技术路线起点。

### HOK-012 live-trace 方法论

#### 工具链（HOK-012-A / HOK-012-B 沉淀）

- **bundle-scoped 诊断 env**：`PlayApp.effectiveLaunchEnvironment()` 与 `LaunchService.effectiveLaunchEnvironment()` 对 `minimalStartupCompatBundleIdentifiers`（目前仅 `com.tencent.ngr`）注入 `DYLD_PRINT_INITIALIZERS=1` + `DYLD_PRINT_APIS=0`；两处共用 `minimalStartupCompatDiagnosticEnvironment` 常量，语义对齐。`DYLD_PRINT_APIS=0` 是**必要显式设置**，防止父终端的 `DYLD_PRINT_APIS=1` 污染 initializer 日志。
- **watchpoint 自动化**：MCP `launch_app_with_lldb` 支持可选入参 `watchAddress` / `watchSize` / `preRunCommands` / `dyldInitializersLogPath`；默认分支保持 HOK-006 的 "stop -> quit" 行为，watchpoint 模式切换为 "stop 抓 backtrace 后 continue" 循环，并用 `process launch -e <path>` 把子进程 stderr 重定向到指定文件。
- **Swift 解析器**：`LLDBRunOptions` / `WatchpointHit` / `parseWatchpointHits` 位于 `PlayCoverMCP/HostServices/Launch/LaunchService.swift`；`parseLLDBEvidence` 优先选择**非 watchpoint** 的 stop 作为 fault 字段，避免 watchpoint 命中污染 fault 归因。
- **Python 自动化**：`Scripts/hok006_ngr_lldb_runner.py` 新增 `--watch-address` / `--watch-size` / `--pre-run-command` / `--dyld-log` / `--watchpoint-report`；watchpoint 模式下默认写 `build/hok-012-ngr-watchpoint-report.json` 与 `build/hok-012-ngr-dyld-initializers.log`，并把 dyld log 尾部与 initializer 行数嵌入顶层报告的 `artifacts` 字段。

#### 标准 live-trace 命令

```
python3 Scripts/hok006_ngr_lldb_runner.py \
  --watch-address 0x10e2146f8 \
  --watch-size 8 \
  --skip-build-install
```

- 需保持候选 E 的 apply 状态，才能让 NGR 跑过 reader init 并观察下游 writer；revert 只在需要对比"无 patch 时 dyld / watchpoint 行为"时临时用。

#### writer image 与假设分类

将 watchpoint 命中结果与 dyld initializer 日志对齐，识别出 writer 所在的 image：

- 若命中的是 **embedded framework initializer** → **H1**：在 PlayTools 里预触发同一个函数即可。
- 若命中的是 **ObjC `+load`** → **H2**：确认 PlayTools 是否需要调整 ObjC runtime 环境（DYLD 环境变量、framework 加载顺序等）。
- 若命中的是 **跨 dylib C++ static ctor 链** → **H3**：考虑用 `DYLD_INSERT_LIBRARIES` 或 PlayTools 层 `dlopen(force-init)` 提前触发。
- 若 watchpoint 从未命中（app 从头到尾这个 slot 都是 0，只是之前 `QtsFileSystem` 阶段又崩了）→ 候选 E 视为长期方案，主线回到 `HOK-010`（摘除 `rootWorkDir` gate）。

#### 口径说明

- **watchpoint 模式的 timeout 行为**：capture window 到期后的 `process interrupt` + `thread backtrace all` 会完整 flush transcript；`timedOut=true` 不降级 watchpoint 命中证据。
- **fault 字段优先级**：`parseLLDBEvidence` 在 watchpoint 模式下仍然能正确归因真正的 fault（`EXC_BAD_ACCESS` 之类），因为它会跳过所有 `stop reason = watchpoint …` 行。
- **stderr 重定向的局限**：`process launch -e <path>` 只覆盖 child 自身的 stderr，若 child 内部又 `posix_spawn` 出孙进程，孙进程的 dyld 环境不会继承该重定向；遇到这种场景需退回到 shell 层 tee stderr 的方案。
