# 当前问题清单

## P01：`install_ipa` 的 MCP 路径与 GUI 原生安装路径行为不一致

### 状态

- **状态**：进行中
- **优先级**：高
- **类型**：产品行为不一致 / 安装链路问题

### 现象

对以下 IPA 通过当前可用的 `playcover` MCP 端点执行 `install_ipa`：

- IPA：`/Users/songdogwang/Downloads/NSS_Debug_Test_DB_1.55.0.36877_1828878_12136_enterprise_sign_forpay.ipa`

得到结果：

- `install_ipa` 返回：`task-1`
- `list_tasks` 可见该任务
- `get_task(task-1)` 最终返回：
  - `state = failed`
  - `error.code = -32015`
  - `error.message = MachO conversion failed: No ARM64 architecture found in fat binary`

但用户明确反馈：**相同 IPA 通过 PlayCover 图形化界面安装是可以成功的**。

### 本轮证据

#### 1. MCP 长任务主路径工作正常

本轮已确认：

- `install_ipa` 可以正常发起长任务
- `list_tasks` / `get_task` 可以正常观测任务状态
- 错误信息已经能通过标准 tool 路径直接拿到，不再需要绕过到原始 JSON-RPC

也就是说，这次问题**不是 task 能力不可观测**，而是**安装链路本身的最终行为与 GUI 不一致**。

#### 2. 当前 MCP 路径的稳定失败结果

任务终态如下：

```text
state = failed
code = -32015
message = MachO conversion failed: No ARM64 architecture found in fat binary
```

#### 3. GUI 路径的反证

用户反馈：同一 IPA 在 GUI 中可以安装成功。  
这直接说明：当前不能再把该 IPA 简单定性为“必然无 ARM64 / 必然不兼容”的稳定负例。

### 当前判断

更合理的结论是：

1. `PlayCoverMCP/HostServices/Install/InstallerService.swift` 与 GUI 原生 `PlayCover/AppInstaller/Installer.swift` **很可能没有完全走同一套语义**
2. 差异点可能在：
   - 可执行文件定位
   - Mach-O 架构预检
   - 转换前后的二进制筛选逻辑
   - PlayTools 注入开关与分支差异
   - GUI 路径额外容错，而 MCP 路径没有

### 影响

- 当前 `install_ipa` 不能被视为与 GUI 安装等价
- 会让使用 MCP 的自动化测试者拿到**比 GUI 更严格或不同步**的安装结果
- 现有“把该 IPA 当成稳定负例”的测试结论需要回退重审

### 建议排查

1. 对比 `InstallerService.swift` 与 `PlayCover/AppInstaller/Installer.swift` 的主链路差异
2. 记录 GUI 成功安装该 IPA 时的关键日志，与 MCP `task-1` 失败日志并排比对
3. 明确产品语义：到底应该以 GUI 结果为准，还是以 MCP 结果为准
4. 在结论明确前，不再把该 IPA 当成“稳定不兼容样本”写入固定回归预期

## P02：旧文档中的 raw TCP 手测步骤已与当前 GUI MCP 形态不一致

### 状态

- **状态**：进行中
- **优先级**：中
- **类型**：文档 / 手测 SOP 过期

### 现象

旧的 `LocalDocs/MCPWithGUITask/G04-MCPManager生命周期管理.md`、`G08-端到端集成测试.md` 等文档仍以：

- `nc localhost 19820`
- 发送 raw JSON-RPC initialize

作为 GUI 内嵌 MCP 的手测步骤。

但本轮真实环境中，PlayCover GUI 暴露的是：

- `streamable HTTP MCP`
- 端点：`http://127.0.0.1:19820/mcp`

### 本轮证据

#### 1. 当前 HTTP 端点工作正常

本轮已成功完成：

- `Scripts/test_http_mcp.sh`
- `WITH_REGRESSION=1` 的完整 HTTP MCP 回归
- `CLI stdio initialize` 回归

并确认：

- `initialize`
- `tools/list`
- `resources/list`
- SSE primer event
- task / security 校验

都能在 HTTP 端点下正常工作。

#### 2. 旧 raw TCP 路径返回错误

本轮直接对 `127.0.0.1:19820` 发送旧式 raw initialize，请求得到：

```text
HTTP/1.1 400 Bad Request
```

这说明当前 19820 端口已经不是旧文档假设的“纯行分隔 raw TCP JSON-RPC”手测入口。

### 影响

- 后续测试者如果继续照旧文档用 `nc` 做 initialize，会误判为 GUI MCP 失效
- 会浪费排查时间在错误的 transport 假设上
- `G04/G08/G07` 的部分手测说明需要与当前 HTTP MCP 现实对齐

### 建议处理

1. 把 GUI 手测主路径统一改成 `http://127.0.0.1:19820/mcp`
2. 将 `Scripts/test_http_mcp.sh` 作为当前推荐冒烟脚本
3. 在旧文档中显式标注：raw TCP 手测步骤已过期，不再代表当前 GUI MCP 形态

## 附：本轮重要环境注意事项（暂不单列为产品 bug）

### E01：残留 `PlayCoverMCP` CLI 占用 `52741` 会导致 GUI 路径 `create_session` 超时

本轮一度出现：

- GUI 内嵌 MCP 在 `19820` 正常监听
- 但 `52741` 的 runtime 注册监听被旧的 `/tmp/PlayCover-DerivedData/Build/Products/Release/PlayCoverMCP` 进程占用
- 结果：`create_session(timeout=30)` 对 `原神` 持续超时

清理残留 CLI 并重启 GUI 后：

- `19820` 与 `52741` 均回到同一个 `PlayCover.app` 进程持有
- `create_session(timeout=45)` 成功
- 后续 `tap` / `swipe` / `press_key` / `type_text` / `toggle_debug_overlay` / `long_press` / `drag` 均再次通过

### 结论

这更像是**测试环境冲突**而非当前稳定产品 bug，但它对 live 回归影响很大，后续必须先排除。
