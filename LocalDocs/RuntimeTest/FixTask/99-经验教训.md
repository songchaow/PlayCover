## RuntimeTest FixTask 经验教训

> 本文档给后续 agent 使用。  
> **维护规则**：每次任务完成后，都要结合现有内容做整合、去重、优化；不要按 task 机械追加流水账。

---

### 一、先判断是真 bug、假设不成立，还是“诊断不够清楚”

这轮问题里至少有三类情况：

1. **真实实现缺失**：例如 runtime `BridgeListener` 还是骨架、host 没启动 `RegistrationListener`
2. **协议 / 工具层不一致**：例如 `tasks/get` 参数形状、任务通知 method、tool 层没暴露 task 查询
3. **产品体验问题，不一定是底层逻辑 bug**：例如无 ARM64 的 IPA 被拒绝本身可能合理，但当前失败太晚、信息不清楚

后续 agent 在改代码前，先判断属于哪一类，不要把“应该改进诊断”误当成“必须强行支持不兼容输入”。

---

### 二、session / runtime 问题一定要看三层，不要只盯一个函数

`create_session` 失败，不代表只要改 `SessionService.createSession(...)` 就行。至少要同时检查：

1. **host bootstrap**：`MCPManager.swift`、`PlayCoverMCP/main.swift` 是否真的启动了 listener / monitor
2. **host runtime bridge infrastructure**：`RegistrationListener.swift`、`SessionRegistry.swift`、`SessionHealthMonitor.swift`
3. **runtime side**：`Carthage/Checkouts/PlayTools/.../BridgeListener.swift` 是否真正实现、是否真的被 `PlayCover.launch()` 接入

如果只改其中一层，真实 app 链路通常仍然不通。

另外，真实回归时一定要确认是不是 **fresh launch**：

- 如果 host 侧 `PlayCover` 重启了，但被测 app 旧进程还活着，runtime 往往不会自动重新注册
- 此时 `create_session(timeout=20/30)` 仍可能超时，但这不等于当前 host listener 代码坏了
- 要先看 `lsof -iTCP:52741`、`list_sessions`、app 进程状态，再决定是否需要先重启 app

否则很容易把“旧进程没有重注册”误判成“本轮代码回归失败”。

---

### 三、GUI 与 CLI 有两套入口，凡是 server bootstrap 相关改动都要双查

当前服务注册逻辑至少在两处：

- `PlayCover/Services/MCPManager.swift`
- `PlayCoverMCP/main.swift`

后续 agent 只改其中一处，很容易出现：

- GUI 测得通，CLI 不通
- CLI 测得通，真实 GUI 不通

凡是涉及 tool 注册、session 基础设施、task 能力暴露的改动，都要双查两条入口是否一致。

特别地，**`RegistrationListener` 和 `SessionHealthMonitor` 也属于 session 基础设施的一部分**。它们必须在 GUI（`MCPManager.registerServices`）和 CLI（`main.swift`）两条启动路径中同时创建和启动，并在退出/stop 时正确清理。CLI 入口还需要通过 `SIGINT`/`SIGTERM` 信号处理来确保清理逻辑被执行。

在 GUI 入口中，`logger` 是 `Optional`（因为 `stop()` 会置 nil），因此所有日志调用必须使用可选链 `logger?.log(...)`，不能直接访问。闭包中引用时需 `[weak self]` 避免循环引用。

---

### 四、改 `Carthage/Checkouts/PlayTools/` 后，单元测试通过不代表真实 app 已生效

runtime 相关代码在 `Carthage/Checkouts/PlayTools/` 下。  
这类改动常见误区是：

1. 本地 Swift 测试过了
2. host fake runtime 测试过了
3. 就误以为真实注入 app 已经在跑新代码

实际仍需确认：

- `PlayTools.xcodeproj` 已把新增 runtime 文件纳入 `PlayTools` target；**源码文件存在不等于 framework 工程真的会编它**
- PlayTools 被重新构建
- `Carthage/Build/PlayTools.xcframework/ios-arm64/PlayTools.framework` 已被新构建产物替换；**当前 GUI 构建默认复制的是这份预编译 framework，而不是直接吃 `Carthage/Checkouts/PlayTools/` 源码**
- 目标 app 被重新注入 / 重装 / 重签
- 真实 app 进程里跑到的是新 bridge 代码
- **至少单独构建一次 `PlayCover` app scheme**，但不要把“`PlayCover` 能 build 通过”误判成“runtime 新源码已进入 live framework”；这两件事不是一回事

必要时还要检查 `.gitignore` 是否把 `PlayTools.xcodeproj/project.pbxproj` 之类的关键工程文件挡掉，否则本机修好以后，仓库里仍然留不住 target membership 变更。

否则会看到“代码已经改了，但 live 行为还是旧的”。

---

### 五、先补复现测试，再做修复，尤其是“看起来像缓存”的问题

例如 keymap 删除后回读残留，表面像缓存问题，但不能只凭直觉改。  
正确顺序应是：

1. 先写稳定复现测试
2. 再定位是 config、磁盘、缓存、通知还是 GUI observer 的问题
3. 修完后用同一个测试锁住回归

这类问题如果不先补测试，后面很容易“看起来修好了，但下一轮又回来”。

而且不要把验证只限制在 `delete_keymap`：本轮真实原神回归证明，`rename_keymap` 成功后首次 `list_keymaps` 也可能仍返回旧名。  
因此后续测试至少要覆盖：

- create → rename → immediate list
- create → rename → get_keymap(旧名/新名)
- delete → immediate list
- delete → get_keymap(not found)

这样才能把“真实状态已变、但列表缓存未刷”的问题完整锁住。

另外，如果某个 live 问题在后续 fresh / headless 回归里已经**连续不再复现**，要及时把结论从“稳定复现”降级成“条件复现待补证据”，并写清楚这次回归时 GUI 相关页面是否打开、是否已有旧缓存、是否是 fresh session。否则很容易让后续排查继续围着已经失效的复现路径打转。

---

### 六、先抓原始输入 / 输出，再改解析逻辑

针对 entitlements、codesign、installer 预检这类问题，优先保留原始证据：

- 原始 `codesign` 输出
- 原始 plist / JSON / task result
- 原始错误 message

不要在没看原始数据前就重写解析逻辑，否则很容易把“输入格式兼容性问题”误改成“业务语义变化”。

---

### 七、无效 IPA 的正确修复方向是“更早失败、报错更清楚”——但前提是先确认 GUI / MCP 路径结论一致

对于**已经确认**缺少 ARM64 的 IPA，正确目标通常不是“让它也能安装”，而是：

1. 更前置地发现问题
2. 给出可操作的错误信息
3. 让调用方能通过标准 task / tool 路径直接看到根因

这能显著降低后续人工测试和问题定位成本。

但 2026-03-30 夜间 live 复核也说明：**不要只因为 MCP 路径报了 `No ARM64 architecture found in fat binary`，就直接认定 IPA 本身一定不兼容。** 如果用户或 GUI 路径对同一 IPA 能安装成功，应优先把问题升级为：

- GUI 与 MCP 是否走了不同安装器实现
- 预检 / Mach-O 转换 / 注入步骤是否存在分支差异
- 哪条路径才代表产品想要的真实语义

否则很容易把“安装链路实现不一致 bug”误判成“测试包本身无效”。

---

### 八、协议修正优先让规范路径成为默认，再决定要不要兼容旧形状

像 `tasks/get` / `tasks/cancel` 这类 JSON-RPC 接口，最稳妥的做法不是继续围绕历史输入形状写文档，而是：

1. 先把**规范路径**定成默认实现（例如对象参数 `taskId`）
2. 再评估旧输入形状是否可以低成本兼容
3. 最后把错误提示、测试、文档一起切到新主路径

否则很容易出现“代码支持 A，文档写 B，测试还在锁 C”的三向漂移。

---

### 九、所有任务完成后，都要把“新增验证方式”沉淀到文档或测试里

这轮已经证明：只靠聊天记录保留测试路径非常容易丢。  
后续 agent 新发现的有效验证方法，要么补进：

- 单元测试 / 集成测试
- 脚本
- `FixTask` 文档

至少要落一个地方，不能只停留在临时操作里。

另外，像真实 app 冒烟这类依赖本机 MCP / GUI 环境的验证，在开跑前要先确认端点本身可达；如果环境先挂了（例如 `playcover` MCP 直接 `fetch failed`），要明确记录为**环境阻塞**，不要把“验证没跑起来”误记成“代码仍然无效”。

---

### 十、长任务能力不能只停留在底层 method，标准 tool 路径也要可达

像安装、导出这类长任务，如果底层只有 `tasks/get` / `tasks/list` / `tasks/cancel`，但标准 `tools/call` 路径拿不到等价能力，真实 MCP 使用者依然会卡在“任务开始了，但后面怎么看”。

后续凡是新增长任务能力，至少同步检查四件事：

1. 是否有可直接调用的标准 tool 包装
2. 返回文案是否指向实际可用的 tool 名称，而不是只写底层 method
3. 失败时是否保留了对调用方有意义的专用错误码 / 错误类型，而不是被更大的兜底错误吞掉
4. GUI / CLI 两条入口是否都完成了注册与回归验证

---

### 十一、重装 / 重启 GUI 后，要把 HTTP MCP 会话当成全新服务处理

本轮最终 live 回归里，重新执行 `./BuildScripts/build_and_install.sh` 并重启 `PlayCover.app` 后，旧的 `Mcp-Session-Id` 会立即失效；如果客户端继续复用旧 session，服务端会返回 `Invalid or expired session ID`。

因此后续 agent 做 GUI live 回归时，要注意三点：

1. 只要重装、重启 `PlayCover.app`，或切换 transport，就先重新 `initialize`，不要直接沿用旧 session 调工具
2. 如果目标是验证“新代码是否已经真正生效”，要先确认命中的是新 GUI 进程，再用**新 session**重跑关键 tool
3. 遇到 `Invalid or expired session ID` 时，优先判断是不是会话已失效，不要立刻误判成业务逻辑又回归失败
