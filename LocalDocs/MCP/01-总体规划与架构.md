### 目标

把 `PlayCover` 中现有的宿主侧控制能力与运行时输入能力，整理并实现为一套**可测试、可持续迭代、可由多个 agent 串行推进**的 MCP Server。

### 总体架构决策

#### 一、Server 形态

采用**新的本地命令行 target**：`PlayCoverMCP`

原因：

- MCP 最自然的本地接入方式是 `stdio`
- 命令行 target 比把协议层塞进主 app 更容易测试
- 后续可以新增 `PlayCoverMCPTests` 做自动化测试

#### 二、工程组织

规划中的代码布局建议如下：

- **`PlayCoverMCP/`**
  - MCP transport / protocol
  - tool registry
  - resource registry
  - task manager
  - logging adapter
- **`PlayCoverMCP/HostServices/`**
  - 对 `PlayCover` 现有宿主能力做服务封装
- **`PlayCoverMCP/Session/`**
  - session registry
  - host/runtime bridge client
- **`PlayCoverMCPTests/`**
  - unit tests
  - integration tests
  - MCP smoke tests
- **`Scripts/`**（如有需要）
  - 本地 MCP 冒烟脚本
  - fixture 生成脚本

#### 三、Host 与现有代码的关系

优先策略：

- **优先新建薄服务层包装已有 `PlayCover` 逻辑**
- **避免一开始做大规模源码迁移**
- 如确实需要共享逻辑，再逐步下沉公共服务

#### 四、Session Bridge 方案

当前运行时输入能力在 `PlayTools` 进程内，缺 host -> runtime 桥。规划采用：

- **host 侧**：`PlayCoverMCP` 管理 session registry 与命令发送
- **runtime 侧**：在 `PlayTools` 中增加轻量 bridge listener
- **传输**：优先采用**本机 loopback TCP + JSON 消息**
- **发现机制**：runtime 启动后向 host 注册 `sessionId / bundleId / pid / port`

选择 loopback TCP 的原因：

- 对同机跨进程通信足够简单
- 调试可观测性更好
- 比临时拼 UI 事件或 AppleScript 通道更稳定

### MCP 协议能力规划

#### 必备能力

- **`tools`**：所有动作型接口
- **`resources`**：状态快照、会话状态、任务状态
- **`logging`**：执行过程日志
- **`tasks`**：安装、导出、重签名、注入等长任务

#### 首选 transport

- **`stdio`**

先把本地 CLI server 跑通，再考虑是否需要其他 transport。

### 测试策略摘要

每个任务都至少要满足以下之一：

- **自动化单元 / 集成测试**
- **MCP 级冒烟测试**
- 如果无法自动化，必须给出**明确原因**与**可重复的人工验证步骤**

但总体目标是：**尽量自动化，不把验证责任甩给后续 agent。**

### 风险清单

- **工程层风险**：当前仓库只有 `PlayCover` app target，没有现成 test target
- **复用层风险**：现有很多能力带 UI 假设，MCP 需要改造成 headless 服务
- **runtime 风险**：`PlayTools` 是注入侧代码，bridge 设计要尽量轻量与可回滚
- **测试风险**：部分真实 IPA / 已安装 app 场景很难全自动，需要 fixture 与 fake service 双线验证
- **vendor 风险**：Session 相关改动可能涉及 `Carthage/Checkouts/PlayTools`，需要控制变更面
