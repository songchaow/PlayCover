## 现状调研与缺口

## 文档职责

本文只回答三类问题：

1. 语义验证为什么是一个独立问题
2. 现有工程链路已经提供了哪些证据
3. 当前缺口分别属于哪一层

**任务状态、进展、优先级、TODO、完成判定与默认执行顺序统一只在 `00-Dashboard.md` 维护。** 本页不重复这些动态控制面信息。

## 已有基础

### 1. 目标始终是“语义等价”

这里的目标不是“源码可见”、不是“能重新编译”，也不是“文本差异变少”，而是尽量建立一条**可信、可解释、可回归**的语义证据链。

因此当前默认把证据分成几层：

- `round-trip` 闭环证据
- canonical compare + 风险分级证据
- compile posture / runtime-like compile 证据
- 行为级补充证据
- 真实场景后置证据

这些证据都重要，但没有哪一层可以单独替代全部语义判断。

### 2. 工程主链路已经具备

现有工程链路已经覆盖：

- `BitcodeModule.data` 获取与样本落盘
- `llvm-dis` 反汇编
- `IRToMSLConverter` 生成 MSL
- `SharedCompilePlanner.swift` 提供 compile posture 单一决策
- `corpus_replay_runner.py` / `ir_semantics_roundtrip_runner.py` 驱动单模块离线闭环
- `aggregate_replay_runner.py` 驱动多模块 aggregate 离线验证
- `metal_aggregate_compile_harness.swift` 提供 `MTLDevice.newLibraryWithSource(...)` 形态的最小 runtime-like compile
- canonical compare、风险分级、gate 报告与行为 / live 辅助工具

因此当前重点不是重新搭基础设施，而是把这些现成能力组织成**稳定的方法标准**。

### 3. 已有证据类型已经足够丰富

仓库中已经具备的证据类型包括：

- 单模块 `IR -> MSL -> AIR -> IR` round-trip 报告
- `compare-summary.json` / `risk-report.json` / `gate-summary.json`
- compile posture 结构化字段，例如：
  - `originalFastMathMode`
  - `inferredMetalArgs`
  - `effectiveMetalArgs`
- aggregate compile summary 字段，例如：
  - `fastMathMode`
  - `fastMathDecision`
  - `usesExplicitCompileOptions`
  - `compileOptionsFastMathEnabled`
  - `explicitOverrideSource`
- `gate-summary.json` 中的 `layeredDecision`
- L3 / L4 的行为与真实场景辅助脚本

这些能力已经足以支撑一条**offline-first、报告优先、按需升级**的验证路线。

## 缺口分类

### A. 结构化证据仍然不是语义证明

即使 `original.ll` 与 `regenerated.ll` 在文本、统计或结构摘要上很接近，也仍然只能说明“风险较低”或“差异可解释”，不能直接等同于行为一致。

因此默认要把：

- 文本 / 结构相似
- 风险分级
- compile posture 对齐
- runtime-like compile 复核
- 行为 / 真实场景确认

拆成不同层次处理。

### B. 默认入口必须保持自动化与可复跑

真正的工程难点不只是“能不能跑一个样本”，而是：

- 能否让显式 `.ll`、`ShaderCorpus`、`ShaderSourceDiagnostics`、aggregate replacement 都进入结构化报告体系
- 能否避免把 GUI、人工登录、人工准备环境、人工枚举路径写回默认流程
- 能否让报告而不是口头描述成为事实载体

这属于**证据规模化与自动化边界**问题。

### C. compile posture 与 runtime-like compile 是独立证据面

单模块 `xcrun metal -c` 闭环能回答很多问题，但它不等于 runtime 真值。当前方法上需要明确区分：

- 单模块 round-trip：默认、低成本、批量入口
- aggregate `mtl-device` compile：多模块 / compile posture / runtime-like 问题的补充证据

也就是说，compile 是否成功、compile 用了什么 posture、runtime-like backend 会如何解释同一份 aggregate 源码，属于不同证据层。

### D. 行为级证据仍是独立层

L1/L2 更像“低成本、可批量的风险筛查器”；L3 才开始回答“固定输入下行为是否一致”。因此行为级验证应被视为按需升级的独立能力，而不是让 L1/L2 承担它本来不该承担的语义承诺。

### E. 真实场景验证需要单独治理

`.gputrace`、render diff、runtime replacement、真实 app 验证都属于高成本证据。它们有价值，但环境依赖、样本依赖和人工依赖更强，因此必须单独定义进入条件与确认规则。

## 为什么“文本一致”不是终点

语义验证需要区分：

- **文本 / 结构近似**：提供强线索
- **compile posture / runtime-like compile 一致**：提供更贴近执行宿主的工程证据
- **行为 / 语义一致**：需要更高层证据补足

因此当前默认顺序是：

1. 先做 `round-trip`
2. 再做 canonical compare 与风险分级
3. 若问题涉及 compile posture / aggregate，再补 runtime-like compile 证据
4. 只有在必要样本上，才升级到行为级或真实场景验证

## 对路线设计的启示

从问题本身推导出的长期原则是：

- **先离线，再按需升级到行为或真实场景**
- **canonical compare 是任务入口，报告是事实主源**
- **单模块 round-trip 是默认低成本闭环；aggregate 问题优先补 `mtl-device` runtime-like compile 证据**
- **不要把 `xcrun metal -c` 的成功直接当成 runtime 真值**
- **涉及 PlayCover 构建、重建、安装时，必须使用 `BuildScripts/` 标准脚本**
- **高层验证用于补证，不用于跳过低层验证**
