## Install IPA Fail：问题来龙去脉与后续收敛方向

### 一、文档目的

本文用于沉淀 `install_ipa` 安装失败问题的完整上下文，包括：

- **问题是如何暴露出来的**
- **为什么 GUI 可以安装而 MCP 会失败**
- **当前已经确认到什么程度**
- **为什么当前实现会分叉成两套安装逻辑**
- **后续应如何按 GUI 原本的成熟实现进行收敛**

本文的核心原则只有一条：

> **后续 `install_ipa` 的实现应尽量对齐 GUI 原本那套已经稳定运行很久的安装语义，而不是继续扩张 MCP 自己的独立安装分支。**

---

### 二、问题背景

#### 1. 用户侧现象

用户反馈同一个 IPA：

- 通过 **PlayCover GUI 原生安装** 可以成功
- 通过 **GUI 内嵌 MCP 的 `install_ipa`** 会失败

失败时的典型任务错误为：

```text
MachO conversion failed: No ARM64 architecture found in fat binary
```

#### 2. 当前工程形态

当前 PlayCover MCP 的最终形态不是单入口，而是：

- **GUI 入口**：`PlayCover/Services/MCPManager.swift`
- **CLI 入口**：`PlayCoverMCP/main.swift`

这两条入口都要暴露 MCP 能力，因此安装逻辑需要既能服务 GUI，也能服务 CLI / tests / headless 场景。

#### 3. 已知关键事实

在本次排查前，已经有一个非常重要但尚未被工程化落地的事实：

- **GUI 原生安装长期稳定**
- **MCP 的 `InstallerService` 是后续补出来的 headless 安装实现**
- 两者虽然功能目标相近，但并没有完全走同一套底层语义

这意味着：

- 当前问题不应被简单理解成“某个 IPA 本身不兼容”
- 更合理的判断是：**MCP 安装链路与 GUI 安装链路在实现细节上出现了分叉，且分叉处存在真实 bug**

---

### 三、本次调查结论

#### 1. 两条安装链路确实不是同一实现

本次对比确认：

- GUI 原生安装核心在 `PlayCover/AppInstaller/Installer.swift`
- MCP 安装核心在 `PlayCoverMCP/HostServices/Install/InstallerService.swift`

虽然两者都在做“解压 IPA → 找到 app → 处理 Mach-O → 注入 / 签名 → 安装”，但并不是同一个底层实现。

#### 2. GUI 安装链路与 MCP 安装链路的主要差异

GUI 原生路径主要依赖：

- `Installer.swift`
- `Macho.swift`
- `PlayTools.swift`
- `Entitlements.swift`
- `PlayApp.sign()`

MCP 路径则主要依赖：

- `InstallerService.swift`
- `MCPShell.swift`
- 自己实现的 fat Mach-O 解析 / slice 提取 / version command 修改 / dylib 替换

#### 3. GUI 那套为什么更可信

GUI 原生安装路径有两个优势：

- **历史时间更长**：已经被真实用户使用很久
- **能力更完整**：不仅做安装，还同时处理了 GUI 侧长期沉淀下来的签名、entitlements、PlayTools 注入、信息修补等语义

因此，在两套实现出现冲突时，应优先把 **GUI 视为事实上的正确参考实现**。

---

### 四、为什么现在会出现“两套安装实现”

#### 1. 两套入口本身是合理的

当前 MCP 需要同时支持：

- **GUI 内嵌 HTTP MCP**
- **CLI stdio MCP**

因此，工程上保留两套入口是合理的：

- GUI 负责产品运行态与设置页、状态页、HTTP transport
- CLI 负责 stdio、最小测试闭环、无 GUI 的工具场景

#### 2. GUI 安装器本身带有明显的交互式依赖

GUI 的 `Installer.install(...)` 并不是一个纯业务内核，它依赖很多 GUI 侧语义，例如：

- `NSAlert` 询问是否安装 `PlayTools`
- `InstallPreferences` 读取安装偏好
- `ModifierKeyObserver` 判断是否按下 Option
- `InstallVM.shared` 上报 GUI 进度
- `checkOfficialMacOS()` 触发面向用户的提醒逻辑

这些依赖说明：

- GUI 安装器**不能被 MCP 直接原样调用**
- 至少需要一层 **headless / no-UI 适配层** 来承载 CLI 与 MCP 场景

#### 3. 现在的问题不在于“两套入口”，而在于“两套安装内核”

这里必须区分两个概念：

- **两套入口**：合理，应该保留
- **两套安装算法 / 两套底层安装语义**：不理想，应逐步收敛

当前真正的问题是：

> **为了做 headless MCP，工程新增了 `InstallerService`；但它没有仅仅作为 GUI 安装器的无头适配层，而是又复制出了一套独立的 Mach-O / 注入 / 签名实现。**

这一步就是后续产生行为偏差的根源。

---

### 五、本次问题的直接根因

#### 1. 真实复现结果

本次 live 验证中，已经成功在最新 PlayCover GUI 上复现：

- 启动最新 GUI
- 通过 GUI 内嵌 HTTP MCP 调 `install_ipa`
- 任务推进到 `converting ...`
- 随后失败，报错：

```text
MachO conversion failed: No ARM64 architecture found in fat binary
```

#### 2. 核心根因

本次确认到的最直接 bug 在 `InstallerService.swift` 中的 fat Mach-O 解析逻辑。

具体表现为：

- `inspectMachOArchitectures()` / `parseFatArchitectures()` 对 `CAFEBABE` 的解析采用了 **big-endian** 语义
- 但 `stripFatBinary()` 的 fat header 读取却没有完全遵守同一套端序语义
- 结果造成：
  - `nfat_arch` 可能读错
  - `cputype` 可能读错
  - `slice offset / size` 可能读错
  - 最终误报为 **“fat binary 中没有 ARM64”**

这说明：

> **同一个 `InstallerService` 文件内部，fat Mach-O 的“预检解析逻辑”和“真实截取逻辑”本身就不一致。**

这不是 IPA 本身的问题，而是 MCP 自己安装实现里的真实解析错误。

#### 3. 次级问题

同时还发现：

- `replaceVersionCommand()` 中 `mach_header_64` 的字段偏移读取也有问题
- 这不一定是本次 ARM64 误判的直接来源，但会影响后续 load command 解析稳定性

因此，本次修复把该问题一起处理了。

---

### 六、本次已经完成的修复与验证

#### 1. 已完成修复

本次对 `InstallerService.swift` 做了两个直接修复：

- **修正 fat Mach-O 的端序解析与 slice 边界检查**
- **修正 thin Mach-O header 中 `ncmds` / `sizeofcmds` 的偏移读取**

#### 2. 已完成测试

本次已完成以下验证：

- `InstallerServiceTests` 全量通过
- 新增 fat ARM64 回归测试，确认不会再错误报出：
  - `No ARM64 architecture found in fat binary`

#### 3. 已完成 live 验证

本次已完成以下 live 验证：

- 成功构建并安装最新 `PlayCover.app`
- 成功启动 GUI，并确认：
  - `19820` 为 GUI MCP HTTP 端口
  - `52741` 为 runtime 注册端口
- 用 GUI 内嵌 MCP 成功安装：
  - 一个小型真实 IPA 样本
  - 一个**带真实 fat framework 的轻量复现包**

这说明：

> **本次修复已经直接打掉了原来那条 fat binary 解析失败路径。**

#### 4. 当前仍需保留的边界结论

对于完整的大型真实 IPA：

- 本次重新验证时曾长时间停留在 `unzip`
- 当前判断更像是大包 I/O / 解压耗时问题，而不是这次 fat Mach-O 解析 bug 的继续表现

因此，当前状态应理解为：

- **原始报错路径已经被有效修复**
- **完整超大包仍建议继续做一次完整 end-to-end 关单验证**

### 七、新增收敛结果：PlayTools / entitlements / QQ飞车 大包回归

#### 1. `QQ飞车` 真实大包已完成 end-to-end 安装回归

在后续继续验证中，已使用真实 IPA：

- `NSS_Debug_Test_DB_1.56.0.36637_1827436_12421_enterprise_sign_forpay.ipa`

通过最新 GUI 内嵌 MCP 再次完成完整安装任务，`install_ipa` 最终成功返回：

- `bundleIdentifier = com.tencent.tmgp.speedmobile`
- `appPath = ~/Library/Containers/io.playcover.PlayCover/Applications/com.tencent.tmgp.speedmobile.app`
- `injectPlayTools = true`

这说明：

> **原始的 `install_ipa` 安装失败问题已经不再阻塞真实 `QQ飞车` 大包安装。**

#### 2. UI 惊叹号 / “未安装 PlayTools” 问题已经定位并打通

后续 live 排查确认：

- GUI 侧 `PlayApp.hasPlayTools()` 的判断标准是：
  - **主可执行文件中存在真实的 `LC_LOAD_DYLIB -> PlayTools.framework/PlayTools`**
- MCP 原始安装实现一度只有 `rpath` 语义
- 这会导致：
  - MCP 自己曾误判“已安装 PlayTools”
  - 但 GUI UI 仍显示惊叹号和“此应用并未安装 PlayTools”

本轮收敛后，已经确认新版 GUI 内嵌 MCP 安装出的 `QQ飞车` 同时满足：

- `check_playtools_installed == true`
- `otool -L` 中可见真实的：
  - `/Users/.../Library/Frameworks/PlayTools.framework/PlayTools`
- 应用包内已复制：
  - `PlugIns/AKInterface.bundle`
  - `en.lproj/Playtools.strings`
  - `zh-Hans.lproj/Playtools.strings`

这说明：

> **`PlayTools` 的“注入”和“检测”语义已经和 GUI 原实现重新对齐，UI 惊叹号对应的底层根因已被解决。**

#### 3. 新发现的签名分叉点：MCP 不能简单保留 IPA 原始 entitlements

继续用真实 `QQ飞车` 大包做启动验证时，又发现一个更深的 GUI / MCP 分叉点：

- 若 MCP 安装链路在最终签名时**直接保留 IPA 原始 entitlements**
- 对于企业签 / 分发包这类样本，可能会把以下受限键原样带入 ad-hoc 签名结果：
  - `application-identifier`
  - `com.apple.developer.team-identifier`
  - `keychain-access-groups`

这样虽然 `codesign --verify` 可能表面通过，但在真实启动路径上，`amfid` 仍会拒绝：

```text
Restricted entitlements not validated, bailing out.
The signature on the file is invalid
```

这再次证明：

> **MCP 安装链路不能把“保存原始 entitlements + 原样重签”当成 GUI 等价语义。**

#### 4. 新增修复：GUI 内嵌 MCP 最终签名切到 PlayCover 原生语义

为继续向 GUI 原实现收敛，本轮新增了一步非常关键的修复：

- 给 GUI target 增加 `PLAYCOVER_GUI` 编译标记
- 在 `InstallerService.swift` 中：
  - **GUI target 下最终签名优先走 `PlayCover` 原本的 entitlement 组合逻辑**
  - 即复用 `PlayApp` / `Entitlements.composeEntitlements(...)` 那套成熟语义
- CLI target 继续保留原有 fallback，避免破坏无 GUI 构建

修复后的重新安装结果已确认：

- `QQ飞车` 最终 entitlements 已不再是 IPA 原始 restricted 组合
- 而是切回 PlayCover 常规的 sandbox / TCC / sbpl 组合语义

这说明：

> **MCP 的 GUI 内嵌安装路径已经开始在“最终签名语义”上真正收敛到 GUI 原实现，而不再只是表面共享流程。**

#### 5. `QQ飞车` 当前剩余问题已被收缩为“更后段兼容性退出”

在上述两类问题修复后，再次验证 `QQ飞车` 启动行为时，可确认：

- 之前的 `dyld` 缺库问题：
  - `MobileCoreServices.framework` 缺失
  - 可通过启用 `iosFrameworks` 路径绕过
- 之前的 `amfid` restricted entitlements 拒绝：
  - 已不再出现
- 当前最新状态：
  - `launch_app` 仍返回 `launched = true`
  - 进程未稳定留存
  - 没有产生新的 `speedmobile-*.ips` crash 文件
  - 近期日志也不再出现前述两类早期硬错误

因此当前边界应更新为：

> **安装链路、PlayTools 状态、最终签名语义都已经过关；`QQ飞车` 尚未持续运行，剩余问题更可能属于应用自身兼容性 / 更后段运行时退出，而不是本问题最初的 `install_ipa` 安装失败。**

### 八、为什么说这次修复是“建设性的，但不是最终形态”

#### 1. 为什么是建设性的

因为它修的是一个真实根因，而不是绕过：

- 不是放宽校验
- 不是跳过失败
- 不是对某个 IPA 特判
- 而是修正了 `InstallerService` 内部明确错误的 fat Mach-O 解析实现

#### 2. 为什么还不是最终形态

因为当前最大结构性问题仍然存在：

- GUI 有一套成熟安装内核
- MCP 仍然保留一套独立安装内核

也就是说，本次修复虽然把一个真实 bug 打掉了，但**没有从架构层面消除 GUI / MCP 安装行为分叉**。

---

### 八、后续方向：原则上向 GUI 原本实现收敛

本问题的后续方向，应明确以下原则：

> **MCP 不应继续维护一套与 GUI 长期并行发展的独立安装算法。后续应保留 GUI / CLI 双入口，但逐步收敛到 GUI 原本已经稳定运行很久的那套安装内核。**

换句话说：

- **入口可以有两套**
- **安装内核应尽量收敛为一套**

---

### 九、推荐的目标形态

#### 1. 应保留的部分

应继续保留：

- GUI bootstrap：`MCPManager.swift`
- CLI bootstrap：`PlayCoverMCP/main.swift`
- MCP 的 tool / task / transport / session 基础设施

这些是产品形态与接入方式的差异，不是问题本身。

#### 2. 应收敛的部分

应逐步把以下安装相关底层能力收敛到 GUI 成熟实现上：

- **Mach-O 识别与转换**
- **fat binary slice 提取**
- **加密检测**
- **PlayTools 注入语义**
- **AKInterface / 相关资源复制逻辑**
- **entitlements 组合逻辑**
- **最终签名语义**
- **Info.plist 修补语义**

原则上：

- GUI 已经长期跑稳的实现，应成为默认真相源
- MCP 应优先复用 GUI 的稳定实现，而不是继续做自己的平行重写

---

### 十、推荐的工程落地方式

#### 方案原则

推荐不是“让 MCP 去直接调用 GUI 的交互式 `Installer.install(...)`”，而是：

> **从 GUI 安装器中抽出“无 UI 的稳定安装内核”，让 GUI 和 MCP 都调用同一套底层实现。**

#### 目标分层

建议未来把安装逻辑拆成三层：

##### A. 共享安装内核层（推荐新增 / 抽取）

职责：

- 只负责纯安装语义
- 不依赖 `NSAlert`
- 不依赖 `SwiftUI`
- 不依赖 `ObservableObject`
- 不依赖 GUI 单例状态

这一层应优先吸收 GUI 当前成熟能力，例如：

- `Macho.swift`
- `PlayTools.swift` 中稳定的注入逻辑
- `Entitlements.swift`
- `PlayApp.sign()` 里的签名语义
- GUI 安装中关于 `Info.plist`、`MinimumOSVersion`、`MetalCaptureEnabled` 的处理

##### B. GUI 适配层

职责：

- 负责用户交互
- 负责读取 `InstallPreferences`
- 负责弹窗
- 负责 `InstallVM` 进度更新
- 负责将用户偏好映射为安装参数

GUI 继续保留原有产品体验，但不再自己维护另一套独立安装算法。

##### C. MCP / CLI 适配层

职责：

- 接收工具参数
- 提供完全 headless 的默认值
- 将进度回调映射到 `TaskManager`
- 负责 tool result / task result / error 包装

MCP 需要的是 **headless adapter**，而不是另一套安装内核。

---

### 十一、推荐实施步骤

#### 第一步：冻结 GUI 语义为参考标准

先明确：

- 当前 GUI 安装路径是参考真相源
- 后续若 GUI 与 MCP 结果冲突，默认以 GUI 语义为对齐目标

#### 第二步：逐项识别 MCP 与 GUI 的分叉点

建议重点核对并收敛以下差异：

1. `MachO` 处理是否复用 GUI 的 `Macho.swift`
2. `PlayTools` 注入是否复用 GUI 的成熟语义
3. `AKInterface` 与资源复制逻辑是否一致
4. `entitlements` 是否采用 GUI 的组合逻辑，而不是简单保留原值
5. 最终签名是否与 GUI 保持一致
6. `Info.plist` 修改是否与 GUI 保持一致

#### 第三步：把 GUI 稳定逻辑抽成共享内核

目标不是让 `PlayCoverMCP` 依赖 GUI View 层，而是把 GUI 当前安装能力里“真正成熟的业务部分”抽出来，成为：

- GUI 可调用
- MCP 可调用
- CLI 可调用
- tests 可调用

的共享内核。

#### 第四步：让 `InstallerService` 退化成适配层

理想状态下，未来的 `InstallerService` 应只保留：

- 参数解析
- 默认值
- progress callback
- error 映射
- task 状态回传

而不再持有自己的独立 Mach-O / 注入 / 签名实现。

#### 第五步：补齐回归验证

收敛过程中必须补齐以下验证层次：

- GUI 原生安装验证
- GUI 内嵌 MCP `install_ipa` 验证
- CLI 下 headless 安装验证
- 小样本 IPA 验证
- 含真实 fat frameworks 的复现包验证
- 完整大包真实 IPA end-to-end 验证

---

### 十二、不推荐的方向

以下方向不推荐：

#### 1. 继续在 `InstallerService` 里加越来越多独立补丁

如果继续沿当前模式做：

- 遇到一个差异修一个差异
- GUI 改一点，MCP 再补一点
- GUI 稳定逻辑不复用，MCP 自己重写一遍

那么未来几乎必然继续出现：

- GUI 通，MCP 不通
- 某些 IPA GUI 能装，MCP 不能装
- MCP 修了一个样本，又冒出另一个样本

#### 2. 直接把 GUI 的交互式安装器原样暴露给 MCP

这也不推荐，因为 GUI 安装器当前本身包含：

- 弹窗
- 用户偏好
- GUI 进度状态
- 交互式判断

MCP 需要的是 **可 headless 运行的稳定安装内核**，而不是把这些 GUI 依赖硬塞进 tool 调用路径。

---

### 十三、当前建议的优先级

#### P0：保持当前 tactical fix

当前已修复的 fat Mach-O 解析 bug 应保留，不应回退。

因为它对应的是 `InstallerService` 中已经确认存在的真实错误。

#### P1：尽快开始“向 GUI 语义收敛”的重构

这比继续堆更多样本补丁优先级更高。

#### P2：完成完整超大 IPA 的最终 live 回归

在当前修复已通过轻量真实复现验证的前提下，再补上完整大包 end-to-end 结果，作为问题关闭依据。

---

### 十四、结论

本问题的来龙去脉可以总结为：

1. `install_ipa` 在 MCP 路径下失败，并不是简单的 IPA 不兼容问题
2. 根因是 MCP 自己维护了一套与 GUI 长期分叉的安装实现
3. 本次已经确认并修复了其中一个真实根因：fat Mach-O 解析错误
4. 该修复已经通过测试与 live 轻量复现验证，属于**建设性的战术修复**
