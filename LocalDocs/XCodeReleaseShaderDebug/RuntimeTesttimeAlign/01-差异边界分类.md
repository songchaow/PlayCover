## 差异边界分类

## 文档职责

本文只记录 `RTA-002` 的**差异边界分类结论**：哪些差异必须继续对齐，哪些属于 backend / 输入形态 / 执行宿主差异而有意保留。

**任务状态、优先级、TODO 与完成判定统一只在 `00-Dashboard.md` 维护。** 本页不重复动态控制面。

## 判定原则

默认按下面三条判断是否要继续收口：

1. **会不会改变 compile decision 本身**：同一组 original IR 输入下，若 runtime 与离线会因为规则来源、posture 决策或 aggregate 形态不同而得到不同的“该不该编 / 用什么 compile posture 编”的结论，就属于必须对齐。
2. **会不会改变 aggregate replacement source 的真实语义形态**：模块顺序、函数去重、preflight yes/no 这类差异若会影响最终拼出的 MSL 源码或 compile 成败，也属于必须对齐。
3. **是否只是 backend-specific 执行宿主 / 产物 / 诊断表现不同**：若差异只影响 `xcrun` / `MTLDevice` / host bridge / CLI diagnostics 的执行方式与落盘产物，而不改变共享输入语义与 compile summary 结论，则允许有意保留。

补充规则：

- 当前被归为“有意保留”的差异，**只要开始稳定制造新的 blocked sample / `L3`**，就必须重新升级为“必须对齐”。
- 当前统一范围仍优先聚焦 dashboard 已定义的三层：`fast-math` compile posture、compile preflight、aggregate 形态；超出这三层的 compile option 或工具链差异，默认先作为观察项，而不是立即扩成新的统一面。

## 当前结论总览

### 必须继续对齐的差异

| 差异面 | 当前结论 | 原因 | 现有证据 |
|---|---|---|---|

| `fast-math` compile posture 决策语义 | **必须对齐** | 同一组 original IR 不能在 runtime 走显式 `MTLCompileOptions.fastMathEnabled=false`，而离线又被裸 `xcrun metal -c` 回编成 `air.compile.fast_math_enable` | `RTA-001.1` / `RTA-001.4.1` / `RTA-001.4.2` 已完成；`CC-003.8` full-batch 已验证 corpus `L3 54 -> 7`、diagnostics `L3 1 -> 0` |
| aggregate source 形态：模块顺序 | **必须对齐** | aggregate 拼源顺序会影响“哪个重复函数先出现、最终保留哪个模块”，属于 runtime-like source shape，不是可随意不同的日志字段 | runtime 在 `buildAggregateReplacementSource(...)` 中按 `preparedModules` 顺序拼源；`replacement.meta.json` 的 `moduleKeys` 是稳定排序后的身份字段，不等于拼源顺序；离线通过 `resolve_manifest_capture_order(...)` 恢复 capture 顺序，且 `test_aggregate_replay_runner.py` 已覆盖 |

| 上游 `entry 参数` 残余高风险 family | **必须继续收口** | 这批 residual 仍然表现为 `entry 参数个数变化 + entry 参数类型摘要变化 + entry 参数语义摘要变化`，会直接留在 `L3` / blocked 层，不能被当作 backend 差异放过 | `CC-003.8` 收掉 compile posture 后，corpus 剩余 `7` 个 `L3` 已全部收敛到这支 family；这就是 `RTA-003` / `CC-003.9` 的直接输入 |

### 有意保留的差异

| 差异面 | 当前结论 | 为什么可以保留 | 备注 |
|---|---|---|---|
| compile 执行 backend 本身 | **有意保留** | runtime 真实路径是 `MTLDevice.newLibraryWithSource(...)`；离线仍可保留 `xcrun metal -c` 作为 AIR / CLI diagnostics 补充入口 | 统一的是 decision layer，不是强行把 runtime 和离线都改成同一个 backend |
| `MTLCompileOptions` 的拥有权 | **有意保留在 Swift runtime / harness** | `MTLDevice` backend 的 compile posture 决策天然属于 Swift 侧；Python 重建一份 runtime-like `MTLCompileOptions` 只会制造漂移 | `aggregate_replay_runner.py` 只做 orchestration；`metal_aggregate_compile_harness.swift` 持有 runtime-like posture 决策 |
| backend-specific 产物形态 | **有意保留** | `xcrun` 天生产出 `airPath`；`mtl-device` 天生产出 `backendReportPath` 与 `libraryFunctionNames`；它们不是同类产物 | 当前只要求 compile summary 语义对齐，不要求产物一一同形 |
| CLI-specific diagnostics / failure clustering / baseline diff | **有意保留在 Python `xcrun` backend** | 这部分是离线诊断增强，不是 runtime compile decision 的一部分 | `COMPILE_FAILURE_CATEGORY_RULES`、compiler diagnostics 提取、AIR baseline diff 继续只服务 `xcrun` |
| runtime `LLVMDisassembler` host bridge 与离线 `llvm-dis` CLI | **有意保留** | 这是执行宿主差异：runtime 需要绕开 injected app sandbox 的 `process-fork` 限制；离线直接用本机 `llvm-dis` 更简单稳定 | 只要差异没有把风险抬成 blocked sample，就不单独把两套反汇编宿主再做统一工程 |
| `target triple / data layout`、SDK / 编译器版本残余 | **默认有意保留，只作记录** | `04-L2-CanonicalCompareAndRiskGrading.md` 已明确：这些字段可记录，但通常不单独作为阻断依据 | 若未来证明它们会稳定制造 compile blocker，再升级回必须对齐 |
| 仅 instruction-level 的 fast-math residual | **有意保留在当前范围外** | 当 compile option 与 function attr 已对齐后，只剩 instruction flags 统计变化时，当前 compare 口径把它视为 `L1` 观察项 | 不应为了这类 residual 重新放大 compile posture 主线 |
| preflight reject 后的 side effect | **有意保留** | runtime 需要返回 original library、写 `RuntimeLaunchDiagnostics`、保留 dump；离线只需要结构化 JSON 报告与失败归类 | 必须统一的是“reject 不 reject”的判断，不是 reject 之后的宿主行为 |
| 非 `fast-math` compile option 的更广统一 | **当前暂不纳入统一范围** | dashboard 当前只把 compile posture 统一重点收口到 `fast-math`；没有证据表明更广 compile option 已经成为当前 blocked 杠杆 | 若后续 canonical compare 证明它们制造新的 `L3` / blocked，再单独升级 |

## 当前最重要的边界解释

### 1. 不要把 `replacement.meta.json` 的 `moduleKeys` 误当成 aggregate 拼源顺序

runtime 在 replacement 落盘时，会把：

- `moduleKeys` 写成稳定排序后的身份字段
- `moduleSummaries` 保留 `preparedModules` 的真实顺序
- aggregate source 本体按 `preparedModules` 顺序拼接

因此：

- `replacement.meta.json` 更像**身份与归档字段**
- `manifest.jsonl` 里的 capture 顺序才更接近 aggregate source 的真实模块顺序
- 离线 aggregate runner 必须优先恢复 capture 顺序，不能只消费稳定排序后的 `moduleKeys`

### 2. preflight 必须统一“决策”，不必统一“后处理”

当前必须对齐的是：

- 哪些 token / pattern 会把 source 判成 invalid
- 遇到 invalid source 时，是否继续进入 compile

当前允许不同的是：

- runtime 返回 original library 还是离线返回结构化失败状态
- dump 文件、日志、diagnostics 组织方式

换句话说，**同一份 aggregate source 的 preflight yes/no 必须一致；但 reject 后怎么记录、怎么回退，可以保留宿主差异。**

### 3. `xcrun` 不是 runtime 真值，`mtl-device` 才是更接近 runtime compile 结论的入口

当前边界已经很明确：

- 若目标是判断“runtime compile 在同样 aggregate source 下会不会过”，优先看 `Scripts/aggregate_replay_runner.py --compile-backend mtl-device`
- 若目标是拿 AIR、看 CLI diagnostics、做 failure clustering / baseline diff，继续使用 `xcrun`

因此不能再把：

- `xcrun metal -c` 的通过
- `llvm-dis` 的文本结果

直接当成 runtime compile truth。

## 何时重新打开“有意保留”的边界

只有满足下面任一条件，才应把当前“有意保留”的差异重新升级为新的统一任务：

- 它开始稳定制造新的 `blockedSamples` 或 `L3`
- 它改变了 aggregate source 的真实形态或 compile yes/no 结论
- 它迫使 runtime 与离线再次手写两份高频规则表
- 它让 `fastMathMode` / `fastMathDecision` / `usesExplicitCompileOptions` 这类 shared summary 字段无法再稳定对应

## 与后续工作的关系

这份边界分类文档后续主要服务两类判断：

- **判断某个 residual 是否需要继续收口**：如果它会改变 compile yes/no、aggregate source 真实形态，或开始稳定制造新的 `blockedSamples` / `L3`，就应归入“必须继续对齐”。
- **判断某个差异是否仍可保留为 backend-specific 行为**：如果它只影响执行宿主、产物形态、diagnostics 组织方式，而不改变共享输入语义与 compile summary 结论，就继续归入“有意保留”。

在后续分析中，尤其应持续用这份文档来约束下面两类问题：

- `entry 参数个数变化 + entry 参数类型摘要变化 + entry 参数语义摘要变化` 这类仍停留在 blocked 层的 residual family
- compile planner 共享化之后，哪些 backend-specific 行为仍然允许保留，哪些已越界成新的决策层分叉
