## 从 MCP Phase 0-1 继承的关键教训

以下教训来自 `LocalDocs/MCP/08-经验教训与常见陷阱.md`，在本轮工作中同样适用：

1. **pbxproj 修改极其危险**：使用三步验证（plutil → git diff → build），脚本中动态查找 ID
2. **测试 target 需同步添加源文件**：新增 .swift 必须同时加入业务 target 和测试 target
3. **先确认架构可行性再写代码**：先验证 target 依赖、API 签名，再动手
4. **小步验证**：每次改动后立即构建
5. **filter 语义是"保留"**：移除元素时条件取反
6. **脚本使用绝对路径**：避免相对路径的 cwd 问题

## G01：Shell 命名冲突解决

1. **replace_in_file 处理重复代码段时需注意**：InstallerService.swift 的 `install()` 和 `export()` 方法结构非常相似，包含几乎相同的代码行（如 `try Shell.run("/usr/bin/unzip", ...)` 等）。使用 `replace_in_file` 时，如果 `old_str` 在文件中出现多次，替换会失败。解决方案：使用 `sed` 命令进行全局替换更加可靠。

2. **sed 替换要小心双重替换问题**：如果先用 `replace_in_file` 成功替换了部分 `Shell.` → `MCPShell.`，再用 `sed` 全局替换 `Shell.` → `MCPShell.`，会导致已替换的 `MCPShell.` 中的 `Shell.` 被再次替换为 `MCPMCPShell.`。应该先确认哪些替换已生效，或者从一开始就统一使用 `sed`。

## G02：MCP 源文件集成到 GUI Target

1. **Swift WMO 不允许同 target 同名文件**：即使两个文件内的类型名不同（`Shell` vs `MCPShell`），WMO（Whole Module Optimization）编译器仍然不允许同一 target 中有两个同名 `.swift` 文件。报错：`filename "Shell.swift" used twice`。G01 只改了类名但没改文件名，G02 需要把 `Shell.swift` 重命名为 `MCPShell.swift`。

2. **`SYSTEM_FRAMEWORK_SEARCH_PATHS` 会覆盖 SDK 系统框架路径**：PlayCover GUI 设置了 `SYSTEM_FRAMEWORK_SEARCH_PATHS = "/System/Library/PrivateFrameworks"`，这导致 `import Network` 时从 PrivateFrameworks 中错误加载了一个不完整的 Network.framework（缺少 nw_object.h）。解决方案：改为 `FRAMEWORK_SEARCH_PATHS` 而非 `SYSTEM_FRAMEWORK_SEARCH_PATHS`，让系统公共框架的搜索保持默认优先级。

3. **pbxproj 脚本解析需注意 section 边界，优先用 replace_in_file**：同一个 ID 在 pbxproj 中会出现在多个 section（如 PBXBuildFile 和 PBXSourcesBuildPhase 同时引用）。Python 脚本按 ID 匹配时容易定位到错误 section，把条目插入到错位置。**推荐方案**：直接用 `replace_in_file` 工具匹配包含上下文的多行文本，在 4 个位置（PBXBuildFile、PBXFileReference、PBXGroup、PBXSourcesBuildPhase）分别插入一行，比脚本更精确、更不容易出错。（G02/G03/G04 均验证了此结论）

4. **GUI target 编译验证需绕过环境依赖**：PlayCover GUI 依赖 Carthage（需安装）和代码签名（需 provisioning profile），缺失时构建会失败但不影响代码正确性。用 `FASTLANE=1` 跳过 Carthage Bootstrap 脚本，`CODE_SIGNING_ALLOWED=NO` 跳过签名。编译成功的标志是 Swift 编译 + 链接产出了可执行文件，而非 BUILD SUCCEEDED（后续脚本阶段可能因环境问题失败）。（G01 发现问题，G02 给出具体解决方案）

5. **使用独立 DerivedData 避免缓存污染**：Yams 仓库包含一个 `BUILD` 文件（Bazel），在 macOS 不区分大小写文件系统上会与 Xcode 需要创建的 `build` 目录冲突。使用 `-derivedDataPath /tmp/...` 可以绕过此问题。

## G03：TCPTransport 实现

1. **NWConnection.start() 后不能立即 scheduleReceive()**：`NWConnection.start(queue:)` 是异步的，连接 ready 之前调用 `receive()` 可能导致数据丢失或异常。正确做法是在 `stateUpdateHandler` 中检测到 `.ready` 状态后再开始 `scheduleReceive()`。

2. **XCTest 的 `waitForExpectations` 会等待所有未完成的 expectations**：如果在一个测试方法开头创建 expectation A，中间创建 expectation B，第一个 `waitForExpectations` 会同时等待 A 和 B。如果 A 需要经历多个阶段才能完成，应该在上一个 `waitForExpectations` 之后再创建下一阶段的 expectation。

3. **AnyCodable 初始化在 WMO 模式下可能被推断为 throwing**：在 PlayCoverMCPTests target 的 WMO（Whole Module Optimization）模式下，`AnyCodable(["key": "value"])` 可能被编译器推断为调用 `init(from decoder: Decoder) throws` 而非 `init(_ value: Any?)`。解决方案：显式声明参数类型为 `Any?`（如 `let dict: Any? = ["key": "value"] as [String: Any]; AnyCodable(dict)`），或在辅助方法中预构建。

4. **TCP 行分隔协议的测试请求必须以 `\n` 结尾**：测试中发送 JSON-RPC 请求时，必须在末尾加 `\n`，否则 TCPTransport 的行分割逻辑不会处理这条消息。使用多行字符串字面量时尤其容易忘记。

5. **PlayCover.app 没有 App Sandbox**：TCP 监听 loopback 不需要额外的 entitlement（`com.apple.security.network.server`），因为 PlayCover.app 未启用 App Sandbox。

## G04：MCPManager 生命周期管理

1. **TCPTransport 的 `init` 不会 throw**：G04 文档模板中的代码示例使用了 `try TCPTransport(port:handler:)`，但实际 TCPTransport 的 init 不是 throwing（NWListener 的创建在 `start()` 的异步回调中）。实际实现中不需要 `do/catch` 包裹 init。

2. **使用 `onStateChange` 回调而非直接设置 `isRunning`**：由于 `TCPTransport.start()` 是异步的（通过 DispatchQueue），在 `start()` 返回时监听器尚未就绪。正确做法是通过 `onStateChange` 回调在 `.running` 状态时才设置 `isRunning = true`，这样 UI 状态反映的是真实的监听状态。

3. **Services 目录已存在**：`PlayCover/Services/` 目录已有 `NotifyService.swift` 和 `SoundDeviceService.swift`，无需在 pbxproj 中新建 PBXGroup，只需在现有 group 中添加子项。

## G05：GUI-MCP 状态联动

1. **方案 A（无条件 post）是最简单且无副作用的选择**：NotificationCenter 在没有 observer 时 post 通知是完全无害的 no-op。不需要设置标志位区分 GUI 模式和 CLI 模式，代码更简洁。

2. **通知发送使用 `DispatchQueue.main.async` 包裹**：MCP Service 方法运行在 TCP transport 的后台 DispatchQueue 上，而 GUI 的 `@Published` 属性必须在主线程修改。虽然 `addObserver(forName:queue:.main)` 会自动切换到主线程执行回调，但在发送端也用 `DispatchQueue.main.async` 双重保障，并封装为 `MCPNotificationPoster` 辅助类，Service 调用更简洁。

3. **通知名文件放在 MCP 目录（`PlayCoverMCP/Common/`）更合适**：因为通知的发送方是 MCP Service，文件放在 MCP 目录中自然被 PlayCoverMCP 和 PlayCoverMCPTests target 编译。同时通过 target membership 也编译进 PlayCover GUI target。如果放在 `PlayCover/` 目录，CLI target 和 Tests target 反而不方便引用。

4. **Settings 和 Keymaps 通知的 userInfo 可携带 bundleID**：当前实现传递了 `bundleID` 作为 userInfo，为未来 GUI 侧做精确刷新（只刷新受影响 app 的设置/键位映射）预留了接口。当前 `mcpSettingsChanged` 和 `mcpKeymapsChanged` 在 GUI 侧尚未有 observer（AppsVM 只监听 `mcpAppsChanged`），但通知基础设施已就位，G06 或后续任务可按需添加。

## G06：UI 状态指示

1. **TCPTransport 的连接数变化回调应派发到主线程**：`onClientCountChanged` 回调在 TCP 的串行 DispatchQueue 上触发，但 MCPManager 的 `@Published` 属性必须在主线程更新。因此回调内部需要 `DispatchQueue.main.async` 包裹，与 `onStateChange` 保持一致的设计模式。

2. **Settings TabView 添加新 tab 只需改 PlayCoverSettingsView.swift**：Settings 页面使用标准 SwiftUI `TabView`，添加新 tab 只需在 `Tabs` 枚举中加一个 case，在 body 中加一个 tab 项即可，不需要改动 `PlayCoverApp.swift`。

3. **MCPStatusView 无需在 MCP CLI/Tests target 中编译**：这是纯 GUI 视图文件，只需添加到 PlayCover target，不需要像 MCP 源文件那样双 target 编译。

4. **本地化字符串 fallback 机制**：macOS 的本地化系统会自动 fallback 到英文，所以只需要在 en/zh-Hans/zh-Hant 三个主要语言文件中添加新字符串，其他语言使用英文 fallback 即可。
