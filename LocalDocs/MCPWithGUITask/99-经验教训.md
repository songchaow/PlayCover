## 从 MCP Phase 0-1 继承的关键教训

以下教训来自 `LocalDocs/MCP/08-经验教训与常见陷阱.md`，在本轮工作中同样适用：

1. **pbxproj 修改极其危险**：使用三步验证（plutil → git diff → build），脚本中动态查找 ID
2. **测试 target 需同步添加源文件**：新增 .swift 必须同时加入业务 target 和测试 target
3. **先确认架构可行性再写代码**：先验证 target 依赖、API 签名，再动手
4. **小步验证**：每次改动后立即构建
5. **filter 语义是"保留"**：移除元素时条件取反
6. **脚本使用绝对路径**：避免相对路径的 cwd 问题

## G01：Shell 命名冲突解决

1. **replace_in_file 处理重复代码段时需注意**：InstallerService.swift 的 `install()` 和 `export()` 方法结构非常相似，包含几乎相同的代码行（如 `try Shell.run("/usr/bin/unzip", ...)` 等）。使用 `replace_in_file` 时，如果 `old_str` 在文件中出现多次，替换会失败。解决方案：使用 `sed` 命令进行全局替换更加可靠。

2. **sed 替换要小心双重替换问题**：如果先用 `replace_in_file` 成功替换了部分 `Shell.` → `MCPShell.`，再用 `sed` 全局替换 `Shell.` → `MCPShell.`，会导致已替换的 `MCPShell.` 中的 `Shell.` 被再次替换为 `MCPMCPShell.`。应该先确认哪些替换已生效，或者从一开始就统一使用 `sed`。

3. **GUI target 的签名和 Carthage 问题**：PlayCover GUI target 构建可能因 provisioning profile 缺失或 Carthage 依赖未配置而失败，这是环境问题，不影响代码正确性判断。关键是确认 Swift 源码编译阶段无错误。

## G02：MCP 源文件集成到 GUI Target

1. **Swift WMO 不允许同 target 同名文件**：即使两个文件内的类型名不同（`Shell` vs `MCPShell`），WMO（Whole Module Optimization）编译器仍然不允许同一 target 中有两个同名 `.swift` 文件。报错：`filename "Shell.swift" used twice`。G01 只改了类名但没改文件名，G02 需要把 `Shell.swift` 重命名为 `MCPShell.swift`。

2. **`SYSTEM_FRAMEWORK_SEARCH_PATHS` 会覆盖 SDK 系统框架路径**：PlayCover GUI 设置了 `SYSTEM_FRAMEWORK_SEARCH_PATHS = "/System/Library/PrivateFrameworks"`，这导致 `import Network` 时从 PrivateFrameworks 中错误加载了一个不完整的 Network.framework（缺少 nw_object.h）。解决方案：改为 `FRAMEWORK_SEARCH_PATHS` 而非 `SYSTEM_FRAMEWORK_SEARCH_PATHS`，让系统公共框架的搜索保持默认优先级。

3. **pbxproj 脚本解析需注意 section 边界**：同一个 ID 在 pbxproj 中会出现在多个 section（如 PBXNativeTarget 中引用 build phase ID，PBXSourcesBuildPhase 中定义 build phase）。解析时必须先定位到正确的 section（`/* Begin PBXSourcesBuildPhase section */` 到 `/* End PBXSourcesBuildPhase section */`），否则会匹配到错误位置。

4. **GUI target 编译验证需绕过环境依赖**：PlayCover GUI 依赖 Carthage（需安装）和代码签名（需 provisioning profile）。可以用 `FASTLANE=1` 跳过 Carthage Bootstrap 脚本，用 `CODE_SIGNING_ALLOWED=NO` 跳过签名。编译成功的标志是 Swift 编译 + 链接产出了可执行文件（检查 .o 文件数和二进制大小），而非 BUILD SUCCEEDED（后续脚本阶段可能因环境问题失败）。

5. **使用独立 DerivedData 避免缓存污染**：Yams 仓库包含一个 `BUILD` 文件（Bazel），在 macOS 不区分大小写文件系统上会与 Xcode 需要创建的 `build` 目录冲突。使用 `-derivedDataPath /tmp/...` 可以绕过此问题。

## G03：TCPTransport 实现

1. **pbxproj 修改用 replace_in_file 比 Python 脚本更安全**：Python 脚本中使用 `insert_after` 按 ID 匹配时，同一个 ID 可能出现在 PBXBuildFile section 和 PBXSourcesBuildPhase section 中。脚本的第一次匹配会定位到 PBXBuildFile section，导致把 Sources build phase 条目插入到错误位置。直接使用 `replace_in_file` 工具匹配包含上下文的多行文本更精确。

2. **NWConnection.start() 后不能立即 scheduleReceive()**：`NWConnection.start(queue:)` 是异步的，连接 ready 之前调用 `receive()` 可能导致数据丢失或异常。正确做法是在 `stateUpdateHandler` 中检测到 `.ready` 状态后再开始 `scheduleReceive()`。

3. **XCTest 的 `waitForExpectations` 会等待所有未完成的 expectations**：如果在一个测试方法开头创建 expectation A，中间创建 expectation B，第一个 `waitForExpectations` 会同时等待 A 和 B。如果 A 需要经历多个阶段才能完成，应该在上一个 `waitForExpectations` 之后再创建下一阶段的 expectation。

4. **AnyCodable 初始化在 WMO 模式下可能被推断为 throwing**：在 PlayCoverMCPTests target 的 WMO（Whole Module Optimization）模式下，`AnyCodable(["key": "value"])` 可能被编译器推断为调用 `init(from decoder: Decoder) throws` 而非 `init(_ value: Any?)`。解决方案：显式声明参数类型为 `Any?`（如 `let dict: Any? = ["key": "value"] as [String: Any]; AnyCodable(dict)`），或在辅助方法中预构建。

5. **TCP 行分隔协议的测试请求必须以 `\n` 结尾**：测试中发送 JSON-RPC 请求时，必须在末尾加 `\n`，否则 TCPTransport 的行分割逻辑不会处理这条消息。使用多行字符串字面量时尤其容易忘记。

6. **PlayCover.app 没有 App Sandbox**：TCP 监听 loopback 不需要额外的 entitlement（`com.apple.security.network.server`），因为 PlayCover.app 未启用 App Sandbox。

## G04：MCPManager 生命周期管理

1. **TCPTransport 的 `init` 不会 throw**：G04 文档模板中的代码示例使用了 `try TCPTransport(port:handler:)`，但实际 TCPTransport 的 init 不是 throwing（NWListener 的创建在 `start()` 的异步回调中）。实际实现中不需要 `do/catch` 包裹 init。

2. **使用 `onStateChange` 回调而非直接设置 `isRunning`**：由于 `TCPTransport.start()` 是异步的（通过 DispatchQueue），在 `start()` 返回时监听器尚未就绪。正确做法是通过 `onStateChange` 回调在 `.running` 状态时才设置 `isRunning = true`，这样 UI 状态反映的是真实的监听状态。

3. **Services 目录已存在**：`PlayCover/Services/` 目录已有 `NotifyService.swift` 和 `SoundDeviceService.swift`，无需在 pbxproj 中新建 PBXGroup，只需在现有 group 中添加子项。

4. **pbxproj 修改 replace_in_file 很安全**：对于只添加一个新文件的场景，使用 `replace_in_file` 工具在 4 个位置（PBXBuildFile、PBXFileReference、PBXGroup、PBXSourcesBuildPhase）分别插入一行，比用 Python 脚本更简单、更直观、更不容易出错。
