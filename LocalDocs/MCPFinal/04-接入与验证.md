## PlayCover MCP 接入与验证

### 一、GUI 接入（推荐）

当前推荐接入方式是 **PlayCover GUI 内嵌 HTTP MCP**。

#### 1. 默认端点

```text
http://127.0.0.1:19820/mcp
```

#### 2. 在哪里看当前端点

GUI 中的 `Settings` → `MCP` 页面会显示：

- 当前 transport
- 可复制 endpoint
- 实际监听地址
- 当前连接 / session 数

对应文件：`PlayCover/Views/Settings/MCPStatusView.swift`

#### 3. transport 选择建议

- **优先 HTTP**
- 仅在兼容场景或旧系统上使用 TCP
- 不要把 `0.0.0.0` 当作客户端复制用 endpoint；对客户端应继续使用 `127.0.0.1`

### 二、CLI 接入

CLI 模式仍然保留，入口为 `PlayCoverMCP`。

适用场景：

- 本地 stdio MCP 客户端
- 不依赖 GUI 的最小测试环境
- 回归验证 CLI 未被 GUI HTTP 方案破坏

### 三、优先使用 `BuildScripts`

`BuildScripts/` 已经把常用的构建、安装、测试流程标准化，默认封装了：

- ad-hoc 签名参数
- `FASTLANE=1`
- 本地 `build/` 产物目录
- 统一 scheme / destination 配置

因此，后续接入与验证应**优先使用现成脚本**，而不是重新手写 `xcodebuild` 命令。

#### 1. 常用脚本

| 脚本 | 用途 |
|---|---|
| `BuildScripts/build_gui.sh` | 构建 PlayCover GUI |
| `BuildScripts/build_mcp.sh` | 构建 PlayCoverMCP CLI |
| `BuildScripts/test_mcp.sh` | 运行 MCP 单元测试 |
| `BuildScripts/build_and_install.sh` | 构建 GUI 并安装到 `~/Applications` / `/Applications` |
| `BuildScripts/build_all.sh` | GUI + CLI + MCP tests 全量回归 |
| `BuildScripts/build_for_testing.sh` | 只构建测试 target |
| `BuildScripts/test_without_building.sh` | 不重编译直接重复跑测试 |
| `BuildScripts/lint_pbxproj.sh` | 做 `pbxproj` 语法检查 |
| `BuildScripts/verify_render_capture.sh` | Render Capture 专项验证 |

#### 2. 产物目录

上述脚本统一把构建产物输出到：

```text
build/
```

这比手工写到全局 `DerivedData` 更适合作为本项目默认 SOP。

补充说明：

- `build_gui.sh`、`build_and_install.sh`、`build_all.sh` 现在会先自动执行 `BuildScripts/sync_playtools_xcframework.sh`
- 这样可以保证 `Carthage/Checkouts/PlayTools` 中的源码改动会真正进入 GUI 打包产物，而不是继续误用陈旧的 `Carthage/Build/PlayTools.xcframework`

### 四、推荐工作流

#### 1. 只想构建 GUI

```bash
./BuildScripts/build_gui.sh
```

如需 Debug：

```bash
./BuildScripts/build_gui.sh Debug
```

#### 2. 只想构建 CLI

```bash
./BuildScripts/build_mcp.sh
```

#### 3. 运行 MCP 全量测试

```bash
./BuildScripts/test_mcp.sh
```

如果只想跑某个测试类：

```bash
./BuildScripts/test_mcp.sh SigningServiceTests
```

#### 4. 反复调试测试时

先构建一次：

```bash
./BuildScripts/build_for_testing.sh
```

之后重复跑：

```bash
./BuildScripts/test_without_building.sh
```

或指定测试类：

```bash
./BuildScripts/test_without_building.sh KeymapServiceTests
```

#### 5. 做完整回归

```bash
./BuildScripts/build_all.sh
```

这是当前最适合“提交前 / 合入前”的标准回归入口。

### 五、GUI 安装与 live 验证

#### 1. 优先用安装脚本，而不是手工复制 `.app`

推荐直接使用：

```bash
./BuildScripts/build_and_install.sh
```

如需 Debug：

```bash
./BuildScripts/build_and_install.sh Debug
```

该脚本会：

1. 构建 `PlayCover.app`
2. 默认安装到 `~/Applications`
3. 按需切换到 `/Applications`
4. 对安装后的 `.app` 做 ad-hoc 重签名
5. 输出最终安装路径

如需调整安装策略，可使用：

- `PLAYCOVER_INSTALL_MODE=user`
- `PLAYCOVER_INSTALL_MODE=auto`
- `PLAYCOVER_INSTALL_MODE=system`

例如：

```bash
PLAYCOVER_INSTALL_MODE=auto ./BuildScripts/build_and_install.sh
```

#### 2. GUI live 验证时的启动方式

不要默认用：

- `open -a PlayCover`
- 直接执行 `Contents/MacOS/PlayCover`

更稳妥的做法是：

1. 先用 `BuildScripts/build_and_install.sh` 完成安装
2. 再对脚本输出的最终安装路径执行 `open <绝对路径>`

#### 3. GUI 重启后要重新 initialize

只要 GUI 重装、重启、切换 transport，原有 `Mcp-Session-Id` 都不应继续复用。

### 六、HTTP 冒烟验证

#### 1. 标准脚本入口

当前仓库里的 HTTP 冒烟脚本仍然是：

- `Scripts/test_http_mcp.sh`

它不在 `BuildScripts/` 下，但仍然是**HTTP 协议级验证**的直接入口。

建议组合方式是：

1. 先用 `BuildScripts/build_and_install.sh` 安装并启动目标 GUI
2. 再用 `Scripts/test_http_mcp.sh` 做 HTTP MCP 冒烟

#### 2. 最小手工 HTTP 流程（仅在需要排查协议细节时）

如需直接排查 `/mcp` 协议行为，可手工执行：

##### initialize

```bash
curl -X POST http://127.0.0.1:19820/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"test","version":"1.0"}}}'
```

成功后应拿到：

- JSON-RPC 响应 body
- `Mcp-Session-Id` header
- `Mcp-Protocol-Version` header

##### initialized notification

```bash
curl -X POST http://127.0.0.1:19820/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Mcp-Session-Id: <session-id>" \
  -H "Mcp-Protocol-Version: 2025-11-25" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
```

##### tools/list

```bash
curl -X POST http://127.0.0.1:19820/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Mcp-Session-Id: <session-id>" \
  -H "Mcp-Protocol-Version: 2025-11-25" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'
```

##### 打开 SSE 监听流

```bash
curl -N http://127.0.0.1:19820/mcp \
  -H "Accept: text/event-stream" \
  -H "Mcp-Session-Id: <session-id>" \
  -H "Mcp-Protocol-Version: 2025-11-25"
```

##### 关闭 session

```bash
curl -X DELETE http://127.0.0.1:19820/mcp \
  -H "Mcp-Session-Id: <session-id>"
```

### 七、`pbxproj` 验证

如果这次修改涉及 `PlayCover.xcodeproj/project.pbxproj`，优先用：

```bash
./BuildScripts/lint_pbxproj.sh
```

而不是手工再敲一遍 `plutil -lint`。

### 八、Session / Runtime 联调前检查

如果你要测 `create_session`、`tap`、`swipe`、`press_key`、`capture_metal_frame`，建议先检查：

1. GUI HTTP 端点是否正常
2. `52741` 是否被当前 `PlayCover.app` 持有
3. 是否有残留 CLI `PlayCoverMCP` 进程占用 runtime 注册端口
4. 被测 app 是否 fresh launch

### 九、验证分层建议

#### L1：构建验证

- `./BuildScripts/build_gui.sh`
- `./BuildScripts/build_mcp.sh`

#### L2：单元测试

- `./BuildScripts/test_mcp.sh`

#### L3：协议级冒烟

- `./BuildScripts/build_and_install.sh`
- `Scripts/test_http_mcp.sh`

#### L4：能力级验证

- 只读工具
- 设置修改
- keymap 增删改查
- `install_ipa` 与任务查询

#### L5：真实 runtime 联调

- `create_session`
- `tap` / `swipe` / `drag`
- `press_key` / `type_text`
- `capture_metal_frame`

如涉及 Render Capture 专项回归，可补充：

- `./BuildScripts/verify_render_capture.sh`
- `./BuildScripts/probe_metal_capture_env.sh`

其中：

- `verify_render_capture.sh` 更适合检查仓库内实现与接线是否齐全
- `probe_metal_capture_env.sh` 更适合区分当前阻塞点究竟是 **PlayCover session 链路问题**，还是 **当前机器 / Xcode-Metal 运行环境级限制**
- 如果普通 Swift 进程中 `default_device` 可见，但 `supports_gpu_trace=false` 且 `supports_developer_tools=false`，应优先转向系统 / 工具链 / Apple API 限制分析，而不是继续换更多真实 app

### 十、接入结论

如果你今天要新写一个 PlayCover MCP 客户端，最稳妥的默认假设应该是：

1. **GUI 用 HTTP**
2. **CLI 用 stdio**
3. **项目内构建 / 测试 / 安装优先使用 `BuildScripts/`**
4. **HTTP 协议级冒烟优先使用 `Scripts/test_http_mcp.sh`**
5. **长任务不要只看 `install_ipa` 的返回值，要继续用 `get_task` / `list_tasks`**
6. **GUI restart 之后重新 initialize，拿新 session**
