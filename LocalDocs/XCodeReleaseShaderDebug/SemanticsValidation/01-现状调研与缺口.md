## 现状调研与缺口

## 目的

本文档承接当前语义验证现状的调研结论，回答两个问题：

1. **我们已经有什么？**
2. **为什么这些能力还不足以证明语义等价？**

主文档只保留结论与任务控制面；本文件保留当前现状、能力边界与缺口说明。若只是推进日常主线任务，优先读 `00-Dashboard.md` 与 `02-总体技术路线.md`；本文件按需阅读即可。

## 当前已确认的事实

### 1. 文档目标明确要求“语义等价”

前置任务已经把优先级写得很清楚：

1. **语义等价**
2. **可编译**
3. **可读性**

也就是说，项目目标并不是“能把源码塞进 `.gputrace` 就行”，而是希望生成的 MSL 与原始 IR 在语义上尽量一致。

### 2. 当前主链路已经成熟

当前已具备的链路：

- hook `makeLibrary(...)`
- 从 `metallib` 提取 bitcode module
- 用 `llvm-dis` 反汇编为 LLVM IR 文本
- `IRToMSLConverter` 生成 MSL
- `makeLibrary(source:)` 或 `metal -c` 编译
- 对成功与失败样本都能形成离线输入

这说明语义验证专项不需要重建基础设施，而是在**已有 replay/corpus/runtime 工具链之上补一层更严格的验证体系**。

### 3. 当前已有的工程保证

当前已存在的保证主要有四类：

- **翻译策略**：`IRToMSLConverter` 采用逐指令机械翻译，而不是自由重写
- **结构卫生**：生成 MSL 时会检查 LLVM token 泄漏
- **可编译性**：离线与 runtime 都要求生成结果能通过 Metal 编译器
- **回归能力**：已有 replay / compile / baseline diff / `.gputrace` 检查 / render-structure diff

这些能力对工程落地非常重要，但它们并不等于“语义已经被证明”。

### 4. 当前阶段更适合把它当作“前置任务完成后的深化验证”来看

结合最近进展回看，前置任务已经把采集、replay、compile 与运行时验证链路逐步铺开；而 `Semantics Validation` 当前更像：

- 把已有能力继续沉淀成低成本离线证据
- 帮助把“compile green / replay green”继续推进到“结构风险可见”
- 在不引入人工 gate 的前提下，为后续 L3/L4 提供更清晰的入口

因此这里的重点应放在“把已有能力收口成稳定日常 gate”，而不是把篇幅放在说明它处于哪一层关系里。

## 当前缺口

### 1. L1 round-trip 已落地，但还没有结构化 compare

这节标题保留的是本专项立项时的原始缺口表述；按当前进展回看，这个缺口已经**不是 active gap**。当前已经具备：

- `Scripts/ir_semantics_roundtrip_runner.py`
- `Scripts/ir_canonical_compare.py`
- `compare-summary.json / risk-report.json / high-risk-samples.json`
- `test-data/` 首轮批量结果与固定 preset 入口

因此当前真正缺的，已经不再是“有没有结构化 compare”，而是：

- 如何把 L1/L2 收口成**稳定、低心智负担、跨机器仍可执行**的日常 gate
- 如何把 `test-data-representatives` 维持为硬默认入口，同时把 `ShaderCorpus` 保持为本地增强证据
- 如何让代表集、gate profile、baseline snapshot 与 manifest 一起维护，避免边界漂移

### 2. 没有 canonical compare

这条同样已经从 active gap 变成了**已关闭的历史缺口**。当前 compare 已不再只是文本 diff，而是可以专门比较：

- 原始 IR 结构摘要 vs regenerated IR 结构摘要
- 关键 entry / 地址空间 / builtin / CFG / instruction family / fast-math 语义点
- 差异风险应该如何分级

因此现在的问题已经切换为：

- L2 风险分级是否稳定进入日常回归入口
- `L2` 样本如何先在代表集内聚类、缩面，再进入 `L3`
- `gate-summary.json` 的已知 debt / 新增回归语义，是否已经足够支撑后续 `SV-006`

### 3. 没有行为级测试

`test-data/` 当前更像：

- lowering 模式样本
- replay/compile 的回归样本
- 编译器行为探针

而不是：

- 固定输入 → 执行 shader → 校验输出

因此它还不是“行为 gold test”。这一点到当前仍然成立，也是 `SV-004` 仍未进入完成态的直接原因；并且在 `SV-003 / SV-006` 收敛前，不应让 `SV-004` 抢跑成为主线。

### 4. 真实场景验证还不是严格后置 gate

虽然仓库里已经具备：

- `.gputrace` 检查
- render diff
- launch diagnostics
- MCP live 控制能力

但当前仍需继续明确：

- 何时允许进入 L4
- 哪些场景/样本属于默认代表集
- 哪些验证可自动完成，哪些必须先征求用户确认
- 若本机没有现成 live 条件，如何在不增加人工依赖的前提下合理止损

换句话说，L4 当前仍应保持“严格后置、自动化优先、人工确认兜底”的角色，而不是被写回日常默认流程。

## 为什么“文本一致”不是最终目标

语义验证需要明确区分：

### 1. IR 文本/结构完全相同

这通常意味着：

- 指令级组织几乎一致
- SSA 命名、块拆分、metadata 形态也很接近

### 2. IR 语义相同

这只要求：

- 对同样输入产生同样行为
- 资源/地址空间/builtin/输出语义一致

两者不等价。即使未来补了 round-trip，也不应把“字节级 identical IR”当成唯一目标。更合理的方向是：

- 先做 **canonical summary compare**
- 再做 **风险分级**
- 再在高风险或关键样本上补 **行为级/真实场景验证**

## 当前最准确的现状表述

推荐统一使用下面这句话描述当前状态：

> **“语义等价”仍然是明确目标；L1/L2 的自动化离线证据已经形成，当前阶段缺的已不是 runner 或 compare 本身，而是如何把这些能力收口成稳定日常 gate，并为 L3/L4 建立严格的升级边界。因此现状仍属于“已经具备结构化语义证据”，而不是“已经拥有严格语义保证”。**

## 对本专项的直接启示

### 主优先级

现阶段优先做：

1. **`SV-003`：把 L1/L2 收口成稳定日常 gate，并扩到代表性 `ShaderCorpus`**
2. **`SV-006`：明确什么时候可以停在 L2，什么时候必须升级到 L3/L4**
3. **`SV-004`：在经过聚类与代表集选择后，再补 compute-first 行为测试**

因为当前最稀缺的，不是 compare 指标，而是：

- 更低心智负担的默认入口
- 更清晰的升级/止损规则
- 真正能承接 L2 风险结果的行为级样本入口

### 不要过早重投入的方向

在 `SV-003 / SV-006` 没有形成前，默认不把下面方向当成主线：

- 大规模 live 验证
- GUI 自动化重度依赖
- 用户手动参与的 render 对照
- 高成本工作区外分析

这些都应当后置到 L3/L4 需要时再启用。
