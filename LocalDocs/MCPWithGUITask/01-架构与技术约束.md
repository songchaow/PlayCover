# 架构与技术约束

> 本文件是所有 agent 的必读参考，包含技术方案摘要、关键决策和代码锚点。

## 一、方案概述：进程内 TCP Transport（A2）

```
┌─────────────────────────────────────────────┐
│  PlayCover.app (GUI 进程)                     │
│                                               │
│  ┌──────────┐   ┌───────────┐   ┌──────────┐ │
│  │ SwiftUI  │   │MCPManager │   │ TCP:19820│◀── Agent (Claude/Cursor)
│  │   Views  │   │           │   │Transport │ │
│  └────┬─────┘   └─────┬─────┘   └────┬─────┘ │
│       │               │              │        │
│       │         ┌─────▼─────┐        │        │
│       │         │ MCPServer │◀───────┘        │
│       │         └─────┬─────┘                 │
│       │               │                       │
│       │    ┌──────────▼───────────┐           │
│       │    │  Service Layer       │           │
│       │    │  (App/Install/Sign/  │           │
│       │    │   Keymap/Settings/   │           │
│       │    │   Launch/Cleanup/    │           │
│       │    │   Injection)         │           │
│       │    └──────────┬───────────┘           │
│       │               │                       │
│       │    NotificationCenter                 │
│       │               │                       │
│       ◀───────────────┘                       │
│  (GUI 自动刷新)                                │
└─────────────────────────────────────────────┘
```

核心收益：
- **状态共享**：MCP 操作 → NotificationCenter → GUI ViewModel 自动刷新
- **单进程部署**：无子进程管理
- **多客户端**：TCP 支持多个 Agent 同时连接

## 二、关键技术决策

### 2.1 代码集成方式

**推荐方案**：将 MCP 源文件直接添加到 PlayCover.app target 的 target membership（双 target 编译）。

> 注意：规划文档提到了创建 `PlayCoverMCPCore` 共享 framework 的方案，但考虑到：
> - 当前测试 target 采用源码直编模式，framework 化需要同步改造测试 target
> - framework target 的 pbxproj 改动量大（新增 target + build phases + configurations + dependencies + embed phase）
> - 直接 target membership 改动更小、风险更低
> 
> **建议 G02 agent 评估两种方案的可行性，优先尝试简单方案（target membership），如果遇到无法解决的编译问题再升级到 framework 方案。**

需排除的文件（GUI target 不编译）：
- `PlayCoverMCP/main.swift`（CLI 入口，GUI 有 @main）
- `PlayCoverMCP/Transport/StdioTransport.swift`（GUI 用 TCPTransport）

### 2.2 TCPTransport 设计

- 基于 `Network.framework`（`NWListener` + `NWConnection`）
- 仅监听 `127.0.0.1:19820`（loopback）
- 行分隔 JSON-RPC 协议（与 StdioTransport 完全一致）
- `MessageHandler` 签名与 StdioTransport 相同：`@Sendable (JSONRPCMessage) -> JSONRPCMessage?`
- 后台 DispatchQueue，不阻塞主线程
- 支持多客户端并发连接

### 2.3 MCPManager 启停

```swift
// PlayCoverApp.swift → AppDelegate
func applicationDidFinishLaunching(_ notification: Notification) {
    // ... 现有代码保持不变 ...
    MCPManager.shared.start()   // 新增
}

func applicationWillTerminate(_ notification: Notification) {
    MCPManager.shared.stop()    // 新增方法
}
```

`MCPManager.start()` 内部复现 `main.swift` 的 bootstrap 逻辑，但使用 `TCPTransport` 替代 `StdioTransport`。

### 2.4 GUI-MCP 状态联动

使用 `NotificationCenter` 解耦，MCP Service 操作完成后 post 通知，GUI ViewModel 监听并刷新：

```swift
// 通知名
extension Notification.Name {
    static let mcpAppsChanged = Notification.Name("io.playcover.mcp.appsChanged")
    static let mcpSettingsChanged = Notification.Name("io.playcover.mcp.settingsChanged")
    static let mcpKeymapsChanged = Notification.Name("io.playcover.mcp.keymapsChanged")
}
```

需要联动的操作：

| MCP 操作 | 通知 | GUI 刷新目标 |
|---------|------|-------------|
| `install_ipa` | `mcpAppsChanged` | `AppsVM.fetchApps()` |
| `uninstall_app` | `mcpAppsChanged` | `AppsVM.fetchApps()` |
| `inject_playtools` / `remove_playtools` | `mcpAppsChanged` | `AppsVM.fetchApps()` |
| `clear_app_data` / `clear_app_settings` | `mcpAppsChanged` | `AppsVM.fetchApps()` |
| `update_app_settings` | `mcpSettingsChanged` | 对应 app 的 settings 重新加载 |
| `create/delete/rename_keymap` | `mcpKeymapsChanged` | 对应 app 的 keymap 重新加载 |
| `resign_app` | 无需 | 不改变列表状态 |
| `launch_app` | 可选 | 更新运行状态指示 |

### 3.4 Xcode 工程结构

- **3 个 Target**：`PlayCover`（GUI app）、`PlayCoverMCP`（CLI tool）、`PlayCoverMCPTests`（unit test）
- **2 个 Scheme**：`PlayCover`、`PlayCoverMCP`
- **2 个 Build Configuration**：`Release`、`Nightly`
- **无 PlayCoverMCPCore framework target**（需要在 G02 中创建或采用替代方案）
- **PlayCoverMCP 的 Frameworks build phase 为空**（不链接任何外部框架）
- **PlayCoverMCPTests 直接编译所有被测源文件（约 63 个文件条目）**

### 3.5 main.swift 的完整 Bootstrap 顺序

MCPManager 需要复现以下逻辑（参考 `PlayCoverMCP/main.swift`）：

```
1. 创建 MCPLogger(minLevel: .info)
2. 创建 TaskManager()
3. 创建 MCPServer(serverInfo, capabilities, logger, taskManager)
4. 注册 Service + Tools + Resources：
   a. AppService.defaultService()       → AppTools.register() + AppResources.register()
   b. SettingsService.defaultService()   → SettingsResources.register() + SettingsTools.register()
   c. InstallerService.defaultService()  → InstallerTools.register()
   d. LaunchService.defaultService()     → LaunchTools.register()
   e. CleanupService.defaultService()    → CleanupTools.register()
   f. SigningService.defaultService()    → SigningTools.register()
   g. InjectionService.defaultService()  → InjectionTools.register()
   h. KeymapService.defaultService()     → KeymapTools.register()
   i. SessionRegistry() + SessionService → SessionTools.register() + SessionResources.register()
   j. TouchService(registry:)            → TouchTools.register()
   k. InputService(registry:)            → InputTools.register()
5. 创建 Transport（TCP 替代 Stdio）→ transport.start()
```
