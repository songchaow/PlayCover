## RC-012：原神截帧兼容性攻关

### 一、任务目标

让原神能成功执行 `capture_metal_frame` 生成 `.gputrace`。

### 二、状态

**DONE** — 结论：原神与 `GPUToolsCapture` 根本不兼容，截帧不可用。已实现防崩溃 stubs + 双模式注入。

### 三、调查过程

#### 3.1 延迟 dlopen 后原神仍崩溃

RC-011 验证了原神在延迟注入模式下可以正常启动。但调用 `get_capture_status`（触发 `dlopen`）后约 10 秒，原神崩溃。

**第一次崩溃**（`doesNotRecognizeSelector`）：
```
MakeLayerInfos → OpenLayerStream → CAMetalLayer_shimDrawable → [CAMetalLayer nextDrawable]
```
`GPUToolsCapture` hook 了 `nextDrawable`，渲染线程触发 hook 时，`MakeLayerInfos` 对预创建的 Metal 对象调用 `traceStream` 失败。

#### 3.2 反汇编 GPUToolsCapture 定位根因

通过 `otool -tV` 反汇编 `MakeLayerInfos` 函数（`/System/Library/PrivateFrameworks/GPUToolsCapture.framework`），完整还原了它调用的 selector 序列：

```
对每个 tracked layer:
  layer.device           → MTLDevice (标准属性)
  device.traceStream     → CaptureMTLDevice 私有方法 (崩溃点 1)
  layer.streamReference  → GPUToolsCapture 私有方法 (崩溃点 2)
  layer.frame            → CALayer 标准属性
  layer.name             → CALayer 标准属性
```

**崩溃确认**：
- 崩溃偏移 `0x7e830`（`MakeLayerInfos + 0xF8`）精确对应 `bl _objc_msgSend$traceStream` 后的 `cbz` 指令
- 对象是 `device`（`AGXG16XFamilyDevice`），不是 `CaptureMTLDevice` 代理
- 后续 `CaptureMTLDrawable.texture` 方法中也对 texture 对象调用 `traceStream` 导致二次崩溃

#### 3.3 NSObject fallback stubs 方案

**方案**：在 `dlopen` 前给 `NSObject` 添加 `traceStream` 和 `streamReference` 的 nil-returning stub。

**效果**：
- `MakeLayerInfos` 不再崩溃（`traceStream` 返回 nil，`cbz` 分支跳过）
- `CaptureMTLDrawable.texture` 不再崩溃
- 原神可正常运行，`get_capture_status` 返回 `supportsGPUTrace=true`

#### 3.4 截帧仍失败：stopCapture SIGSEGV

`capture_metal_frame` 能成功 `startCapture`，但 `stopCapture` 时崩溃：
```
GTTraceContextDumpEmptyCapture → SIGSEGV
```

**根因**：延迟 dlopen 后，预创建的 Metal 对象不是 `Capture*` 代理，`GPUToolsCapture` 无法拦截 GPU 命令流，trace context 始终为空。`stopCapture` 访问空 trace context 导致段错误。

**这是 Apple 私有框架内部的 bug**，无法通过 ObjC runtime 修补。

#### 3.5 启动期注入验证

尝试对原神开启 `injectMetalCaptureEnvironment=true`（`DYLD_INSERT_LIBRARIES`），结果启动即 SIGABRT：
```
GPUToolsCapture.CAMetalLayer_init → MakeLayerInfos → doesNotRecognizeSelector
```
与 RC-009 之前的崩溃一致。原神的 `CAMetalLayer` 子类/代理不兼容 `GPUToolsCapture` 的 hook。

### 四、最终结论

| 维度 | 结论 |
|---|---|
| 原神 + 延迟注入 | ✅ 正常启动运行 / ❌ 截帧失败 (空 trace → SIGSEGV) |
| 原神 + 启动期注入 | ❌ 启动崩溃 (SIGABRT) |
| **根本原因** | 原神的 Metal 使用方式与 `GPUToolsCapture` 的 hook 不兼容 |
| **结论** | 当前 Apple GPUToolsCapture 框架无法对原神进行截帧 |

### 五、代码改动

1. **`MetalCaptureService.swift`**：
   - 新增 `installGPUToolsCaptureCompatStubs()`：dlopen 前在 `NSObject` 上安装 `traceStream`/`streamReference` nil-returning stubs
   - 新增 `installGPUToolsCaptureCompatStubsPostLoad()`：dlopen 后的检查
   - `stopActiveCapture()` 增加 `manager.isCapturing` 检查
   - `ensureGPUToolsCaptureLoaded()` 增加 uncaught exception handler（诊断用）

2. **`PlayApp.swift`**：
   - `injectedMetalCaptureEnvironment` 恢复 `DYLD_INSERT_LIBRARIES` 字段（双模式注入）

3. **`LaunchService.swift`**：
   - `injectedMetalCaptureEnvironment` 同步添加 `DYLD_INSERT_LIBRARIES`
