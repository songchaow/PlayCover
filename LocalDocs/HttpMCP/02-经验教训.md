## 一、Xcode 工程文件（pbxproj）

### 1.1 三步验证铁律

**每次修改 pbxproj 后**必须执行：

```bash
# 步骤 1: 语法检查
plutil -lint PlayCover.xcodeproj/project.pbxproj

# 步骤 2: 变更审查
git diff PlayCover.xcodeproj/project.pbxproj

# 步骤 3: 编译验证
xcodebuild -scheme PlayCover -configuration Release build \
  -derivedDataPath /tmp/PlayCover-DerivedData \
  FASTLANE=1 CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES 2>&1 | tail -20
```

**不要跳过任何一步。** `plutil -lint` 只检查语法，`git diff` 确认改动范围，`build` 验证语义正确。

### 1.2 修改 pbxproj 优先用 replace_in_file

| 方式 | 推荐度 | 原因 |
|------|:------:|------|
| `replace_in_file` 多行精确匹配 | ✅ 首选 | 可包含上下文，精确定位到正确 section |
| Python 脚本 `str.replace()` | ⚠️ 慎用 | 同一 ID 在多个 section 出现，容易替换到错位置 |
| 手动编辑 | ❌ 禁止 | 格式极其严格，空格/缩进错误即导致不可解析 |

pbxproj 修改需要在 **4 个 section** 分别操作：
1. `PBXBuildFile` — 添加构建文件条目
2. `PBXFileReference` — 添加文件引用
3. `PBXGroup` — 在 `children` 列表中插入引用
4. `PBXSourcesBuildPhase` — 在 `files` 列表中插入构建文件

### 1.3 Target membership 同步规则

新增 `.swift` 文件时，必须根据 Target 归属矩阵添加到所有需要的 target：

| 文件类型 | PlayCover (GUI) | PlayCoverMCP (CLI) | PlayCoverMCPTests |
|---------|:-:|:-:|:-:|
| 通用 MCP 业务文件 | ✅ | ✅ | ✅ |
| GUI 专属文件（View / Manager） | ✅ | ❌ | ❌ |
| CLI 专属文件（main.swift 等） | ❌ | ✅ | ❌ |
| 测试文件 | ❌ | ❌ | ✅ |
| **Hummingbird 依赖文件（StreamableHTTPTransport 等）** | **✅** | **❌** | **❌** |
| **无外部依赖的工具文件（SSEEncoder、MCPSessionManager）** | **✅** | **✅** | **✅** |

> ⚠️ PlayCoverMCPTests 直接编译源文件，不链接 framework。因此每个需要测试的文件必须在 Tests target 有独立的 PBXBuildFile 条目。

### 1.4 首次引入 SPM 对 pbxproj 的影响

本项目首次使用 SPM（添加 Hummingbird），会在 pbxproj 中新增以下 section：

| Section | 作用 |
|---------|------|
| `XCRemoteSwiftPackageReference` | SPM 包的 URL 和版本约束 |
| `XCSwiftPackageProductDependency` | 引用的具体 product |
| `packageReferences` | 在 project object 中注册包引用 |
| `packageProductDependencies` | 在 target 中注册 product 依赖 |

这些由 Xcode "Add Package" 自动生成，手动修改风险极高。**推荐通过 Xcode 添加 SPM 包后再 `git diff` 审查变更。**

## 二、构建与签名

### 2.1 标准构建参数

所有构建命令必须包含以下参数：

```bash
FASTLANE=1                    # 跳过 Carthage Bootstrap 和 SwiftLint
CODE_SIGN_IDENTITY="-"        # ad-hoc 签名
CODE_SIGNING_REQUIRED=NO      # 跳过严格签名检查
CODE_SIGNING_ALLOWED=YES      # 允许 ad-hoc
-derivedDataPath /tmp/PlayCover-DerivedData  # 避免缓存污染
```

### 2.2 FASTLANE=1 跳过的与不跳过的 Build Phase

`FASTLANE=1` 通过 `if [[ -z "$FASTLANE" ]]` 条件，跳过以下 Build Phase 脚本：

| Build Phase | 是否被 FASTLANE=1 跳过 |
|-------------|:---------------------:|
| Carthage Bootstrap | ✅ 跳过 |
| SwiftLint | ✅ 跳过 |
| Copy Carthage frameworks | ❌ 仍执行（需 carthage 可用） |
| Codesign sparkle | ❌ 仍执行（已有 ad-hoc fallback） |

使用完整构建参数（`FASTLANE=1` + ad-hoc 签名），所有 Build Phase 均可正常通过，**BUILD SUCCEEDED 即为编译成功的判定标准**。

> 前提：环境中 carthage 已安装（`/opt/homebrew/bin/carthage`），且 `Carthage/Checkouts/` 目录已存在。首次 clone 仓库后需先运行一次 `carthage checkout`。

### 2.3 独立 DerivedData 必要性

Yams（Hummingbird 的间接依赖）仓库包含 Bazel 的 `BUILD` 文件。macOS 文件系统不区分大小写时，会与 Xcode 需要创建的 `build` 目录冲突。使用 `-derivedDataPath /tmp/PlayCover-DerivedData` 可绕过。

## 三、跨模块依赖

### 3.1 PlayCoverMCP ≠ PlayCover

`PlayCoverMCP` 是独立的 CLI target，**不链接 PlayCover framework**：

- ❌ 不能 `import PlayCover`
- ❌ 不能使用 `PlayTools`、`PlayApp`、`Entitlements` 等 GUI 类
- ✅ 通过 `Shell.run()` 调用系统命令实现功能

### 3.2 Hummingbird 的依赖隔离

Hummingbird + SwiftNIO 仅链接到 **PlayCover GUI target**：

- CLI target 不需要 HTTP 服务器（继续用 StdioTransport）
- Tests target 不需要 Hummingbird（SSEEncoder 和 MCPSessionManager 无外部依赖，可独立测试）
- `StreamableHTTPTransport.swift` 仅编译到 GUI target

### 3.3 SwiftNIO EventLoop vs GCD

| 层 | 线程模型 | 注意事项 |
|---|---------|---------|
| Hummingbird route handler | SwiftNIO EventLoop | 不可执行阻塞操作 |
| MCPServer.handle() | NSLock 保护 | 已线程安全，可在任何线程调用 |
| @Published 属性 | 必须在主线程 | 从 EventLoop 回到主线程用 `DispatchQueue.main.async` |

## 四、Swift / Foundation API 注意事项

### 4.1 plist 类型限制

`URL` 对象不是合法 plist 值。写入 plist 时用 `.path`（String），读取时用 `URL(fileURLWithPath:)` 转回。

### 4.2 URL 比较不可靠

用 `lastPathComponent` 比较文件身份，不要用 `==`（路径规范化方式不同可能导致 false negative）。

### 4.3 filter 语义是"保留"

```swift
// 删除特定元素 — 条件取反！
array = array.filter { $0 !== targetToRemove }
```

### 4.4 WMO 下同名文件冲突

Whole Module Optimization 不允许同一 target 中有两个同名 `.swift` 文件（即使内部类名不同）。新增文件名避免与现有文件重复。

### 4.5 AnyCodable 初始化陷阱

WMO 模式下，`AnyCodable(["key": "value"])` 可能被推断为 `init(from:) throws`。显式声明参数类型为 `Any?` 以强制使用 `init(_ value: Any?)` 初始化器。

## 五、网络层 / Transport 相关

### 5.1 NWConnection 异步生命周期

`NWConnection.start()` 是异步的，必须在 `stateUpdateHandler` 检测到 `.ready` 后才能开始 `receive()`。

### 5.2 TCP 行分隔协议

测试中发送 JSON-RPC 请求时，**必须以 `\n` 结尾**，否则 TCPTransport 不处理该消息。

### 5.3 HTTP/SSE 格式要求

MCP 规范的 SSE 格式：

```
data: {"jsonrpc":"2.0",...}\n
\n
```

- 每个事件以 `data: ` 前缀开头
- JSON 中不能有裸换行（需 escape 或单行输出）
- 事件之间用**空行**分隔（即两个 `\n`）
- 可选 `id:` 字段（用于断线恢复，本轮暂不实现）

### 5.4 Origin 验证

MCP 规范要求服务端对 HTTP 请求做 Origin 验证以防 DNS rebinding 攻击：

- `localhost`、`127.0.0.1`、`[::1]` 视为合法
- 无 Origin Header 的请求也应放行（curl/CLI 客户端不发 Origin）
- 其他 Origin → 返回 403

### 5.5 Session 管理陷阱

- TCP 模型：连接 = 会话，断开即清理
- HTTP 模型：无连接概念，需显式管理 `Mcp-Session-Id` 的创建、验证、超时和清理
- 过期 Session 要通过定时器或 LRU 策略清理，否则会内存泄漏

## 六、任务执行通用原则

### 6.1 先确认架构可行性再写代码

1. 验证 target 依赖（能否导入需要的模块）
2. 验证关键 API 签名（参数、返回值、sync/async）
3. 验证测试 target 结构（被测文件可见性）
4. **然后**才写实现代码

### 6.2 小步验证

每次改动后立即构建验证，不要累积多个改动再一起验证。

### 6.3 先读后写

编辑文件前先 `read_file` 确认当前内容，避免基于过时信息编辑。

### 6.4 善用 git checkout 恢复

pbxproj 修改出问题时，立即 `git checkout -- PlayCover.xcodeproj/project.pbxproj` 恢复，不要尝试手动修补。

### 6.5 脚本使用绝对路径

Python 脚本中所有路径都用 `os.path.abspath()` 构造。避免相对路径 + `cwd` 参数导致的路径双重拼接问题。

### 6.6 脚本失败时不要静默成功

`str.replace()` 匹配不到时返回原字符串且不报错。关键操作后必须验证是否真正生效（如检查目标字符串是否存在）。

## 七、本轮特有注意事项

### 7.1 SPM 包版本选择

Hummingbird 选用最新稳定版（from: "2.0.0" 或具体版本），确保 async/await API 可用。如果遇到编译问题，优先检查 Swift 版本兼容性。

### 7.2 保留 TCPTransport

不删除 `TCPTransport.swift`。HTTP Transport 完成后，GUI 默认使用 HTTP，但保留 TCP 作为兼容选项（可通过 TransportType 枚举切换）。

### 7.3 端口复用

复用 `MCPManager` 中已有的 `savedPort` / `savedHost` UserDefaults 配置。默认端口 19820。

### 7.4 测试回归验证

每个 agent 在完成自己的任务后，**必须运行全量测试**验证前序任务未被破坏：

```bash
xcodebuild test -scheme PlayCoverMCP \
  -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath /tmp/PlayCover-DerivedData \
  FASTLANE=1 CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=YES 2>&1 | tail -30
```

### H01：SPM 依赖与项目配置

1. **项目已有 SPM 基础设施**：PlayCover 已通过 SPM 管理 7 个依赖（Yams、Sparkle、DataCache 等），因此 `XCRemoteSwiftPackageReference`、`XCSwiftPackageProductDependency` 等 section 均已存在，添加新包只需在现有 section 末尾追加条目，不需要创建新 section。

2. **SPM 包添加需修改 6 处**：
   - `PBXBuildFile` — `{isa = PBXBuildFile; productRef = <DEP_ID>;}`
   - `PBXFrameworksBuildPhase` — 在 PlayCover GUI target 的 `files` 列表中
   - `PBXNativeTarget.packageProductDependencies` — PlayCover target 的产品依赖列表
   - `PBXProject.packageReferences` — 项目级包引用列表
   - `XCRemoteSwiftPackageReference` — 包的 URL 和版本约束
   - `XCSwiftPackageProductDependency` — 引用的产品名和包引用

3. **Hummingbird 需要 macOS 14+**：Hummingbird 2.x 基于 Swift Concurrency 和 SwiftNIO，API 标注了 `@available(macOS 14, *)`。所有使用 Hummingbird API 的代码必须添加 `@available(macOS 14, *)` 注解。

4. **Hummingbird 2.21.1 实际引入的依赖**：SwiftNIO、swift-log、swift-service-lifecycle、swift-collections、swift-metrics、swift-distributed-tracing、swift-http-types、swift-async-algorithms、swift-atomics、swift-nio-extras、swift-nio-http2、swift-nio-transport-services、swift-nio-ssl、swift-crypto、swift-certificates、swift-asn1、swift-http-structured-headers、async-http-client、swift-system、swift-argument-parser、swift-numerics、swift-algorithms。依赖链较长，首次解析耗时较长。

5. **SPM 与 Carthage 共存验证成功**：Hummingbird 通过 SPM 引入后，Carthage 管理的 PlayTools 不受影响，CLI target 和 Tests target 编译正常（624 tests, 0 failures）。
