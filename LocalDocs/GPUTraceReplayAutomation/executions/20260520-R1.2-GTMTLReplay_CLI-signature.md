## 2. GTMTLReplayCLIOptions 结构体重建

通过反汇编中对 `options` 指针的解引用模式，重建出以下字段布局：

| 偏移 | 大小 | 名称（推测） | 证据 |
|------|------|-------------|------|
| +0x08 | ptr | device? | 被加载后调用 `defaultCommandQueue` |
| +0x18 | int32 | loopCount | 字符串 `"replayCapture, loop count=%d/%d"`；循环计数器 w25 与之比较 |
| +0x25 | uint8 (bool) | waitForCompletion | 为 1 时调用 `defaultCommandQueue` → `finish` → `rewind` |
| +0x28 | ptr (char*) | errorLogPath? | 被传给 `stringWithUTF8String:` |
| +0x30 | ptr (char*) | saveDestination | 字符串 `"options.saveDestination=%s"` |
| +0x38 | ptr | 未确定 | 被读取后用于选择器调用 |
| +0xa4 | int32 | gpuStateLevel | bit31 = 禁用；否则 clamp ≥ 2，作为 `@"GPUState"` 键的值 |
| +0xb8 | uint32 (flags) | profilingFlags | 位域，各 bit 控制不同行为 |
| +0xba | uint8 | optimizeRestoresFlags | 低 bits 3-6 (mask 0x78) 控制 `GTMTLReplayController_optimizeRestores` |

### profilingFlags (+0xb8) 已知位定义

| Bit | 含义（推测） | 证据 |
|-----|------------|------|
| bit 6 | ATF_RESULTSDIRECTORY override | `orr w8, w8, #0x40` 在 `ATF_RESULTSDIRECTORY` 检查后设置 |
| bit 17 | profileBatchIdFilter | `ubfx w2, w8, #17, #1` 提取后作为 `@"profileBatchIdFilter"` 的值 |
| bit 21-22 | num_cores 相关 | `and w8, w8, #0xff9fffff; orr w8, w8, #0x400000` 在 num_cores ≥ 7 时设置 |

## 4. g_runningInCI / g_runningValidationCI 分析

| 全局变量 | 地址 | 当前默认值 | 作用 |
|---------|------|-----------|------|
| `g_runningInCI` | 0x2a57843e0 | 0 (false) | 控制 `#CI-INFO#` / `#CI_ERROR#` 格式化日志输出 |
| `g_runningValidationCI` | 0x2a57843e1 | 0 (false) | 未在 CLI 函数中直接使用，可能影响其他子系统 |
| `GT_ENV` | 0x2a57843a8 | NULL | 未初始化；可能需要外部设置 |

**关键发现**：`g_runningInCI` **仅控制日志格式**，不影响实际 replay 逻辑。即使 `g_runningInCI = 0`，`GTMTLReplay_CLI` 仍会正常执行全部 replay 流程。

## 6. Headless Replay 可行性结论

### ✅ 可行

`GTMTLReplay_CLI` 是一个**独立的 C 函数**，不依赖任何 GUI/XPC 基础设施：

1. **参数简单**：只需 gputrace 路径、选项结构体指针、完成回调
2. **不依赖 Xcode**：自行创建 Metal device、初始化 replay controller
3. **CI 友好**：内建 `#CI-INFO#` / `#CI_ERROR#` 日志通道
4. **环境变量控制**：`ATF_RESULTSDIRECTORY` 指定输出目录
5. **支持循环 replay**：`loopCount` 字段控制重放次数

### 调用最小条件

1. `dlopen("GPUToolsReplay.framework")` 成功（需在 macOS 上运行）
2. 有一个合法的 `.gputrace` bundle
3. Metal 设备可用（不需要 display）
4. 构造一个 `GTMTLReplayCLIOptions` 结构体（至少设置 `loopCount = 1`）

### 最小调用伪代码

```c
#include <dlfcn.h>

typedef int (*GTMTLReplay_CLI_fn)(const char*, void*, void*);

void* handle = dlopen("GPUToolsReplay.framework/GPUToolsReplay", RTLD_LAZY);
GTMTLReplay_CLI_fn cli = dlsym(handle, "GTMTLReplay_CLI");

// 构造最小 options（0xC0 字节，大部分为零）
char options[0xC0] = {0};
*(int*)(options + 0x18) = 1;  // loopCount = 1

int result = cli("/path/to/capture.gputrace", options, NULL);
```

## 8. XPC Service 职责分工（附带发现）

从 `GPUToolsReplayService.xpc` 的 strings 和导入分析：

| 服务 | 职责 |
|------|------|
| `GPUToolsReplayService.xpc` | Thin XPC stub，仅导入 `GTMTLReplayController_init` + `GTMTLReplayClient_create/destroyNewTransport`，通过 Mach 内存共享与主进程通信 |
| `GPUToolsCompatService` | bundle 兼容预处理，读 `.gputrace/{startup-0-platform, store0, device-resources-*}` |
| `GPUToolsAgentService` | 推测为设备代理/通信 |

**结论**：`GPUToolsReplayService.xpc` 只是让 replay 引擎运行在独立进程中的 bootstrap wrapper。直接调用 `GTMTLReplay_CLI` 完全绕过了 XPC 层，这正是 Apple CI 使用的路径。
