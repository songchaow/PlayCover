## 恋与深空准备数据阶段网络问题调查进展

### 一、问题背景

当前在 `PlayCover` 中运行 `恋与深空`（`com.papegames.lysk`，版本 `5.0.0`）时，app 会停留在“准备数据”阶段较长时间，随后弹出网络失败。

本轮调查目标不是排查 `PlayCover` 自身 GUI 联网，而是判断：

> **`恋与深空` 自身在准备数据阶段到底有没有把关键请求发出去、哪些请求成功了、又卡在了哪一类网络步骤。**

---

### 二、本轮现场的必要上下文

#### 2.1 当前运行形态

在最新一轮复现现场中：

- `PlayCover` 宿主仍正常运行
- `恋与深空` 新进程 PID 为 `83225`
- `PlayCoverMCP` 可正常连接并看到 runtime session
- app 在启动后会建立多条外连，包括：
  - `api-deepspace.papegames.com:12101`
  - `apm.papegames.com:12101`
  - 若干 `*.papegames.com` / `*.alicdn.com` / 阿里云 / 第三方 SDK 链路

#### 2.2 本地状态

本地偏好和缓存中已能看到：

- 本地 `resVersion = 1.6.1360`
- 服务端 `patchlist` 返回目标 `hotfix_version = 1.6.1374`
- 服务端返回的 `cdn_url` 为：
  - `https://x3cn-client-v7wbza3toheu78pn9r.papegames.com/prd`
  - `https://x3cn-client-v7wbza3toheu78pn9r-backup.papegames.com/prd`

这说明：

> **app 的确已经进入了“检查资源版本 / 决定是否更新”的阶段，而不是启动早期就完全断网。**

---

### 三、当前已确认结论

#### 3.1 `PlayCover` 基本运行态正常，问题不像宿主层“完全没网”

已确认：

- `PlayTools` / runtime session 是活的
- app 能持续建立外部 HTTPS / TCP 连接
- `api-deepspace.papegames.com:12101` 的关键配置请求可以成功返回

因此当前问题**不符合**以下形态：

- `PlayCover` runtime 没启动
- app 完全无法出网
- DNS 全面失败
- TLS 全面失败

更准确地说：

> **这不是“恋与深空完全没法联网”，而是“有一部分链路成功了，但准备数据阶段后续某一步没有继续推进”。**

#### 3.2 `api-deepspace` 主配置接口本身是成功的

在最新一轮启动里，以下请求已成功进入本地 `CFURL` 缓存，并带有正常响应体：

- `entries`
- `privacyagreement`
- `patchlist`
- `parameter(PreDownload_Switch)`
- `parameter(ResUpdate_CheckResIntegrity)`
- `parameter(ResUpdate_ReStartGame)`
- `parameter(SUBPACKAGE_ID)`
- `parameter(DELETABLE_SUBPACKAGE_ID)`
- `parameter(ResUpdate_CheckBPackage_Data)`

其中 `patchlist` 返回内容明确表示：

- 目标热更版本：`1.6.1374`
- scene version：`1.6.1373|15863630|3555270901`
- 资源 CDN 已下发

因此当前可以明确排除一种误判：

> **问题不是“连 `api-deepspace` 都拿不到，所以卡在最早期配置接口”。**

#### 3.3 当前更像是“拿到 patchlist 之后，没有真正进入资源下载推进”

本轮最重要的现象是：

- `patchlist` 已经成功返回
- 本地版本明显落后于服务端目标版本
- 但在本轮新写入的缓存请求里，**没有看到继续进入 `version.txt` / `patch_size.txt` / patch bundle / 实际资源下载 URL 的新记录**

同时：

- 宿主机手工访问下发的 CDN 资源是通的
- `1.6.1374` 对应的：
  - `version.txt`
  - `patch_size.txt`
  都可以直接拿到

因此当前更像：

> **app 成功完成了“配置获取 / 更新判定”，但没有继续推进到真正的资源下载阶段；卡点位于这两者之间，或者就在进入下载前的业务状态机里。**

#### 3.4 存在稳定复现的 30 秒超时请求，但它不像主配置接口

最新一轮现场中，出现了多次重复模式完全一致的超时：

- `NSURLErrorDomain Code=-1001`
- 每次事务时长约 `30078ms ~ 30093ms`
- `request_bytes = 680`
- `response_bytes = 0`
- DNS、TCP、TLS 都很快完成
- 然后整整 30 秒没有收到响应，最终超时
- 失败后立刻重新发起下一次同类请求

而且这几次超时都指向同一个连接特征：

- `Hostname#0d0ba074:443`
- `url hash: d1810b76`

这说明：

> **当前有一条固定的 HTTPS 请求在 30 秒周期内反复超时，但它并不像 `api-deepspace` 的 gameconfig 请求，因为后者已经有成功缓存记录。**

结合启动时序看，这条超时链路更像：

- 第三方 SDK 请求
- 上报 / 策略 / 长连相关请求
- 或某条非 gameconfig 的业务 HTTPS 请求

当前还**不能**仅凭现有证据把它 100% 指认为某个具体域名，但它高度可疑，且确实在反复超时。

---

### 四、当前最高置信判断

综合本轮证据，当前最高置信判断如下：

1. `恋与深空` 在 `PlayCover` 下的**基础联网能力存在**
2. `api-deepspace.papegames.com:12101` 的主配置链路**已经成功**
3. 服务端也已经明确告诉客户端：
   - 需要更新到 `1.6.1374`
   - CDN 地址是什么
4. 但 app **没有继续推进到资源清单 / patch 文件 / 真实下载阶段**
5. 与此同时，存在一条**独立的、固定模式的 30 秒超时 HTTPS 请求**在循环重试

所以当前最合理的问题定义不是：

> **PlayCover 把恋与深空网络彻底搞坏了。**

而是：

> **恋与深空在“准备数据”阶段已经成功完成主配置获取，但后续进入资源更新/下载前的某个步骤没有继续推进；同时还有一条独立的 30 秒超时请求在反复重试，可能干扰或阻塞了该阶段。**

---

### 五、关键证据摘要

#### 5.1 成功证据

- `api-deepspace.papegames.com:12101/v1/gameconfig/patchlist` 有正常 JSON 返回
- `patchlist` 返回：
  - `hotfix_version = 1.6.1374`
  - `cdn_url = x3cn-client-v7wbza3toheu78pn9r.../prd`
- 本机直接访问 CDN：
  - `version.txt` 可读
  - `patch_size.txt` 可读

#### 5.2 卡住证据

- 最新轮启动后，缓存里只看到 `gameconfig` 系列成功
- 没看到紧接着出现新的 `version.txt` / `patch_size.txt` / patch bundle 请求写入缓存
- 存在固定模式的 `-1001 timeout`：
  - 30 秒一轮
  - 响应体始终为 0
  - 失败后立刻继续下一轮

#### 5.3 为什么这很重要

这意味着当前排查重点应从：

- “是不是完全断网”

转为：

- **“为什么 patchlist 已经成功，后续资源更新没有接上”**
- **“那个 30 秒超时的固定 HTTPS 请求到底是谁”**

---

### 六、后续方向

#### 方向 A：优先识别那条固定 30 秒超时请求的真实 URL

当前最值得继续追的目标是：

- `Hostname#0d0ba074:443`
- `url hash: d1810b76`
- `request_bytes=680`
- `response_bytes=0`

需要进一步把它还原成真实 URL / 域名。

这是因为：

- 它是当前现场中最稳定、最可复现的失败模式
- 它在 `patchlist` 成功之后还持续出现
- 如果它恰好是“进入资源更新前的关键接口”，那它就很可能就是主因

#### 方向 B：专盯 `patchlist` 成功之后的第一跳

下一步最关键的不是再证明 `gameconfig` 成功，而是要抓：

> **`patchlist` 成功返回以后，客户端理论上应该访问的第一条资源更新请求是什么，为什么这次没有进入缓存。**

也就是重点观察：

- 是否应该访问 `version.txt`
- 是否应该访问 `patch_size.txt`
- 是否应该开始请求 patch manifest / bundle
- 是否在进入这些请求前，被某个本地状态机、SDK 回调或业务判断挡住

#### 方向 C：把“主配置成功”和“第三方超时”彻底拆开看

当前容易误判的一点是把所有失败都混成“网络失败”。

但从现场看，更合理的拆分是：

- **Papergames 主配置链路：成功**
- **某条固定 HTTPS 请求：稳定 30 秒超时**
- **资源下载推进：未观察到真正开始**

后续调查应继续坚持这个拆分，不要把所有现象粗暴归因为同一个域名或同一个服务。

---

### 七、当前结论（一句话版）

> **截至本轮调查，`恋与深空` 在 `PlayCover` 下并非“完全没网”；它已经成功拿到 `api-deepspace` 的更新配置和 CDN 地址，但没有继续进入真正的资源下载阶段，同时存在一条独立的、固定模式的 30 秒超时 HTTPS 请求在循环重试，这就是后续最应优先钉死的线索。**
